### 6. Z1 (claim 6)

**[S1] The scan reads the gate's three forms but refuses fewer unreadable writes than the plan says.**
- **What the plan claims:** "every … write …, any call handed the notes … anything else fails with its line".
- **What I ran:** 28 snippets through `scan_note_writes` (`g9-tools/z1_probe.py`).
- **Refused, as it should be:**
  - a module constant;
  - a tuple holding a name;
  - `.format(…)` and `%`;
  - a `setdefault` with a variable default;
  - a list built and then assigned or extended;
  - `|=` on the dict;
  - `+=` and slice-assign on an alias;
  - `insert`;
  - a ternary;
  - positional hand-off;
  - an alias of an alias.
- **Pass silently** (nothing read, nothing refused):
  - **dict literals:** `notes = {i: ["code"]}`, `RatingResult(…, notes={i: ["code"]})` and `notes={**notes, i: [...]}`;
  - **a keyword hand-off:** `_add_note(notes=notes, …)`. This contradicts "any call handed the notes": only positional arguments are checked;
  - **aliases the scan does not track:** `for lst in notes.values(): lst.append(CODE)`, `(lst := notes.setdefault(…))`, `n2 = dict(notes)`;
  - **other routes:** attribute access (`result.notes…`), `getattr(…, "append")(CODE)` and `list.append(notes.setdefault(…), CODE)`.
- **Read wrongly:** an f-string whose literal head is not the whole code.
  - `f"sneaky_{kind}_code"` is read as `sneaky`.
  - `f"energy_on_partial_coverage{suffix}"` is read as an existing, HELP-covered code while it writes a new one.
  - The prefix codes the study knows are `:`-separated (`resolution:…`, `tiers_on_represented_volume:…`), so a head not ending in `:` is not a code.
- **Mutations on `tariff_engine.py`** (scratch only), each **surviving** the parity file:
  - G4a: a helper given the notes by keyword, writing `weeks_sampled_unevenly`;
  - G4b: `notes={**notes, "_rating": ["weeks_sampled_unevenly"]}` in the result;
  - G4c: `f"energy_on_partial_coverage{_SUFFIX}"`.
- The gate's own O4a, O4c and O4d are red, as the implementer reports.
- **Impact today:** none. All 12 notes are still covered: `test_every_note_write_in_the_tariff_engine_is_read` passes with `bad == []` on the real file.
- **Why this is a condition:** the purpose of Z1 was that the scan cannot pass a write it did not read, and these are ordinary ways to write code. See **V1**.

**[S2] Latency, double work and the race window (probes P2 and P3).**
- **Latency** (route fixture, fake solver, same machine and load):

  | | base 2ad14b4c | WP9 14d0281f |
  |---|---|---|
  | `POST …/findings/tornado` | **0.30 s** | **5.9–7.4 s** (2 runs) |
  | of which `context_from_disk` | (in the worker) | 1.0–2.0 s |
  | of which `centre_attributions` | — | 4.5–5.2 s |
  | `GET …/findings` (reference) | 6.5 s | 5.6–7.1 s |

  The POST now costs a findings GET.
  - The UI is covered: `Robust` gets `busy={startTornado.isPending}`.
  - The axios timeout is 30 s, so this fixture is safe. A real study whose findings GET takes over 30 s would now time out on the POST too.
- **Double work.**
  - The worker reuses the pre-check's **context** (same object id through `context_from_disk`, `centre_attributions` and `run_tornado`), which saves the second `context_from_disk`.
  - But `run_tornado` → `_centre(ctx, solve)` values every centre case again, about 5 s of engine work per tornado.
  - The pre-check's results are discarded, apart from the bundles, which `_centre` then overwrites.
- **Reuse is safe.**
  - The request thread finishes with `tctx` before `thread.start()`.
  - The handoff is sequential: one owner at a time, and no shared mutation.
  - The only state carried over is `ctx.bundles` and the compiled caches, which `_centre` rebuilds for the same ledger.
- **The race window.** The pre-check runs after the **unlocked** first `_refuse_busy(resident)` and before the locked re-check under `mutation_lock` / `solver_state_lock`.
  - A run started in that window (about 6 s now, about 0 before WP9) replaces the fork files while the pre-check reads them.
  - P3 (a `fork_network_from_disk` that raises `OSError("NetCDF: HDF error")`) shows the POST is then an **untyped 500**: the pre-check catches only `FindingsRefused`.
  - A wrong tornado is not possible: if the read succeeds, the locked re-check refuses 409 `study_running`.
  - The findings GET has the same exposure today (also 500 in P3), so this is not new in kind. It is new for this route, which before WP9 answered 202 and recorded the failure in the worker.
  - The plan's sentence that the move "fixed" the race is accurate for a run already in flight, not for one that starts during the pre-check.
