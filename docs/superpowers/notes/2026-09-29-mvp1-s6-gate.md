**Verdict on the real fixture: `recommended`, which is right.**
- The lowest bound is the demand-charge low bound (80k for `bess_2h`, 289k for `bess_pv_2h`).
- The main caveat is `demand_charge_perfect_foresight` for `bess_2h`, where demand is the top stream (and also for `bess_pv` on its incremental streams, where demand is 76k of 99k).
- The engine names `bess_pv_2h`, because its battery NPV (556k) exceeds `bess_2h`'s (372k). See [S4].

**Constructed cases (`test_study_findings.py`, LP marginal case): correct.**
- `recommended`: best 3e5, every bound positive.
- `marginal`: a bound at −2e4. On the LP, a user's quote of 400 EUR/kWh is re-centred to [280, 520], and fixed sizes give npv_high < 0.
- `not_recommended`: −5 and 0.

**`NPV_TOL_EUR = 1` and break-even.** Defensible in scale.
- A re-dispatch at the centre reproduces the centre NPV to 1e-10 EUR, so 1 EUR is far above solver noise at these magnitudes.
- Two edges are not quite honest. The centre test is strictly `> 0` with no tolerance: a 1.1 kW battery with NPV 0.4 EUR and a bound at −0.9 is `recommended` (probe TINY). And a bound in [−1, 0] still reads "positive … at every tornado bound" (probe BOUND_−0.5). See [N1].

**"Any battery option unattributed → not_established".**
- As coded, it only blocks the `not_recommended` branch. That is right: an unattributed `bess_pv` could be the positive one.
- It does not block `recommended` or `marginal` when an attributed option already decides positive and robust. That is also right for the class, though the named "best" may then not be the best (reason codes carry it).
- It does not over-block. It **under-blocks**: an option with *no attribution at all* is invisible to it. See [B1].

### 2. Battery attribution (PV)

- Verified on a real solve, above: `battery_npv = NPV(bess_pv) − NPV(PV-only at the same PV size)`.
- The reference omits the StorageUnit and fixes PV (asserted by `test_the_bess_pv_battery_is_valued_against_a_pv_only_reference`). CAPEX, replacements and FOM differ by exactly the battery's.
- The streams-as-increment choice is correct economically. For `bess_pv_2h` the increment streams sum to 99,379 EUR/yr (demand 76,359; energy 29,831; network 5,424; export −12,235: the battery soaks up PV that would have been exported). The option's full saving is 365,516 EUR/yr.
- It is disclosed only as the honesty code `value_streams_battery_increment_over_pv_only_reference` plus `value_streams_option`.
- The S5 case route serves *full* streams for the same option id. Two different "value streams of bess_pv_2h" now exist, and nothing typed says which one a list is. See [S5].

### 3. Fixed sizes truly fixed

- **Fixed-size networks.** `fixed_size_network` sets `p_nom = p_nom_max = p_nom_opt`, `p_nom_min = 0` and `extendable=False`. It *omits* a zero-size asset and, for the reference, the battery (BC-1).
- **Explicit config.** `ForkSolver` writes the variant's own `SolverConfig` (`packs.option_solver_config(variant ledger, perturbed tariff)`, `demand_charge` set) to the fork and to the queue job. The route test asserts `solve_strategy == "full"` and `demand_charge` on every tornado call.
- **Discount-rate bar.** The variant rate reaches the ledger, `cfg.discount_rate`, the assets' `discount_rate` and the two-annuity `capital_cost`. Recompute matches. Mutation (e): the rate in the ledger only is refused with `discount_rate_differs_from_lp`.
- **Cost rows.** Storage cost moves CAPEX only; inverter cost also moves the inverter-tied FOM and replacements. Recompute matches.
- **Re-centring.** A value outside its range scales the range by `value / midpoint`, so a relative ±30 % band stays ±30 % around the value. Tested; a value inside keeps the library range.
- **Gap: not tested (see [S1]).**
  - **M4:** leave the battery `p_nom_extendable=True` in `fixed_size_network`. All 21 unit and LP tests and the route file pass. On the real fixture it re-optimises the battery at the low demand-charge bound (0.7703 instead of 0.7720 MW; the bar drifts from 80,300 to 80,337).   - **M3:** the PV-only reference at a price bound keeps the battery (`drop_battery=False`). All 34 S6 tests pass. In effect the `bess_pv` price bars become 0 − 0 = 0, "break-even, not a flip", so the verdict stays `recommended`.

## Findings

**[B1] A run that did not judge every battery option gets a confident "Not recommended".**
- **Cause.** `verdict()` sees only the options in `ctx.options`, meaning those solved *and* unchanged since the run. An option that is pending (aborted run), failed, or whose fork changed is simply absent. `unjudged` only counts attributions with status `not_established`.
- **Reproduced.** I aborted a run after `none` and `bess_1h`, with a solver sizing `bess_1h` to zero. GET findings then returned:
  - `available: false` and `options_status: not_established`;
  - `pending_options: [bess_2h, bess_4h]`;
  - `verdict: {status: "ok", class: "not_recommended", sentence: "Not recommended: the model sized no battery above zero, or none has a positive battery NPV, at the centre."}`;
  - `completeness.battery_attribution: "ok"`.
- **Also.** The tornado POST is accepted on that run (202).
- **Why it matters.** The plan says `not_recommended` only "when … every battery option is judged". The S5 gate showed sector profiles size short batteries to zero, so this is the likely shape of an interrupted real run. A novice would act on it.

**[B2] The findings route crashes (500) on a custom tariff without a currency year.** See § 7. The verdict must take the currency year the case was built on (`InvestmentCase.currency_year`, from `proforma._one_currency_year`), not the tariff's optional field.

**[S1] The fixed-size property on the price rows, and the PV-only reference at the price bounds, have no test that fails.**
- M4 (battery left extendable) and M3 (reference keeps the battery) both pass the whole S6 suite.
- M4 changes a real bar on the fixture. M3 silently turns every `bess_pv` price bar into zero while keeping `recommended`.
- These are the two properties B5 and the S6 amendment exist for.

**[S2] Stale-tornado exclusion is correct but untested.** M5 (drop the option-hash comparison) survives.

**[S3] Case reads are refused during a tornado.** This is a regression of S5 behaviour, with a message about deleting. The findings route allows the same read.

**[S4] Ranking battery NPVs across different references.**
- The verdict names `bess_pv_2h` because its battery NPV (556k, *given 2.27 MW of PV*) beats `bess_2h` (372k, no PV).
- The sentence and the disclosure say so ("measured against the same PV of {{pv_p_nom_mw}} MW alone"), so it is honest. But it quietly recommends PV as well.
- A client who will not build PV should read 0.77 MW and 372k.
- Carry to S7: show the battery-only best beside a `bess_pv` verdict, plus the option's total NPV.

**[S5] Two different value-stream lists for one option id.**
- Findings streams for a `bess_pv` verdict are the battery's increment (sum 99k); the case route's streams are the full saving (365k).
- Only an honesty code distinguishes them.
- Carry to S7 and S8: a typed `value_streams_basis` (`baseline` | `pv_only_reference`), and a label on the waterfall.

**[N1] Tolerance edges.**
- The centre is judged strictly `> 0` while bounds get −1 EUR.
- The sentence says "positive … at every bound" when a bound sits in [−1, 0].
- Consider `>= NPV_TOL_EUR` at the centre, and "not negative" wording or a `break_even_at_bound` disclosure.

**[N2] The energy-price skip code.** On the flat seed, the energy-price row is skipped as `not_applicable` (the ledger's flag), not `energy_price_level_no_effect_single_band`. The plan's code appears only on a single-band tariff whose row has a value. Align the plan text or the code.

**[N3] Stale-tornado reason.** When the tornado is stale, the verdict's reason is `tornado_not_run` (the robustness note says `tornado_stale`).

**[N4] `bess_pv` with PV sized to zero.** The attribution uses the baseline as reference (correct), but the value streams stay `not_established` (`value_streams_need_the_pv_only_reference`), although the baseline bill is the reference.

**[N5] GET findings is heavy.** Every call re-reads every option network from disk and rebuilds every case and explanation. Cache on the recorded hashes when S8 polls it.

**[N6] Manifest.** `RunRefused` codes (`baseline_not_solved`, `campaign_budget_exhausted`, …) are not literal `error_kind`s, so the manifest does not list them. This is the pre-existing S4 pattern; S8 needs copy for `baseline_not_solved`.

**[N7] Crash leftovers.** A process crash mid-tornado leaves a `-var-` fork until the next tornado reaches that slug or the study is deleted. The `throwaway` marker is not yet read by anything; S9 should sweep it.

## Scrutiny point 1: is "`recommended` stands with an unjudged option" honest to a novice?

**The class is defensible, the claim behind it is overstated, and the page as served hides the caveat.**

- **What is true.** A judged battery with a positive NPV at the centre and at every bound is worth building whatever the other options turn out to be. So "a BESS pays here" is established, and blocking it would withhold a true answer.
- **What is not true.** The plan text and the docstring say `recommended` stands "whatever the others are". Under the plan's own rule, the verdict names the **best-at-centre** option and runs the tornado on it. An unjudged option with a larger centre NPV that flips at a bound would make the complete verdict **`marginal`**, naming a different size and duration. The class is therefore not monotone in the options judged. The "recommended MW and duration" (the plan's Goal) is exactly what an unjudged option can overturn.
- **What the client sees** (probe `NZ`, run aborted after `none` + `bess_1h` at 0.3 MW, tornado then run):
  - `verdict.status: ok`, `class: recommended`, `option_id: bess_1h`;
  - `reasons: [options_not_all_judged]`;
  - `disclosures`: only the two by-construction codes;
  - sentence: "Recommended: a battery of {{battery_p_nom_mw}} MW with {{battery_max_hours}} hours of storage has a positive battery NPV … at the centre and at every tornado bound."
  - `available: false` and `pending_options: [bess_2h, bess_4h]` are on the payload but outside the verdict.

  A novice reading the verdict card would buy a 1-hour battery the study never compared against 2 h or 4 h. `reasons` is a code list the S7 prose guard and the S8 card are not required to show. `disclosures` is the field that is shown beside the figures.
- **Required (BC-S6-v2-1):**
  - With any unjudged option, `recommended` uses a separate fixed template, digit-free with fact IDs. For example: "Of the battery options the study could judge, a battery of {{battery_p_nom_mw}} MW with {{battery_max_hours}} hours … is recommended; the others were not judged, so a better size or duration may exist."
  - `options_not_all_judged` goes into `disclosures`.
  - Correct the plan and docstring claim: the class can change to `marginal` once the missing option is judged.
  - Test: the `NZ` case asserts the template and the disclosure.
- **The alternative the owner may prefer.** `not_established` for every class while options are unjudged. It is simpler and conservative, but it withholds a true "yes, a battery pays" on a `bess_pv` reference failure.

  **Either choice passes this gate, provided it is visible in the sentence and the disclosures.**

## Scrutiny point 2: the full-suite failure and the release ordering

**The diagnosis is confirmed by the code.**
- At 791c536, `runner._worker` published the terminal status in two places inside `_finish`: `_set(status=…)` on the live record, and the `run` aux on disk.
- Only afterwards did its `finally` unmark the fork keys and call `_release_base`, which dropped and then unmarked.
- `wait_run` returns on "done" and the test asserts `_study_owned == ∅` at once, so any scheduling delay leaks a key. That is the reported shape: one `<org>:<uuid>` key when run in order.

**The fix.**
- `_finish` returns the terminal fields.
- The worker reads the fork keys before `db.close()`, unmarks them, calls `_release_base`, and only then `_set`s the terminal status.
- **The tornado worker has the same ordering.** `_save` (disk) runs first, then `db.close()`, then `_release_base`, then `_set` (live).

**Mutations.**
- Moving the tornado's `_set` back before the release turns `test_a_tornado_reports_done_only_after_it_has_released_everything` **red**.
- The implementer's REL mutation on the runner turns its twin red.

**One residual issue in the fix: BC-S6-v2-2.** `_release_base` now runs `unmark_study_owned(key)` (under `_registry_lock`) and then `drop(key)` (a bare `_contexts.pop`).

- **Why the flip was made.** The terminal record is already on disk. Once the base is dropped, a poll reads "done" from disk, and with the old drop→unmark order it could see a key still marked.
- **What the new order exposes.** Between the two statements the base is **resident and unexempt**. A concurrent registration by another session at the cap would count it: `register` → `_evict_if_over_cap` counts every non-study-owned context. The base itself is protected (its live record still says running), so the eviction picks **a user's least-recently-used context and writes it back to disk**. That is BC-S4-1's harm, in a two-statement window.
- **Neither order is pinned by a test.** Reverting to drop→unmark passes both release tests: the 1 s sleep sits before both statements.
- **The two orders compared:**
  - The old order's residue is harmless: a marked key that is not resident is never counted, and it only shows up in `_study_owned`.
  - The new order's residue is the harmful one.
- **Required:** make the pair atomic. Add a `PyPSAService` helper that, under `_registry_lock`, pops the context and discards the mark in one critical section, keeping `drop`'s unbind-if-active outside the lock. `_release_base` uses it. The per-fork paths in `runner._worker` and `ForkSolver` already drop before they unmark, which is the safe order; the helper may replace them too. Test: patch the helper or `_contexts` and assert that a key is never observed resident and unmarked, or pin the helper's use by source inspection. Either is acceptable for a two-line critical section.
