## (1) Library seed against the v0.14.0 extraction and the plan

- **[OK] Values, units, currency year and sources.** I checked every row against `docs/superpowers/notes/2026-09-28-mvp1-s2-seed-rows-technology-data-v0.14.0.csv`. The 12 sourced rows match exactly:

  - battery storage: 189.861 EUR/kWh, lifetime 25;
  - solar-utility: 482.4785 EUR/kW_e, FOM 2.4757 %/yr, lifetime 40;
  - solar-rooftop: 883.8138 EUR/kW_e, FOM 1.4234 %/yr, lifetime 40.

  Every row has currency year 2020, and the source strings are verbatim. `test_the_technology_rows_are_the_v0_14_0_transcription` pins this against the note file.
- **[OK] Source year and URL.** `source_year=2026` is the v0.14.0 release date in `data/versions.csv` (2026-02-13). `source_url` is the tagged raw `costs_2030.csv`.
- **[OK] Ranges.** Every range is ±30 % marked `assumed`, and efficiencies are clipped at 1.0; both are documented and tested. The discount-rate range is 0.049 to 0.091, assumed. This follows the S1 nit: `LedgerRange.source` stays `assumed | source`.
- **[OK] Derived round-trip efficiency.** The RTE row is 0.9216 = 0.96². The loader refuses a derived row that disagrees with its formula. `refresh_derived` makes a default derived row follow an edited input and leaves a row the user set alone. This is tested.
- **[OK] Not-used rows.** The two degradation rows have value `null` and `unavailable={value: not_used_in_mvp1}`. They carry no range and no flag, and are not key drivers (ADR-0001 null plus a flag).
- **[S1] The seed costs are 2030 projections, and nothing says so** (BC-S2-5). The plan pins `outputs/costs_2030.csv`, so 189.9 EUR/kWh and 213.9 EUR/kW are technology-data's costs projected for 2030, in 2020 EUR. The ledger shows them to a site owner deciding in 2026 as "Danish Energy Agency, 2026". Only the URL's filename gives the projection year away.

- **[N1] The derived row loses its formula.** It shows `source="derived"` in the ledger, CSV and report. The formula lives only in the CSV `note` column, which is not carried to the `LedgerRow`. Put "derived: battery_inverter_efficiency squared" in `source`.

## BC-S2-1: an illustrative tariff holds the badge at screening. **Closed.**

  A ledger with no tariff row says "names no tariff (re-seed it)". So a ledger stored at `d87f09f` stays at screening until re-seeded. I probed this.
- **Probed outcomes.**
  - Re-entering every key driver on either seed tariff, with an uploaded load, gives `screening` with exactly the tariff reason. This is tested through the function and through the route.
  - A custom tariff with source "Illustrative" and provenance `user` gives `screening`.
  - Provenance `imported` can reach `feasibility`.
  - Provenance `library` on a custom tariff is refused.
  - An intake that gives both a `tariff_id` and a `custom` tariff is refused.
- **A supplied tariff's own rows.** Its `demand_charge_price` and `energy_price_level` rows are seeded as `user` / `customised`. That is honest: those prices are the user's own. They have `changed_at = None`, so a re-seed re-derives them from the intake rather than keeping them.
  - I probed a switch from a custom tariff to the German seed. It re-seeds the demand charge to 9000, `library` / `default`.
  - **Removing that filter turns nothing red.** Without it, a re-seed after a tariff change would keep the old supplied tariff's price as `customised`. This is carried to S4, which rewrites the tariff intake.
- **[N] The `source == "illustrative"` clause is untested.** It works (probed) but has no test.

## BC-S2-2: edits to unused or inapplicable rows are refused, not stored. **Closed.**

- **Refusals.** `apply_user_row` refuses a null row flagged `not_used_in_mvp1`, `not_applicable` or `tariff_descriptor`. The message names the row and the reason, for example "the chosen tariff has no demand charge". This is tested through the function and through the route, with 422 and the sidecar unchanged.
- **Re-seed flagging.** A re-seed marks a kept user row `needs_attention` in two cases:
  - its fresh seed has become inapplicable or unused;
  - its unit changed.

  In each case it adds a `needs_attention:<key>:<reason>` honesty note. Maturity then names the row. The row cannot be edited until `reset`. `PUT` gains `reset: [keys]`, applied after the re-seed and before the edits.
- **Probed outcomes.**
  - A second custom tariff without a demand charge flags the user's 7700.
  - Switching back to a tariff that has one clears the flag, because the notes are rebuilt from the fresh seed.
  - Resetting a unit-changed row and then entering a value in the new unit works.
- **[S] Reset clearing the note is untested.** If `reset_rows` stopped dropping the note, a reset row could never be edited again, and nothing would go red. The one route test that covers reset edits a row that is still `not_applicable`. That refusal fires before the attention check, so it cannot see the note. Add a unit-changed reset-then-edit test.
- **[N] The reason lives in a string, not a typed field.** The needs-attention reason is only in the string protocol `needs_attention:<key>:<reason>` in `honesty_notes`. S8 must parse it; a typed field would be cleaner.

## BC-S2-3: values outside a row's physical domain are refused. **Closed.**

- **`LedgerDomain`.** It is written in interval notation and parsed back. Unbounded ends are normalised to open.
- **Where the domain comes from.**
  - Every technology row: a CSV `domain` column, which is required. The loader checks that the value and both range ends sit inside it.
  - `discount_rate`: `[0, 1)` from the YAML.
  - Demand charge: `[0, inf)`.
  - Energy price level: `(0, inf)`.
- **Enforcement.** `apply_user_row` refuses with the row, the value and the interval named. The `LedgerRow` validator refuses the same values as a backstop. The CSV round-trips `domain`.
- **Tests.** Twelve refusal cases, including `battery_inverter_efficiency = 96` and a storage lifetime of 0, plus four closed-bound acceptances. The route refuses with 422.
- **[N] `[0, 1)` excludes a negative real discount rate.** That is defensible for a site owner in MVP-1. State it if a user asks.

## BC-S2-4: one currency year, never mixed silently. **Closed.**

- **Edits.** An edit whose `currency_year` differs from the row's is refused, naming both years and "nothing is converted". Omitting the year means the row's year.
- **Study year.** `with_study_currency_year` adds `study_currency_year_<y>_differs_from_ledger_<years>_nothing_converted`. It is applied on GET and PUT, it is idempotent, and it is tested in both places. This was one of the two options BC-S2-4 allowed.
- **A supplied tariff in another year.** A custom tariff in 2026 EUR gives the ledger two currency years. The existing seed note names this (`tariff_currency_year_2026_differs_from_study_2020`), so it is not silent. **S5 must still refuse or convert this explicitly**; that was already carried.
- **[N] S8 must show the row's currency year beside the input.** Omitting the year silently takes the row's.

## The moved maturity tests

- **Why they moved.** The earlier feasibility, synthetic-load, one-default-row, measured and needs-attention tests now seed on `USER_TARIFF`, a supplied tariff. An illustrative tariff now holds screening by design, so this is required, not a weakening.
- **They still test their claims.** Each asserts its exact reasons list. For example, the synthetic-load test asserts that the load is the only reason, which also proves the user tariff adds no reason. The one-default-row test asserts exactly `discount_rate: default (library)`.
- **`test_measured_rows_count_as_established` is strengthened.** It now sets `status=default`, so only the measured clause can pass it. This closes N8.
- **`_customise_key_drivers` now skips null rows.** Editing them is refused now.
- **The `not_applicable` skip ([S7]) is tested twice.** It has its own test on a user tariff without a demand charge, and `illustrative[tou]` also depends on it.
