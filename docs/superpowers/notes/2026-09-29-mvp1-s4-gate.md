## 1. M0: the study creates its own base project

**[OK] Creation leaves every other project alone.** Checked in `routers/studies.py::_create_pack_study`.
- The chain is the one BC-5 names: `create_root` → `ensure_project_dir` → `PyPSAService.build_context()` → `_save_context(ctx, row.name, project_row=row, storage_dir=base_dir, persist_user_ts=False, db=db, user=user)`.

- `test_study_m0.py::test_creating_a_study_changes_no_existing_project_and_builds_its_own_base` hashes every project in the database, compares the request's slot, and compares `_user_ts`.
- Mutation `m1` saves the pack into the path project's directory. Exactly that test goes red.

**[OK] A record on an existing project never runs.** Checked in `runner._runnable`, using `DecisionStudy.pack_project`.
- A record attached to an existing project (`pack_project=None`) gets 409 `study_not_runnable`, and the directory hash is unchanged. Tested.
- A copied record (whose `pack_project` is the origin's uuid) gets 409, and its findings and report are marked stale on adoption through `routers/studies.py::_adopt`. Tested.
- Mutation `m5` drops the `pack_project` check. Only `test_a_copied_pack_record_is_stale_and_not_runnable` goes red.

**[B1] (blocker) A study run rewrites user projects on disk, and saves their unsaved edits.**

*Mechanism*
- `runner.base_context` calls `PyPSAService.register(base_key, ctx)` whenever the base is not resident, and M0 never makes it resident.
- For every fork, `solve_queue._run_solve_job` calls `PyPSAService.register(fork_key, ctx)`.
- Each registration runs `_evict_if_over_cap`. That picks the least-recently-used resident context that is neither active nor solving and writes it back to disk through `_save_evicted_ctx` → `_save_context`.
- `start_study_run` calls `base_context()` before the budget check. So a run that is then refused still registers the base, and can still evict.

*Reproduced* in `scratchpad/gate-s4/.../tests/test_gate_s4_eviction.py`, at the default `RESIDENT_CAP = 5` with nothing monkeypatched:
- A user has opened five projects this session; `ev-src` is the active one.
- The user creates a study and runs it with the fake solver.
- `ev-user1` and `ev-user2` change on disk: `metadata.json`, `network.nc` and `solver_config.json` are rewritten.
- In a variant, I put an unsaved in-memory edit (an added bus) on the resident, non-active `ev-user1`. After the run that bus is in `ev-user1/network.nc`.
- So clicking **Run** on a study persists a user's unsaved work into their project, without the user saving it.

*Why this is a blocker*
- It breaks the global constraint "No user project is ever mutated by a study".
- It breaks the definition of done: "no pre-existing project's directory hash changes at any point".
- It is the silent cross-project write that this gate exists to catch.
- Eviction write-back is not new behaviour: opening a sixth project does the same. What is new is a study triggering it. The implementer's open point 1 records it, and no test covers it.
- The S9 driver would miss it unless it runs at the cap.

*Required fix.* No registration made on a study's behalf may evict, and so write back, a context the study does not own. That covers:
- the base context;
- each fork;
- the S6 throw-away forks later.

The mechanism is the implementer's choice. Some options:
- study-owned registrations skip the cap check and let the registry go temporarily over the cap by a bounded amount;
- study-owned contexts are the only eligible victims when the registration is a study's;
- fork solves run outside the registry. This must not reintroduce the D-1 double-context defect, and it departs from the plan's "enqueue".

*Required test.* A run with the registry at `RESIDENT_CAP` must leave every pre-existing project's directory byte-identical. The test must include:
- a resident, non-active project holding an unsaved edit;
- the refused-run path, for example the budget refusal.
