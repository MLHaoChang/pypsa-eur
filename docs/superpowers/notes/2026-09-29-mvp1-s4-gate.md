## 1. M0: the study creates its own base project

**[OK] Creation leaves every other project alone.** Checked in `routers/studies.py::_create_pack_study`.
- The chain is the one BC-5 names: `create_root` → `ensure_project_dir` → `PyPSAService.build_context()` → `_save_context(ctx, row.name, project_row=row, storage_dir=base_dir, persist_user_ts=False, db=db, user=user)`.

- `test_study_m0.py::test_creating_a_study_changes_no_existing_project_and_builds_its_own_base` hashes every project in the database, compares the request's slot, and compares `_user_ts`.
- Mutation `m1` saves the pack into the path project's directory. Exactly that test goes red.

**[OK] A record on an existing project never runs.** Checked in `runner._runnable`, using `DecisionStudy.pack_project`.
- A record attached to an existing project (`pack_project=None`) gets 409 `study_not_runnable`, and the directory hash is unchanged. Tested.
- A copied record (whose `pack_project` is the origin's uuid) gets 409, and its findings and report are marked stale on adoption through `routers/studies.py::_adopt`. Tested.
- Mutation `m5` drops the `pack_project` check. Only `test_a_copied_pack_record_is_stale_and_not_runnable` goes red.

**[B1] (blocker) A study run rewrites user projects on disk, and saves their unsaved edits.**

*Mechanism*
- `runner.base_context` calls `PyPSAService.register(base_key, ctx)` whenever the base is not resident, and M0 never makes it resident.
- For every fork, `solve_queue._run_solve_job` calls `PyPSAService.register(fork_key, ctx)`.
- Each registration runs `_evict_if_over_cap`. That picks the least-recently-used resident context that is neither active nor solving and writes it back to disk through `_save_evicted_ctx` → `_save_context`.
- `start_study_run` calls `base_context()` before the budget check. So a run that is then refused still registers the base, and can still evict.

*Reproduced* in `scratchpad/gate-s4/.../tests/test_gate_s4_eviction.py`, at the default `RESIDENT_CAP = 5` with nothing monkeypatched:
- A user has opened five projects this session; `ev-src` is the active one.
- The user creates a study and runs it with the fake solver.
- `ev-user1` and `ev-user2` change on disk: `metadata.json`, `network.nc` and `solver_config.json` are rewritten.
- In a variant, I put an unsaved in-memory edit (an added bus) on the resident, non-active `ev-user1`. After the run that bus is in `ev-user1/network.nc`.
- So clicking **Run** on a study persists a user's unsaved work into their project, without the user saving it.

*Why this is a blocker*
- It breaks the global constraint "No user project is ever mutated by a study".
- It breaks the definition of done: "no pre-existing project's directory hash changes at any point".
- It is the silent cross-project write that this gate exists to catch.
- Eviction write-back is not new behaviour: opening a sixth project does the same. What is new is a study triggering it. The implementer's open point 1 records it, and no test covers it.
- The S9 driver would miss it unless it runs at the cap.

*Required fix.* No registration made on a study's behalf may evict, and so write back, a context the study does not own. That covers:
- the base context;
- each fork;
- the S6 throw-away forks later.

The mechanism is the implementer's choice. Some options:
- study-owned registrations skip the cap check and let the registry go temporarily over the cap by a bounded amount;
- study-owned contexts are the only eligible victims when the registration is a study's;
- fork solves run outside the registry. This must not reintroduce the D-1 double-context defect, and it departs from the plan's "enqueue".

*Required test.* A run with the registry at `RESIDENT_CAP` must leave every pre-existing project's directory byte-identical. The test must include:
- a resident, non-active project holding an unsaved edit;
- the refused-run path, for example the budget refusal.

**Terms used below**

- When that limit is exceeded, the least recently used project is saved to disk and unloaded. This is eviction.
- "Exempt" means a context the study owns (the `_study_owned` set). Exempt contexts do not count toward the limit and are never evicted.

## B1 / BC-S4-1: a study run must not evict, and so save, a user project

### The fix is in place

The fix, in `services/pypsa_service.py`:
- `_evict_if_over_cap` counts only contexts that are not in `_study_owned`, and never picks an exempt one to evict.
- `register` skips the limit check when it registers an exempt key.
- `mark_study_owned` and `unmark_study_owned` add and remove keys, under `_registry_lock`.

The runner, in `services/study/runner.py`:
- `start_study_run` runs the busy check (`_refuse_busy`) and the budget check on the already-loaded base context, if there is one, before it registers anything.
- A base the run loads itself is marked exempt before `base_context()` loads it.
- Each option fork is marked before it is queued, and unmarked after it has been read and dropped.
- The worker's `finally` unmarks every fork it created and calls `_release_base`.

M0, in `routers/studies.py::_create_pack_study`:
- Correction to my first gate: the first save's `rekey_context` did put the base into the registry, without eviction.
- It is now dropped after the save with `PyPSAService.drop(key)`.

### [S-v2-1] (binding) The base stays loaded after the run

**Cause.** `_release_base` runs in the worker thread's `finally`. It treats the base as in use if `PyPSAService.get_active_id() == key`. In the worker, `get_active_id()` returns the request context the worker bound, which is the base itself. So the check is always true and the base is never dropped. The mark is lifted, so after every full or aborted run the base counts as a sixth user context.

**Consequence**, shown with one ordinary project open after the run (`test_next_user_open_after_a_run`):
- Without a prior study, the open saves 1 user project to disk: `nx-user1`, the least recently used.
- After a study run, the same open saves **2**: `nx-user1` and `nx-user2`.
- So the study still causes one extra user project to be saved, one step later. That save carries any unsaved edit in that project.
- This is milder than B1: the save is triggered by the user's own action, and the base is study-created.
- It is still a study-caused write to a user project, so BC-S4-1 is not closed.

**Candidate fix, validated on copy `m10`.** Use `in_use = key in PyPSAService._session_active_keys()` only. On `m10`:
- after full, aborted and refused runs the base is not loaded and user contexts are at 5;
- the next open saves exactly one user project, the same as with no study.

**No test pins it.**
- **Mutation `m8`:** `_release_base` returns at once, so the base is never dropped and **never unmarked**, which makes it exempt forever and lets memory grow without bound. All 26 tests in `test_study_runner.py` and `test_study_m0.py` stay green.
- The implementer's cap test checks only that the resident set before the run is a subset of the set after it. It does not check that nothing is left behind.

### [S-v2-2] (binding, small) Two refusal paths never lift the mark

In `start_study_run`, two paths after the base is registered leave it marked, with no `_release_base`:
- `campaign.start` raises `CampaignError` → `RunRefused(422)`;
- `thread.start()` fails.

The budget is validated first, so both are hard to reach. But either one leaves the base exempt forever. Wrap everything from `base_context()` to the successful thread start in one `try/except` that calls `_release_base`.

### What the implementer's mutation claim shows

**Mutation `m9`** removes only the `register()` shortcut (`if project_id in cls._study_owned: return []`). All 26 tests stay green.
- The shortcut is redundant: the counting and victim-choice exclusions already stop the eviction.
- The implementer's mutation removed both, and it does turn `test_a_run_at_the_resident_cap_changes_no_user_project[full_run]` red.
- So the load-bearing guard is the exclusion inside `_evict_if_over_cap`. This is fine; I note it for whoever maintains that code.

### [N] Remaining edges (not binding)

- **The runner drops forks unconditionally.** After reading a fork it calls `PyPSAService.drop(key)` even if a session has that fork open. This is unchanged from the first commit and rare, since forks being solved are seldom opened.
- **A base the user opens mid-run.** After the run it is kept and unmarked. The limit is then exceeded by one until the next registration. The candidate fix above keeps it, which is correct, because it is the user's now. Also running `_evict_if_over_cap(protected_ids={key})` at unmark would make this exactly equivalent to the user opening it.
