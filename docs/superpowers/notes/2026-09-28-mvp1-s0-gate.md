## Blocking findings

### [B1] `test_chat_explain_investment.py` is red: the lift removed a name that a test still reads
- Checked: `pytest tests/test_economics_reading_notes.py tests/test_chat_explain_investment.py tests/test_golden_coverage.py tests/test_results_seam.py tests/test_fom_reconciliation.py tests/test_golden_economics.py tests/test_asset_economics_capital_costs.py tests/test_asset_results_export.py -k "not frontend_payload_fixture"` gave **4 failed, 112 passed**.
- All four failures are `test_binding_constraint_classification[wind1-at_upper_bound | gas1-interior | nuclear1-not_built | diesel-not_extendable]`, each with `AttributeError: module 'services.chat_tools' has no attribute '_BINDING_EXPLANATIONS'` (`tests/test_chat_explain_investment.py:95`: `assert out["sizing"]["explanation"] == T._BINDING_EXPLANATIONS[expected]`).
- This answers brief question 2 ("does anything else import the removed names"). No production module imports `_finite`, `_is_at` or `_BINDING_EXPLANATIONS` from `chat_tools`, but this test does. The implementer's evidence says `test_chat_explain_investment.py` passes. It does not.
- Fix: point the assertion at the one home, `from services.results.sizing import BINDING_EXPLANATIONS` (preferred: it keeps the assertion's strength and pins the new home). Re-exporting a `_BINDING_EXPLANATIONS` alias from `chat_tools` also works. Then re-run the file and the full backend suite and record the counts.

### [B2] The "solved" rule in `is_interior_optimum` is unsound, and Asset Detail shows a false caveat
- The docstring claims "an `<nom>_opt` column exists only after a solve". That is false in PyPSA 1.1.2: `p_nom_opt` / `e_nom_opt` are static attributes with default 0.0 and are always present. Checked: `'p_nom_opt' in pypsa.Network().add(Generator…).generators.columns` gives `True`, value `[0.0]`.
- Case 1, unsolved network: an extendable Generator with `p_nom_min=5`, `p_nom_max=100` and no solve has dispatch state `none`, yet `classify_sizing(..., solved=True)` returns `interior` (opt 0 lies on neither bound) and `build_response(..., category="summary")["reading_notes"]` returns the zero-profit note. Reproduced.
- Case 2, stale `p_nom_opt` (the realistic case): solve a one-bus network (gas built interior at 80 MW, dispatch `fresh`), then `clear_dispatch(n)`. The `main.py` middleware does exactly this after *every* successful `/api/network/*` mutation. The state is now `none` and `p_nom_opt` stays at 80. The Asset Detail summary still returns the note. Reproduced. `explain_investment` on the same network reports `not_solved` and **no** zero-profit note, so the two surfaces disagree. That disagreement is the one this phase exists to prevent.
- Does the difference matter?
  - **`/results/asset_economics`: no, in practice.** `routers/results.py::get_asset_economics` refuses with `_not_solved()` unless `_dispatch_ready(n)` (is_solved and `dispatch_status == "fresh"`), so `compute_asset_economics` only sees fresh networks. It is still the wrong rule inside a pure, lifted function that has other callers (tests, and the S5 and S6 reuse the plan names).
  - **Asset Detail: yes.** `routers/asset_results.py::get_asset_results` has no freshness gate. `params` and `identity` render on unsolved networks by design, so the summary request is served on unsolved and edited-after-solve networks.
- Honest fix: decide "solved" the way `explain_investment` does. `solved = dispatch_status_detail(n)["state"] == "fresh"`, computed once in `interior_optimum_notes` (or passed in) and handed to `classify_sizing(row, nom_col, solved=solved)`. Remove the column-existence rule and correct the docstring.
- Add two surface tests: (a) extendable asset with `p_nom_min > 0` on an unsolved network gives `reading_notes == []`; (b) solved interior asset, then `clear_dispatch`, gives `[]`.
- Residual shared by all three surfaces and not introduced here: a "fresh" network whose bounds were edited outside `/api/network/*` would classify old `p_nom_opt` against new bounds. The middleware clears dispatch on network mutations, so no action is needed for S0.
