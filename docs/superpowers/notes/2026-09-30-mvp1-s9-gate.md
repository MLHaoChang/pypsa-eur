## 2. The driver

- **The reconciliation is real, not a tautology.**
  - CAPEX 541,137.46 = 680,000 EUR/MW × 0.79579 MW. I checked 680,000 by hand: 450 EUR/kWh × 1 h × 1000 + 230 EUR/kW × 1000. It is not only `battery_upfront_eur_per_mw` checked against itself.
  - FOM 15,443.31 = 617.7323 × 25. That equals `asset_economics.fom_cost_eur` from the run record, and also `cost_breakdown`'s StorageUnit FOM, recomputed from the fork's `network.nc` with the fork's solver config (617.73229).
  - The `upfront_cost_series` gap is printed (+22.3 %) and asserted, and it is disclosed in the report (`battery_upfront_from_ledger_not_back_calculated`).
  - An independent check of the report: the market revenue at duals, 57,407 EUR/yr / 0.7958 MW = 72,137 EUR/MW/yr. My two annuities plus FOM give 38,615 + 32,747 + 776 = 72,138. So the zero-profit sentence is true at this interior optimum.
- **The `marginal` verdict hangs on a thin margin ([S2]).** It hinges on one bound. I ran the same driver with only the storage quote changed:
  - at 420 EUR/kWh the low-bound NPV is **+2,240**, the verdict becomes `recommended`, and the driver **fails** (56/57);
  - at 480 it is −45,507, and the driver passes.

  The size is 0.7958 MW in all three runs, because the spike sets it. So the result is deterministic on pinned data, but it sits about 6 % above the edge of the `marginal` window (roughly 423 to 785 EUR/kWh). A +3 % change to the seed's demand charge, or any library retune of that size, turns the QA gate red with no product change.
- **Runtime.**
  - My run: 104.6 s in-driver. The run took 60.8 s (4 LPs), the tornado 20.3 s (2 LPs), plus the aborted run.
  - The implementer measured 109 s under load.
- **Cleanup.**
  - The driver deletes both studies. The cascade removes 4 forks and 1 fork, both records are 404, no `-var-` row or directory is left, nothing stays marked study-owned, and neither base stays loaded.
  - It leaves the harness's `/tmp/pypsa-gui-test-projects-*` root behind: the bases and user projects, about 1 MB. That is pre-existing harness behaviour for every driver (605 such directories in `/tmp`), not S9's ([N1]).
- **The assertions are real.** Every check compares against state read independently: DB rows, directory hashes, `PyPSAService._contexts` and `_study_owned`, the fork's `network.nc`, and the parsed DOCX and XLSX. None is only a status code, except the HTML chart count.

## 3. The startup sweep (`forks.sweep_leftover_forks`)

- **What the rule deletes.** The sweep deletes only what `is_study_owned` proves: the metadata names the study and the base, **and** the DB row's parent is that base. That covers throw-away variants (`throwaway`, `owner_variant_id` and `-var-` all required) and option forks whose record file is absent. It deletes through `delete_fork`, which re-verifies ownership and refuses an active job or a child project.
- **The probes** (`s9gate/tree/.../tests/test_zz_gate_s9_probes.py`, 6/6 behaved as required):
  - **P1 (names).**
    - User scenarios of the study base named `pn-var-x`, `pn-opt-x` and `pn-opt-bess_9h` are never swept.
    - A user branch of fork `bess_2h` **inherits the fork's owner keys**, because `_create_scenario_db` copies `metadata.json`. It is still not swept (its parent is the fork), and the fork itself is kept (`fork_has_children`).
    - With the record present, nothing is swept. With the record absent, only the other 4 forks go.
  - **P2 (adopted copy).**
    - A scenario of the base carries the record.
    - An adopted copy in an unrelated project (PATCHed) keeps nothing alive for the origin. When the origin's record goes, the origin's 5 forks are swept; both copies stay and still read 200.
  - **P3 (auth mode, two orgs, identical names).**
    - Removing org 1's record sweeps org 1's 5 forks only.
    - An org 2 fork forged to name org 1's base uuid is not swept, because its parent does not match.
  - **P4 (missing parent).**
    - Base directory moved away: nothing swept.
    - Base row deleted (SQLite leaves orphan children): nothing swept.
  - **P5 (ordering with `reconcile_on_boot`).**
    - Setup: a persisted *queued* job on a leftover variant, then boot.
    - The sweep deletes the fork, then reconcile restores the job, which fails with `FileNotFoundError … network.nc` (`queue_error`).
    - The directory is **not** recreated and no context stays resident.
    - The order (sweep, then reconcile) is right: the reverse would make the fork undeletable (`fork_solving`), and M9 pins it.
  - **P6 (Save-As).**
    - An ordinary user save gains no owner keys and changes no metadata key.
    - Fork `bess_1h` force-saved over fork `bess_2h`: `bess_2h` drops its keys, and the next re-run fails typed with `fork_name_taken`, so it fails closed.
- **Two overlapping local launches.** The second instance's lifespan runs before uvicorn binds, so its sweep can delete the first instance's live `-var-` fork.
  - Outcome: that tornado row fails, and there may be an orphan directory.
  - Only variants are at risk: a live run's option forks have their record.
  - It is the same shape as the pre-existing `reconcile_on_boot` race, which marks the first instance's running jobs `interrupted`.
  - Acceptable until the single-instance guard lands, and the note records it.
- **A path not covered.** `record.exists()` on Python 3.12 raises for EACCES, which the per-fork `except` catches, so a non-traversable `studies/` directory is kept, not treated as absent. I could not probe this as root.

## 5. The wait deadline

**It is acceptable.** 4 h (queue time included) + 60 s grace, then `SolveDeadlineExceeded` → the run is `failed` with `solve_deadline_exceeded: … (option X)`, and the pending options are named. The verdict then reads the run as unjudged (BC-S6-1).
- **A stuck fork is left.** `delete_fork` refuses while the queue holds the job, and the fork is recorded in `fork_removal_refused`. That is correct, because deleting under a live solver is worse. The per-option release still drops its context, so nothing stays exempt from the cap.
- **[N2] The tornado keeps going after a deadline.** `VariantFailed` fails the row and the next re-dispatch row is enqueued behind the same stuck job. The worker can then be pinned for about (re-dispatch rows) × 4 h. It is finite and typed, but the runner stops at the first deadline and the tornado should too.
