**[N2] `intake_incomplete` in the preview is a change, not a dead end.**
- **Before:** `BillCalculator` priced the load and tariff with no site or connection, so the Tariff step showed a bill for a study whose intake was incomplete. The guided intake asks for the site first, but a study can be created incomplete (API, the assistant).

- So no stored fork reaches `_gs_bill_of` or the pro forma. See S2 for the tornado's own solves.

### 2. Stale path (claim 2)

**[N4] An old study gets a clear re-run offer, and the re-run clears it.**
- **Probe P1** (fake solver, `compiled_hash` and `option_compiled_hashes` stripped, as for a WP7-era run):
  - findings, case, tornado POST and report POST all answer 409 `engine_inputs_changed_since_run`, with "This study was run by an earlier version of the app … Run the study again";
  - the stored report reads stale with `["run_by_an_earlier_version"]`;
  - **a re-run is accepted (202)** and finishes `done`;
  - after the re-run: findings 200, the case 200, the old report reads stale (`run_by_an_earlier_version` plus `fork_changed_since_findings:*`, because the re-run makes new fork uuids);
  - **re-assembling gives `stale: false`, `[]`**.
- **No zombie tornado.** An old tornado record cannot read as fresh after the re-run: its `option_network_hashes` are keyed by the old fork uuids, which `_create_fork` replaces.
- **What the user sees:**
  - the `Refusal` banner shows ERROR_COPY (both causes named, rerun) **and** the backend message;
  - every page that needs findings shows it;
  - the report page's "Assemble again" ends in the same 409 with "Run the study again from the Run page".

**[N5] No false positive in normal use.** Probe P2, on a normal fake run:
- **Expert open and save:** `GET /api/projects/<fork>` then `POST /api/projects/<fork>` leaves `solver_config.json` byte-identical and the digest equal. The case and findings stay 200.
- **Settings-form echo:** `GET /api/simulation/solver_config`, `PUT` the same body (which re-binds `commercial`), then save. The digest is still equal, and the case and findings stay 200.
- **Digest stability:** canonical JSON (`sort_keys`, fixed separators) of only `commercial` and `finance`, read back from the file the queue saved after the solve. The run and its readers therefore hash the same bytes. No netCDF is involved.
- **Pinned:** G3 (the run records a digest that differs from the saved blocks) turns 8 red across `test_study_compiled_hash` and `test_study_case_routes`, so "a normal run is not stale" is pinned.

**[N6] `compiled_hash` is a stamp; the guard is the per-fork digest.**
- No reader recomputes `compiled_hash`. `compiled_matches` only requires it to be present and then compares `option_compiled_hashes[fork_uuid]` with the fork's current digest.
- That is sufficient, because the digest covers both engine inputs. But the plan's "compiled_hash = …" reads as a check. Say "stamp" in the plan (Y4).

**[N7] Edge copy and wording.**
- **The re-run line.** `ReportStep.staleNeedsRun` tests `/changed|copied/`, so the explicit "Run the study again, then assemble the report." line does not show for `run_by_an_earlier_version`. The reason's own HELP sentence does say it, so the user is not stranded. Add `earlier` to the test in part B.
- **The not-engine-ready message.** A fork that is not `engine_ready` is always told "run by an earlier version". A post-WP8 fork whose solve failed to commit the PoC record would loop on that advice. This is not reachable in my probes. Note it for WP10.
- **A stricter rule than before.** An edited engine input refuses the whole findings, where an edited network only drops its fork. This is the plan's stated decision, and the message names the option.
