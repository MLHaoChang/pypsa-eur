# DeepSeek Harness: what to adopt in the chat harness, and what not to

Date: 2026-10-06
Scope: `pypsa-gui/backend/harness/` as of this branch (the contract in
`harness/README.md`; owner decisions in `.scratch/harness/spec.md` §8),
compared with the public docs of `deepseek-ai/deepseek-harness` on GitHub
(`master`, read today).
Method: every claim about DeepSeek Harness (DSH below) is checked against
the repository's own docs and linked to the page it comes from. Every claim
about our side is checked against the cited module. This is an assessment,
not a plan; §6 lists what needs the owner's answer.

---

## 0. Verdict

**Do not integrate the runtime. Adopt five of its designs, in our own
Python, in this order: the append-only session log with fork lineage; spill
storage for oversized tool results; a goal object with a round budget; the
richer question shape; and, when Q8 reopens, the MCP client's naming and
feature-subset rules.** DSH is a Node product in developer preview with a
TypeScript-typed gateway, so the value for us is in the patterns, which are
unusually well written down, not in the code.

Our seam vocabulary (`LLMRequest`/`LLMEvent`, closed `FRAMES`, tiers as
data, Markdown skills and workflows, per-turn user content) maps onto theirs
almost one to one. The gaps are persistence (we log turns, they log
everything the model sees), large results (we truncate, they spill), and
multi-turn autonomy (we have none, they have a budgeted goal).

---

## 1. What DeepSeek Harness is

DSH is an open-source agent harness from DeepSeek. The runtime is Node.js
and the entry point is `npx @deepseek-ai/dsh web`; the license is MIT; the
README states it is in developer preview and that "THERE WILL BE
COMPATIBILITY-BREAKING CHANGES"
([README](https://github.com/deepseek-ai/deepseek-harness/blob/master/README.md)).
Architecturally it is a Cordis plugin tree in which "every part of the
product is a plugin, including the model adapter, the tool registry, the
session log, and the agent loop itself"; five profiles ship (`web`,
`headless`, `sdk`, `sdk-minimal`, `acp`); a **step** is one model request
plus its tool calls and a **turn** is zero or more steps; and the rule that
governs the whole design is "model-visible means logged", so every model
request is reconstructable from the session log
([architecture.md](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.md)).
Capabilities such as `ctx.llm`, `ctx.approval`, `ctx.userQuestions`,
`ctx.sessionPersistence`, `ctx.spillStore`, `ctx.compaction` and
`ctx.workflowEngine` are "swappable capability seams"
([capability-seams.md](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/capability-seams.md)).
The subsystem index lists 63 pages, from `boot` to `product-telemetry`
([subsystems/README.md](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/README.md)).

## 2. Why not integrate the runtime itself

- **Process model.** DSH is a Node process; our 196 tools are in-process
  Python functions over one `ProjectContext` and one mutable PyPSA network
  (`harness/catalogue.py`, `harness/README.md` contract 2). DSH would be a
  sidecar with every tool call crossing a second protocol.
- **The API is TypeScript-shaped.** Remote calls are `POST /api/<namespace>/<method>`
  with an `args` object, streams ride a multiplexed `/api/remote.mux`
  WebSocket, and the contracts are generated by Typert from the host's
  TypeScript program
  ([api-gateway.md](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/api-gateway.md)).
  A Python SDK exists, but it "packages the normal `dsh` CLI" in a
  platform-specific runtime wheel and "launches `dsh --profile sdk`"
  ([architecture.md](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.md)),
  so it does not remove the Node dependency.
- **Our UI contract is ours.** The panel switches on the 19 frames in
  `harness/events.py`, guarded by a tripwire test. DSH's client is its own
  web application (`web-client`, `client-modules`, `slots` in the subsystem
  index). We would be translating their stream into our frames, which is
  the job our loop already does for providers.
- **Packaging.** The desktop build is a PyInstaller bundle with an explicit
  allowlist (see the 2026-09-28 assessment, §0). A Node runtime is not in it.
- **Status.** Developer preview with announced breaking changes
  ([README](https://github.com/deepseek-ai/deepseek-harness/blob/master/README.md)).

## 4. Worth adopting, ranked

### 4.1 An event log, not a turn log

DSH persists every event the model saw, so a session can be resumed after a
crash (the reader appends the missing tool errors and a synthetic
`turn/end { reason: { kind: 'interrupted' } }`) and forked (`parentSession`,
`inheritedEventCount`)
([persistence.md](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/persistence.md)).
We persist completed turns plus one pending-turn record, and the WAL is
"one pending slot per PROJECT, not per session" (`harness/history.py`).

Change: keep `chat.jsonl` as the user-facing transcript (Q7), and add a
per-session event log beside it: `turn/start`, `request` (the exact
`LLMRequest`, system blocks included), each `LLMEvent`, `tool/call`,
`tool/result`, `confirm/asked`, `confirm/decided`, `turn/end`. Write it from
the same places the frames are yielded, so "model-visible means logged"
holds by construction.

Enables: replaying one recorded request against every profile for parity
(instead of re-driving `run_chat_smoke.py`); an audit trail pairing each
confirmation with what was approved; "branch this chat from turn N" to
compare providers on the same prefix.

### 4.2 Spill instead of truncate

DSH keeps an oversized result in a per-session store and gives the model
"ordered head/tail content and a spill address" with a `retrievalHint`
([spill.md](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/spill.md)).
We cut at a character budget and append a truncation notice
(`harness/results.py`). A full `get_timeseries` or a solver log is exactly
the kind of result that is too large to inline and too useful to lose.

Change: a `harness/spill.py` that writes under the project's chat directory,
returns `{locator, bytes, hint}`, and a read-tier `read_spill(locator,
offset, length)` tool. The policy stays in `results.py`.

Enables: the model can page through a large result rather than guess from
its head; the per-turn result budget stops being a hard wall.

### 4.3 A goal with a round budget

DSH's goal has four phases, a `maxGoalRounds` cap, and every continuation
round attributed with a sequential number, so a long task cannot run
unbounded and a `blocked` goal says why
([goal.md](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/goal.md)).
Our workflows are user-walked steps; the only autonomy bounds are per-turn
tool and token caps (`harness/budget.py`).

Change: a session-level goal record `{objective, phase, rounds, max_rounds,
blocked_reason}` set by a `set_goal` tool; the loop admits one continuation
round per checkpoint and refuses past the cap. A workflow step can be the
objective.

Enables: "run the study and tell me when the frontier is done" without a
prompt per step, with a visible budget, and with the confirmation card
unchanged on every write (contract 6).

### 4.4 Richer questions

DSH questions carry `header`, `detail`, `multiSelect`, `custom` free text
and a presentation intent, and a late answer becomes an ordinary user
message
([user-questions.md](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/user-questions.md)).
Our `choice_request` carries `title`, `question`, `options`,
`allow_free_text`. The late-reply rule is already ours (Q4: the pick is the
next user message), so the change is only the shape: add `multi_select`,
`detail`, and an `intent` enum the panel may ignore.

### 4.5 Skills discovery roots

DSH merges ranked roots with "Lower ranks win duplicate skill names"
([skills.md](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/skills.md)).
We read from the package only, because skill bodies are instructions
(spec D12, `harness/skills/registry.py`). Adopt only the narrow form: an
operator-configured second root (never a project directory or an upload)
with the same precedence rule, plus `user_invocable` for skills that are
commands but not model-loadable.

### 4.6 MCP client, when Q8 reopens

Two rules to copy: prefix public tool names with the server name, and
declare the unsupported subset up front (prompts, elicitation, tasks,
resource subscriptions)
([mcp.md](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/mcp.md)).
Discovered tools must land in `catalogue.TOOLS` with a tier, since the
confirmation gate reads the tier from there.

## 5. Not worth adopting

- **Agent teams and the JS workflow engine.** Teammates with `fresh` or
  `fork` context, a mailbox and a task DAG
  ([agent-team.md](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/agent-team.md)),
  and scripts that call `agent()` in `parallel()`
  ([workflow.md](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/workflow.md)),
  assume agents that can work in isolation. Our tools act on one in-memory
  network and one solver per project; two agents editing it would race, and
  the parallel-destructive refusal exists to prevent exactly that
  (`harness/confirm.py`). Keep Markdown workflows.
- **The Claude Code mods bridge.** It is a compatibility layer for Claude
  Code plugins in which a mod runs "with the process's full authority" and
  "No sandbox is applied to mods"
  ([claude-code-mods.md](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/claude-code-mods.md)).
  We have no plugin surface and contract 4 forbids instructions from
  outside the package.
- **The DeepSeek wire extensions.** `dsh_session_log` is "enabled by
  default" and "may expose the Session working directory, system-prompt
  snapshots, user and Assistant content, ... tool arguments and results" to
  the resolved `baseURL`
  ([deepseek-llm-api-wire-extensions.md](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/deepseek-llm-api-wire-extensions.md)).
  Our provider seam forbids anything outside `LLMRequest` on the wire
  (`harness/protocol.py`), and a transcript of a client's network must not
  leave the machine as side data. If we ever add a DeepSeek profile, it goes
  through `openai_compat` with no extension fields.

## 6. Open questions for the owner

1. Does the event log (4.1) replace the pending-turn WAL, or sit beside it
   until the resume path is proven on both wires?
2. Spill location: inside the project directory (travels with save/rename
   lineage) or a per-user cache (never exported)?
3. Is a goal (4.3) allowed in Guided mode, where every write already cards?
4. For 4.4, should the panel render multi-select now, or accept the field
   and render a single pick until there is a workflow that needs it?
5. Does a second skills root (4.5) reopen D12, or is `user_invocable` alone
   enough for now?
6. Does Q8 (MCP) reopen in this branch's lifetime, or after the loop split?
