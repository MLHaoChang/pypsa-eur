# gridspine increment 6 — the frozen app ships the planning pipeline, and PowerFactory read-back (spec stage 6)

**Status:** LANDED on `gridspine-inc2`, 2026-09-09, after increment 5 (e304e5df): A in one commit, B in three (gridspine, backend, frontend). Two asks from the owner: close the planning pipeline's last gap — the desktop app answered 503 for it — and build the read-back the study view has carried a placeholder for since increment 4.

## A — the frozen app ships the planning pipeline

**What was wrong.** D5 made `gridspine` an editable install in every pixi environment, but the frozen desktop app is built from a pip-wheel venv (`gui-requirements.txt`, D14) that carried neither the package nor its engines, so `gridspine_service`'s guarded import failed and every planning action answered 503.

**Facts measured before designing (2026-09-09).** pixi's editable install is a setuptools import-finder hook (`__editable__.gridspine-0.4.0.pth` runs `finder.install()`), which PyInstaller's analysis cannot follow — so installing gridspine into the build venv would buy nothing. PyPI has `pandapower 3.1.2` as a pure-Python wheel and `lightsim2grid 0.10.1` with cp313 wheels for macOS arm64 (macosx_11_0), manylinux and Windows. pandapower reads its IEEE cases `__file__`-relative (`networks/_get_cases_path`); gridspine reads its unit library `__file__`-relative (`templates/unit_params.py`). A Linux pip venv built from `gui-requirements.txt` plus the two engines (python 3.13, 1.1 GB) ran a full 24 h study with screening, and a `sys.modules` diff across that run found ONE lazily loaded third-party module not already in the spec's hidden imports: `cloudpickle` (dask's). pandapower and lightsim2grid are imported at module scope by gridspine, so static analysis sees them.

**The decision.** gridspine is frozen FROM SOURCE through the spec's `pathex` (repo root second, behind the backend), its YAML library and pandapower's JSON cases are collected as `datas`, both packages are written out as real directories (`module_collection_mode pyz+py`, the same fix pypsa needed), the engines are pinned in `gui-requirements.txt`, and `cloudpickle` plus the four gridspine entry modules are hidden imports (the entry modules because the backend imports them inside a try/except — analysable today, spelled out so a future guard change cannot drop the package silently). The guard in `gridspine_service` STAYS as defence in depth. `build-macos.sh` gains a step that builds the bundled project templates with the repo root on the path, so a fresh build ships all four templates including the IEEE 39-bus one from increment 5 (the `.nc` files are gitignored; without this step a fresh checkout shipped none). `smoke/check_bundle.py` expects `case39_units.yaml` and `case39.json`.

**Evidence, Linux.** `pyinstaller pypsa-gui.spec` in the Linux venv completed (674 MB onedir); the frozen tree holds `gridspine/` with its YAML, pandapower's 30 case JSONs, and lightsim2grid's compiled module; `check_bundle.py` on that tree reports exactly one problem — the missing macOS `Info.plist` a Linux build cannot have — and no forbidden file. A frozen PROBE built with the same collection settings, importing what the backend imports, then **found a real defect the tree inspection could not**: `pn.case39()` failed looking for its JSON under `pandapower/__init__/networks/…`. Cause, traced over three probe builds: pandapower's `networks/*.py` do `from pandapower.__init__ import pp_dir`; a normal interpreter re-executes `__init__.py` under that name with the same `__file__`, but PyInstaller freezes `pandapower.__init__` as a package-shaped module of its own (`pandapower/__init__/__init__.py`), whose `pp_dir` is one level too deep. Fix: exclude the name, so the frozen importer falls through to the on-disk source `pyz+py` writes — the normal behaviour. With that, the probe loads the templates and case39 and runs a 24 h study with screening inside the bundle: `completed`, three selected hours, three bundles. The exclusion is held by a packaging test.

**Not done, on record.** The macOS `.app` build and a run of the study flow in it. Everything above is Linux evidence of the same spec; the two platform-specific risks that remain are the lightsim2grid wheel loading under the hardened runtime and codesign of its binary, both of which only a signed macOS build shows.

## B — PowerFactory read-back (spec stage 6)

**What the spec says.** "result read-back is a file upload in the same study view"; `readback/` is "PowerFactory/PSS-E result files → report figures"; the phase-1 gate is <1 % |Vm| and 0.5° per bus, and since increment 2 also 1 % P (floored at 1 MW) and 5 Mvar Q per branch, with the export format fixed by `tests/gridspine/fixtures/powerfactory/README.md`. `readback/pf_compare.py` already holds the per-element comparisons against an `LFResult`; what was missing is a stage: something that compares an upload against a BUNDLE and records the outcome as files.

**Design.**

1. `readback/results.py` (pandas only — the cage keeps `readback/` free of pandapower): the bundle's own `lf_bus.csv` / `lf_branch_flow.csv` are the reference, loaded into a `BundleLF` that duck-types `LFResult`, so nothing is re-solved and the comparison is against exactly what was handed over. `read_back(bundle_dir, bus_csv, branch_csv=None)` runs `compare_lf` and, when a branch export is given, `compare_branch_flows`; only after both succeed does it write — the uploads byte-for-byte (`pf_bus.csv`, `pf_branches.csv`), the per-element tables (`readback_bus.csv`, `readback_branches.csv`) and `readback.json` (per side: n, n_ok, max errors, the worst element, pass; overall pass = AND of what was judged; branches `None` when not uploaded, never assumed). A bad export leaves an earlier read-back intact. `readback_figure(bundle_dir, name)` returns one comparison as DATA (`vm`, `va`, `branch_p`, `branch_q`: both sides per element, the error, the verdict, the tolerance) — the spec's "report figures" as something the UI draws and the copilot reads.
2. `drivers/readback.py`: `ingest_powerfactory_results(run_dir, hour, bus_csv, branch_csv)`, `readback_status(run_dir)`, `result_figure(run_dir, hour, name)` — the backend imports only `gridspine.drivers`. `stage_status` gains `readback: {hour: {pass, bus: {n, n_ok}, branches: {n, n_ok} | None}}`.
3. Backend: `upload_readback(project, hour, bus_bytes, branch_bytes, names)` stores the uploads under the study's `gridspine/uploads/h<hour>/` and calls the driver; `get_readback(project)`; `fetch_result_figure(project, name, hour)` becomes real. Router: `POST /{name}/readback/{hour}` (multipart, `read_capped`), `GET /{name}/readback`, `GET /{name}/figures/{hour}/{figure}`. Chat: `gridspine_get_readback` (read), `gridspine_fetch_result_figure` (read); the upload stays a UI action — a file.
4. Frontend: the read-back section replaces the placeholder — per selected hour with a bundle, a bus CSV (required) and a branch CSV (optional), the summary with a pass/fail tag and the worst element, and the per-element table on demand.
