# gridspine increment 5 — D5 (packaging) and D3 (a project's own network as the dispatch source)

**Status:** LANDED on `gridspine-inc2`, 2026-09-08/09, after the increment-4 follow-ups (14d1cea6): D5 in one commit, D3 in three (gridspine, backend, frontend). Landing notes at the end of each section. Two decisions the increment-4 plan left open or scoped out, taken here because they are what stands between the four-increment pipeline and a user who solves a capacity-expansion project in the GUI and studies its dispatch.

## D5 — how the backend imports gridspine: TAKEN, an editable distribution

**What was wrong.** This repository packaged nothing. `pixi run gridspine-tests` worked because it runs from the root; the backend runs from `pypsa-gui/backend`, so `services/gridspine_service.py` inserted the repo root into `sys.path` at import time — explicit, one place, and a stopgap the frozen desktop build could not reproduce.

**The decision.** A root `pyproject.toml` declaring the `gridspine` distribution and only that (`[tool.setuptools.packages.find] include = ["gridspine", "gridspine.*"]`; PyPSA-Eur's `scripts/`, `rules/`, `config/` are a workflow, not a package). pixi installs it EDITABLE into every environment: `[pypi-dependencies] gridspine = { path = ".", editable = true }`. Editable is load-bearing: the source tree is what runs and what `gridspine-tests` tests; a wheel copied into site-packages would import fine and test stale code. **No runtime dependencies are declared**: every engine (pypsa, pandapower, lightsim2grid, highspy, pandas, numpy, pyyaml) is pinned in `pixi.toml`, the one place versions are decided; a second list would drift and make uv resolve PyPI copies of conda packages. `package-data` carries `templates/data/*.yaml` so a non-editable install would still find the unit library.

**Lock outcome, measured:** `pixi lock` added 19 lines to `pixi.lock` and removed none — the editable entry (`pypi: ./`) in each of the four environments × four platforms plus one package record. No existing package moved: as with the lightsim2grid pin, pixi solved only the new subtree. `pixi install -e test` then `import gridspine` from `/tmp` resolves to `<repo>/gridspine/__init__.py` at version 0.4.0 through `__editable__.gridspine-0.4.0.pth`.

**Sequencing against PR #6.** #6 is still open and touches `pixi.toml` (and the workflow, and `tests/conftest.py`), so this lands a small conflict for whoever merges second: eight comment-plus-one lines under `[pypi-dependencies]`. The lock will need a re-lock at that merge if #6 re-locked too. Taken now anyway because the user asked for D5 and the stopgap was the last piece of the backend that only worked from a checkout.

**What D5 does NOT do — the desktop bundle.** The frozen app is built from the pip venv `gui-requirements.txt` (generated, never typed) and the PyInstaller spec whose `hiddenimports` are measured. Neither carries gridspine or its engines, so the desktop app still answers 503 "planning → dynamics not available in this build", exactly as `OPTIONAL_AT_RUNTIME` records. Bundling means adding `-e .`, `pandapower==3.1.2`, `lightsim2grid==0.10.1` to the venv, `ROOT` to `pathex`, measuring hidden imports, and running `smoke/check_bundle.py` on a macOS build — none of which this session can verify, so it stays a build decision for the owner with those exact steps.

**Tests.** `tests/gridspine/test_packaging.py`: the distribution resolves at the pyproject version; `gridspine.__file__` is this checkout; a subprocess from a temp directory with no `PYTHONPATH` imports the same file. `pypsa-gui/backend/tests/test_gridspine_service.py::test_the_service_does_not_edit_sys_path`: an AST scan that fails if the stopgap comes back (RED with the insert present, GREEN without; mutation: re-adding a `sys.path.insert` turns exactly it red).

## D3 — a project's own solved network as the dispatch source: TAKEN, as the spec's identity map

**What the spec says.** The stage-1 → stage-2 contract is a dispatch table keyed by detailed-grid unit id; PyPSA is a *producer* of that table, and `producers/pypsa_nodal.py` is "solved PyPSA network → dispatch table (identity map)". Increment 4 offered two sources: `"generate"` (case39 + rolling UC inside the study) and `{"from_dispatch": dir}` (another study's tables). What was missing is the flow the product is for: solve a capacity-expansion project in the GUI, then study THAT dispatch.

**The constraint that shapes it.** Everything after the dispatch — the load flow, the screening, the templates, the RAW/DYR writers — is the IEEE 39-bus detailed grid. So a project's network is a dispatch source exactly when its generators ARE case39 units: same names, same buses. That is the identity map, and it is checked in both directions (a unit the network lacks would leave a machine with no dispatch row; a unit the grid lacks has nowhere to go), plus the bus each unit sits on. A PyPSA-Eur clustered network is NOT a source — the spec's "clustered producer (commitment-aware disaggregation)" is a later item — and the error says so with the unmapped ids rather than silently ranking a grid that is not the one being studied.

**Facts measured before designing (2026-09-08).** A PyPSA `export_to_netcdf` round-trip keeps `generators_t.p` always, and keeps `generators_t.status` when at least one unit ever departs from the default (a one-unit probe that was always on came back with no status at all; the 24 h case39 solve, which cycles units, came back with all fifteen columns). So the producer takes the status column for the units that have one and INFERS the rest from output, `status = 1 iff |p| > 1e-4 MW` — exact for case39's units because a committed machine runs at ≥ 30 % of `p_nom` (`p_min_pu=0.3`) — and records which in the manifest's `dispatch_source.commitment`. The GUI saves the solved network into the project's `network.nc` on save (`routers/projects.py` → `export_to_netcdf`), and its solver runs committable units as a MILP, so a saved, solved project carries what the producer needs. The GUI's bundled templates (`project_templates/_build.py`) are unsolved 24-hour networks with DATETIME snapshots; gridspine's `to_pypsa` used `range(hours)`. Both producers align positionally (hour = snapshot position), so a datetime index is fine downstream — and `to_pypsa` now accepts an index as well as a count so the template can be built with one.

**Design.**

1. `producers/pypsa_nodal.py` (the only module that may import pypsa): `to_pypsa(net, snapshots=<int | index>, ...)`; `load_solved_network(path)`; `dispatch_from_network(n, net, registry) -> (dispatch, loads)` — solved check (`generators_t.p` covers every generator), identity map both ways, bus check, then the existing `to_dispatch_table` / `to_loads_table`. Q for loads is the detailed grid's constant power factor, as for a generated dispatch (the same ledger assumption).
2. `drivers/year_study.py`: `dispatch_from_network(src, outdir, *, progress)` — stage `ingest` (case39_res + registry), stage `dispatch` (read, map, write `loads.csv` then `dispatch.csv`, one tick), returning the tables and a `dispatch_source = {network, network_sha256, hours, commitment}` for the manifest; `window`/`overlap` None, as for a resume — the solve did not happen here.
3. `drivers/study.py`: `StudyConfig.from_network: Path = None`, exclusive with `from_dispatch` (a `ContractError` at construction); `run_study` branches on it. In this mode `hours` describes the source, as `from_dispatch` already does.
4. Backend: `set_dispatch_source(db, project, source, user=None)` accepts `{"from_project": <name>}`, resolved under the ACTING USER through `project_registry.resolve_project` (404 for unknown or foreign, like every other lookup), refused with 422 when the source is a planning project, is the study itself, has no `network.nc`, or is not solved (a `generators_t.p` read under the netcdf io lock); stores the absolute `network.nc` path as `from_network` and clears `from_dispatch`. `get_config(project, db=None)` adds `from_project` (the name, found by matching the stored path against the org's project directories) so the UI and the copilot can say which project, not which path. `from_network` is deliberately NOT in `EDITABLE_CONFIG_FIELDS`: a raw path would let a caller point the study at any file the server can read; the project route goes through the ACL. Router: `DispatchSource.from_project`; chat: `gridspine_set_dispatch_source(project_id, from_dispatch=None, from_project=None)`.
5. A bundled **IEEE 39-Bus (New England)** project template (`project_templates/_build.py::build_ieee39`, id `ieee39`): `to_pypsa(load_case39_res(), snapshots=<24 h datetime index>, res_cf=res_cf_for(net, 24))` — the same network the study would generate for itself, so a user can create it, solve it in the GUI, save, and pick it as the source. Without it D3 is plumbing nobody can reach. Like the other templates its `network.nc` is gitignored and built by the script, and feasibility is verified at build time (a 24 h MILP, seconds).
6. Frontend: the panel's Dispatch source section becomes a three-way choice — generate, a finished study directory, a solved project (a dropdown of the org's projects that are not studies and carry an objective, i.e. have been solved and saved) — showing the current source by project name; the wizard's template list gains the 39-bus card.

**Runtime discipline kept:** the driver test solves ONE 24-hour exact UC (~6 s) to make the source network and studies it with k=1, no screening; the backend test does the same once and reuses the file.
