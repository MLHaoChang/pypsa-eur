# Planned validation and test ownership

All cases below are **planned**, not executed. Each has one primary owner ticket and an observable expected result. Exact test function names are selected against implementation-time master; this matrix does not claim those functions exist today. Fixtures must be admitted under the source protocol; independent oracles cannot be generated by the production parser/engine under test.

## Execution and reporting

1. Write meaningful red tests from the assigned case IDs before code. Use explicit source cell/time/physical facts as expected values. Keep source and consumer tests separate so a broken parser cannot define its own truth.
2. Run the ticket's existing regression anchors plus new focused tests. For UI run relevant component tests, typecheck and actual browser Guided/Expert states. For native engine changes include small independent result oracles. Add a full suite only where repository checks or unresolved risk justify it.
3. Any changed chat tool/route must retain schema/handler/argshape/write-surface and results-walk behavior, run generated inventory and applicable control-matrix checks. Source data is untrusted; offline tests must not call paid APIs or external live endpoints.
4. Run applicable exact-head remote checks and fresh repo premerge. Record actual executed CI steps; no path-filtered job substitutes for tests of a changed path. Keep review requirements and coordinator merge ownership.
5. Report source research, software validation, source admission and domain calibration separately, with head SHA, source/fixture hashes, commands/results, intentional skips and residual gaps. Do not add overlapping pass counts.

The inherited **379 passed** in the baseline summary is a previous selected-suite run on master, not execution of any case in this document. This specification PR requires structural/link/dependency/diff checks; future adapters need their own tests.
