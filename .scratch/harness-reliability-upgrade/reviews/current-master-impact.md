## Process-lifetime worker lock and removable project storage

`services/app_workers.py:98`, `require_single_worker`, supplies configured-worker early refusal. `hold_store_lock:106` takes `.worker.lock` with zero timeout and retains its context manager for process lifetime in `_HELD`, keyed only by the realpath string. `harness/durable.py:30`, `transaction`, separately takes `.owner.lock` for each bounded operation. Both guarantees must survive; neither lock is a replacement for the other or for HH-09A's stable project lifecycle guard.

There is a concrete future lifecycle hazard: `_HELD` returns immediately for a cached path without checking the current directory/lock-file identity. On POSIX, deleting/replacing that directory can leave the held handle locking an unlinked old inode while a second process locks the new `.worker.lock`. A local rename moves the held lock inode to the new name but leaves the old pathname cached. Reusing that old name can falsely count the new store as held; reopening the moved store under its new path can also attempt to acquire the already held inode. `project_registry.rename_project:302` / `os.replace:406` really move local-mode project directories; this is not a hypothetical path model.

Minimal preservation requirement for HH-09A §2.7 and its allowlist:

1. Include `services/app_workers.py` for narrow store-identity/rename/delete/restore participation. Keep the process-lifetime exclusivity and existing 503 refusal. A cache hit must establish that its live lock handle still protects the exact current store/lock identity; a path string alone is insufficient. External unexpected replacement refuses closed until safely reconciled; it must not silently bless a new inode.
2. Under the existing proposed stable project lifecycle guard, re-resolve the original project UUID/current directory before any `hold_store_lock`, parent transaction or creation of directories. `hold_store_lock` currently calls `os.makedirs`, so an existence check performed later in `_save` is too late to prevent resurrection.
3. Successful same-project directory moves must preserve the held OS lock while atomically rebinding its cache identity to the current path, with failure/compensation leaving an honest usable binding or an explicit unavailable state. Old-path/name reuse must never inherit the old project's cached ownership. Do not release/reacquire a live worker lock merely to make rename work.
4. Quiescent authorized removal/restore must invalidate or retire the exact cache binding only under the lifecycle fence, after every pending writer/reaper/resource is accounted for; stale waiters return not-found rather than creating a directory. A restored/replaced store must receive an actual current-inode claim. Unsettled inference holds, legacy speech reservations/closing sessions and pending timer writes block removal or require the reviewed quiescence protocol.
5. Timer/boot paths use their original owned project/thread/session identity to resolve the current destination under this fence. A stale captured pre-rename path cannot be authority to recreate or write storage. The lifecycle guard remains outermost; no asynchronous transport close, network call or timer join occurs while it is held.

This is a contract-level requirement; no specific cache implementation or lock API is prescribed here.
