## Outcome and non-negotiable invariant

For the covered main-chat and checked-answer review paths in HH-03A, and every covered stage/worker/resource operation in HH-03B, an enabled durable policy admits each **physical inference send** only after a server-owned reservation and a dispatch-intent transition are durably committed. Admission checks `settled actual + all outstanding upper-bound holds + proposed hold <= configured limit`, atomically within the applicable scope. A hold is not spend, but unavailable capacity. No timeout, abort, process restart, context compaction, session resume, parent generation change, feature rollback, or missing usage receipt may silently release it.

The result is a bound on the configured, declared dimensions for covered requests whose adapter can establish the bounds. It is not a provider billing guarantee, an account-wide spending cap, or a cap on excluded inference. A missing/invalid price or billable-input bound prevents monetary admission; an operator may explicitly select the narrower token policy described below. Never label an estimate or an incomplete coverage set a hard monetary cap.

Existing caps remain independent AND conditions: `budget._turn_budget_block`, session output and turn-count limits, per-turn output/tool limits, `TaskCap` output/tool/round limits, daily-history gate, retry/backoff limits, reviewer output/event/time/slot bounds, and runner unmetered/cost gates. This work must not raise or bypass any of them. Existing gates are observations/checks in addition to this admission ledger; they are not added again as a second charge for the same attempt.

The owner/project-day limit is mandatory in every enabled mode, so opening a new chat/parent cannot bypass the selected cross-session dimension. Networkless/unsaved-project turns refuse before inference with `budget_scope_unavailable`; do not silently run uncovered. Default-off preserves existing unsaved-project behavior.

## Bounds, units and authoritative receipt

Use the existing four neutral token names: `input_tokens` (uncached), `cache_read_tokens`, `cache_create_tokens`, `output_tokens`. Tokens are strict nonnegative integers; reject bool, floats, negative values, NaN/infinity, duplicate JSON keys, overflow and missing required counts. Each receipt records completeness separately from a normalized numeric dictionary. The current `_count` clamping is not completeness validation.

`PreparedCall`/`CallBounds` (new HH-03 contract implemented in the provider layer) must provide adapter/bound-contract version, exact model/endpoint capabilities, `input_total_upper`, `output_upper`, permitted cache categories, reasoning treatment, payload digest and transport send budget. A token count estimate, character length, packet bytes, model name prefix, or requested `max_tokens` on an arbitrary compatible endpoint is insufficient. Supported proofs are a verified local tokenizer+serialization overhead bound for that exact model/payload, or a documented and enforced provider maximum/context contract with full referenced-context accounting. Network token-count endpoints are not used by admission in this ticket; they would themselves require coverage and a latency policy. Vision/PDF/audio inputs and Responses continuation refuse strict total/money admission until their adapter supplies a certified conservative billable bound. Full-context bounding is acceptable even when only a tail is transmitted. Unknown capability stays unavailable; do not guess a context window.

Cache categories partition actual input for supported adapters. Reserve input liability at `input_total_upper * max(applicable uncached/read/create rate)` so a cold cache or cache-write premium is covered. Do not assume cache hits because `stable=True`, or multiply the whole input by all three rates. If a provider bills overlapping cache/input categories, supports additional charges, or lacks a bound on reasoning/storage/tool/other request charges, monetary mode is unavailable until explicitly modeled. Nonmonetary output mode must disclose uncovered billable dimensions.

Currency is exactly `EUR`, accounting unit `micro_eur` (1 EUR = 1,000,000 units); rate units are EUR per million tokens. Parse configured decimal rates as decimal/rational values, snapshot exact canonical values and source/revision, and round each attempt's reservation and settled monetary charge upward to the next micro-EUR. Never compare EUR floats to micro-EUR integers; no implicit FX or USD-to-EUR conversion. `runner.rates()` is a reusable source/validator to refactor into provider-neutral pricing, but its built-in prefixes are configured estimates until the policy explicitly attests exact provider/model/endpoint, rate validity and category coverage. Rate changes affect new attempts only; settle old ones with their pinned snapshot. Source facts do not currently establish verified current provider prices or input bounds; implementing these capabilities is an activation prerequisite, not research to invent in code.

For money, `reserve_micro_eur = ceil(input_total_upper * max_input_rate + output_upper * output_rate + explicitly modeled fixed upper charges)` with rate units converted correctly. Total-token hold is `input_total_upper + output_upper`; output-only hold is `output_upper`. Set `request.max_tokens` at or below all existing/profile/task limits and remaining output capacity; if lowering it, reprepare and hash the actual lower request. A minimal positive requested output that cannot fit refuses. Do not send first to learn the actual input count.

Receipt includes raw-validation status, adapter-normalized four categories, provider request/response IDs when safely available, terminal/complete indication, and digest of the canonical receipt. Missing fields, provider protocol errors, partial-only receipt, absent terminal event or counts beyond certified bounds cannot certify settlement. Persist valid observed lower-bound usage with an unresolved hold and stop further calls in the affected scope if a bound is violated. Record the overrun truthfully and block the capability/policy pending repair; never clamp billed actual to the reservation or continue while asserting a cap held. Complete valid zero usage is possible only with explicit receipt/proof, never with `{}`.

## State machine and exactly-once accounting

Proposed internal APIs are `reserve_call`, `mark_dispatch_intent`, `record_transport_observation`, `record_unknown`, `settle_call`, `prove_no_send`, and `recover_budget_attempts`. They replace/strictly wrap the old free-form helpers for v2; no route accepts them directly.

| State | Capacity and allowed transition |
| --- | --- |
| `reserved` | Holds committed; no dispatch intent. A process-local attempt capability may advance once to `dispatch_intent`. Repeated reserve of identical origin/digest/bounds returns the same receipt, **not permission for a second dispatcher**. |
| `dispatch_intent` | Persisted immediately before invoking transport; treat as potentially submitted. Remains fully held. Transition to `submitted`, `unknown`, `settled` or positive `no_send`. |
| `submitted` | Transport/provider acceptance observed. Hold remains until complete receipt; may become `unknown` or `settled`. This observation is useful, not necessary to retain a hold. |
| `unknown` | Timeout, partial stream, abort/disconnect after intent, missing/invalid usage, provider failure with uncertain billing, or recovery of intent/submitted record. Hold remains. Late complete receipt can settle. No automatic retry/replay. |
| `no_send` | Positive recorded proof that the physical inference dispatch did not occur (or provider explicitly proves nonbillable rejection). Release hold once, retain tombstone/proof. Terminal. |
| `settled` | Complete validated actual receipt; replace hold by actual once. Repeat identical settlement returns the stored receipt. Different receipt/actual is a conflict and blocks admission for repair; never overwrite, double add or subtract. Terminal except explicit audited correction support outside this ticket. |

`mark_dispatch_intent` is a compare-and-set from `reserved` bound to the original process-incarnation capability; it has one winner. An idempotent readback of an already committed intent does **not** grant permission to invoke transport again. If the caller cannot tell whether this transition committed, it records/retains unknown and sends nothing. Never hold the directory/session/network lock while performing provider I/O, waiting on review futures, or backoff.

Positive no-send proof includes cancellation before dispatch while atomically revoking the still-reserved capability, a failed queue submission with no worker pickup, or adapter-local validation before any transport call. If a persisted `reserved` attempt's process died, a recovery transaction can tombstone it as `no_send` only because transport code cannot execute before the durable intent transition, and the new process does not inherit the old capability. Race live workers with the same CAS: a revocation winner prevents send. A connect/DNS error is only proof when the instrumented adapter can establish no request bytes/dispatch and has no hidden retry; a generic mapped `ProviderError('unreachable')` alone is insufficient. No tokens/SSE frames, close(), cancellation request, elapsed lease/deadline, 429/5xx status, and lack of `message_done` are **not** proof. A 400 compatibility rejection may be positively nonbillable only under an explicit validated endpoint contract; otherwise hold it unknown even though another attempt is permitted by retry policy.

At every `message_done`, validate and settle before accepting its result as an accounted complete call. Generator close/finally is not settlement. A complete receipt received before a later cancellation/error may settle irrespective of the answer's publication disposition. If persistence fails after a valid receipt, retain the existing hold; return typed accounting-unavailable and do not make a further provider call. If persistence committed but the acknowledgment was lost, re-read the same attempt/receipt digest and return the existing settlement. Unknown late receipts remain accepted by immutable origin even after session TTL, parent resume, model change or user cancellation. Late worker completion can settle money/tokens but cannot overwrite a published verdict, revive a cancelled answer, clear a new session's abort state or schedule repair.

Recovery on startup/admission reads bounded existing records. Orphan `dispatch_intent`/`submitted` becomes `unknown`; do not probe/replay provider inference. Existing `unknown` stays held. A live-worker timeout marks unknown under the transaction and a racing settlement wins monotonically: if settled, marking unknown is a no-op; if unknown first, settlement later removes the hold once. Final charges are deduplicated by attempt identity, not turn/session cumulative counters. Preserve typed settled records on rollback and restart.

## Retry, transport and reviewer wiring

The output-emitted retry guard remains necessary for UI correctness and is insufficient for billing. Every outer transient retry, fallback and inner token-parameter retry has a separate attempt/hold. A retry after an uncertain failure is a newly authorized inference, not recovery of the old send; outstanding earlier holds remain included. Strict mode may therefore refuse a retry even when no text was emitted. Never recycle an unknown attempt's reservation or reuse its provider idempotency key for a changed payload/model. Provider-supported idempotency keys are used only where documented for the exact endpoint and derived from physical attempt ID; they supplement, not replace, the ledger/CAS.

Disable Anthropic SDK retries with explicit `max_retries=0` in **both** `build_client` and `_anthropic_client_for_profile`; verify injected production clients satisfy the same send contract or refuse strict coverage. Inspect httpx/transport retry behavior too. Preserve the compatibility feature, but move each `_stream_once` send through the HH-03 physical-attempt hook. No uninstrumented adaptive request remains inside `provider.stream` for admitted calls. `openai_responses.payload` must bind any mutable continuation state during preparation; parallel reviewer use cannot change the prepared assistant payload.

Expose/enforce a finite transport-send allowance per logical assistant request, covering existing normal attempts plus the one eligible fallback and compatibility sends. Proposed upper ceiling preserving baseline behavior: `(MAX_STREAM_RETRIES + 1 + int(fallback_eligible)) * compatibility_send_factor`, where factor is at most 2 for the token-parameter adapter and 1 otherwise. The reviewer has one logical call, at most two physical sends only if its adapter's existing compatibility retry is required; no transient retry, model fallback or repair call is added. Count permits before dispatch (including a failed physical request), never reset inside an adapter. HH-03 owns this shared allowance across loop and adapters; it must not create an additional retry budget beside it. Persist send ordinal/ceiling with each retry group so restart cannot replenish it; restart never resumes an unfinished group automatically.

Review sequence: packet validation/slot admission -> submit worker with frozen context -> worker pickup abort/origin check -> prepare and reserve -> intent commit -> physical send -> validate/settle independently of verdict -> existing bounded verdict checks. Queue submission failure releases slot and has no send; a queued cancelled future must prove it never started before releasing a reserved hold. Prefer reserving at worker pickup so queue wait consumes no held capacity. Timeout keeps a running worker's hold and slot until worker cleanup, with no extra review. A late invalid/incomplete receipt stays unknown. Existing usage accrual/metrics become idempotent projections keyed to the accepted settlement, and ordinary main-chat accrual must not double-count the same successful receipt already settled in the send seam. Existing history turn totals remain intact for legacy readers.

`runner.charge` remains its existing task-run accounting/gate; no unconditional call is invented from main chat. HH-03B requires a durable attempt-ID projection receipt in the task's existing state when feeding this existing gate from stage/worker inference; failure blocks further run inference. That projection is not a second ledger. HH-03A alone does not claim strict run-cost pre-send admission. HH-03B must include the run limit and immutable owner/task binding atomically in the existing parent admission scope before enabling paid stages. Keep the baseline fail-closed unknown-model/missing-usage behavior and its tests.
