## 1. Outcome and boundaries

A user can explicitly save “Keep the current model horizon” and “The generator named Solar A must have configured power at most 12 MW.” Once confirmed, these engineering requirements remain typed, inspectable parent-conversation facts after message trimming, a provider change, episode restart, and a same-project rebind. The assistant reads the current records each turn and checks supported candidate effects in native code. A stale validation never turns into permission to change inputs.

The first slice enforces two input predicates: preservation of the confirmed native horizon and bounds on one exact named `Generator.p_nom` scalar. It also retains explicitly optional preferences as advisory notes. It does not enforce arbitrary natural language, solver outputs, financial objectives, optimum capacity, import peaks, reliability, or regulatory compliance. In particular, a bound on configured `p_nom` is not a bound on `p_nom_opt`, dispatch, energy, or the capacity selected by an extendable generator. The confirmation card states this distinction and the current extendable setting. If the user's intent is an optimised-capacity limit, do not translate it to this predicate: offer the appropriate native field edit separately and explain that its persistent requirement adapter is outside this slice.

“Enforced” means enforced for supported effects admitted through an explicitly attached assistant requirement scope. It is not a project edit lock. Manual UI operations continue through native validation. Manual drift invalidates requirement evaluations and pending assistant admissions; it never deletes the user's requirement. A requirement record is a business constraint, never execution authorization, a tool permission, proof of model correctness, a checked-answer approval, an approval envelope, or approval of a study brief. Existing ACLs, locks, tool restrictions, budgets, confirmations, checked-profile guards, and run gates still apply independently.

No new assistant mode, dashboard, requirements sidebar, duplicate Save action, agent memory service, or model-generated policy engine is introduced. Reuse the existing Choice, edit-card, confirmation, parent-thread and task infrastructure.

## 3. Concrete first-slice predicates

All schemas are closed (`extra=forbid`), versioned and server validated. No wildcard, regex, expression language, arbitrary attribute path, query selector, Python, or model-supplied reader is accepted.

| Kind | Target and comparison | Native basis | Meaning and refusal boundary |
| --- | --- | --- | --- |
| `preserve_horizon` | The attached project's horizon; `op=eq` against a server-captured descriptor hash | Exact ordered snapshot index with index type/names, all investment periods, snapshot weights and investment-period weights, including column names/order and finite numeric values | Preserve the exact native sampled horizon and weights, not merely start/end/count. The server reads and hashes it; a request cannot supply its own authoritative hash. Missing, malformed, ambiguous timezone/index data or unreadable weights refuse capture. Solver outputs and asset values are excluded. Solver foresight/rolling settings are not silently added to this predicate. |
| `scalar_bound` | One exact `Generator` name and field exactly `p_nom`; `op` is `eq`, `ge`, `le` or inclusive `within` | Native stored scalar unit and resolved power/commodity basis of that generator, captured from current native metadata and target read | Bound the configured static scalar. Values must be finite JSON numbers excluding booleans; `within` has exactly two ordered finite endpoints. No `p_nom_min`, `p_nom_max`, `p_nom_opt`, time series, cost field, multiple targets, or other class in v1. |
| `advisory_note` | No executable target or comparator | Explicitly optional user preference, up to 240 characters | Informational only; never converted into a blocking predicate by the model or admitted as a native pass. |

The normalized proposal structures are exact:

```text
scalar proposal = {
  kind: scalar_bound, enforcement: enforced,
  target: {component_class: Generator, name: string[1..120], field: p_nom},
  predicate: {op: eq|ge|le, value: finite_number, unit: string[1..32],
              basis: {commodity: string[1..64]}}
    OR {op: within, value: [finite_number, finite_number], unit, basis},
  intent_quote: string[1..512]
}
horizon proposal = {
  kind: preserve_horizon, enforcement: enforced,
  target: {kind: project_horizon},
  predicate: {op: eq, capture: current_native}, intent_quote: string[1..512]
}
note proposal = {
  kind: advisory_note, enforcement: advisory, target: null,
  predicate: null, text: string[1..240], intent_quote: string[1..512]
}
```

Literal values above are enums, not arbitrary strings. Scalar unit/commodity are checked against native resolution, never trusted as supplied. On horizon preview the server replaces `capture` with `{op: eq, descriptor_sha256, descriptor}` in the normalized candidate; confirmation binds that captured descriptor, and re-preview refuses if it changed. The final note record retains `text` and no executable predicate. Every proposal's quote is checked against the owned admitted explicit user source bound by the server; the request does not supply confirmation metadata or choose a foreign source event. A model's reformulation can be shown on the card, but its provenance cannot masquerade as a direct quote.

For scalar bounds, resolve the unit and commodity from the actual row before preview. Where native metadata uses generic `MW` with a commodity-dependent meaning, carry the resolved commodity separately and display its native wording. If the dimensional meaning is unavailable or inconsistent, refuse `requirement_basis_unavailable`. Unit equality is exact after native canonical serialization. No implicit kW/MW, MWh/MW, money-year, currency, annualisation or percent conversion is allowed. A user who supplies a different unit must explicitly confirm a separately shown supported native conversion; that conversion adapter is deferred in v1, so the safe first-slice behavior is a typed unit refusal and a Choice/request using the native unit. The model must not perform a conversion and claim the original quote was confirmed unchanged.

For horizon display, show readable period/range/count/weighting summaries plus the exact descriptor digest and “Preserve snapshots and weights.” Store the complete bounded descriptor privately to make equality independently reproducible; do not put the entire time axis into the model prompt. Cap the canonical descriptor at 256 KiB. An oversized horizon is unsupported, not silently sampled or truncated. The current native index order and representation are authoritative; an equivalent-looking reordered axis needs explicit new confirmation.

Other scalar predicates are follow-on adapters, not aliases accepted by this schema. Candidates include native `Generator.p_nom_min/max`, `StorageUnit` power/duration, `Store` energy and branch apparent-power fields. Each amendment must name its real metadata/target reader, stored unit, basis, dimensional semantics, candidate-effect adapter and tests. Cost predicates additionally require explicit currency/money-year and stored cost basis. Do not expand the registry merely because a field is numeric.

“Peak imports below 5 MW,” “no shedding,” and “lowest annual cost” are result objectives. Present them as proposed objectives or explicitly advisory notes until a separately specified, versioned native gate supports the exact metric, source, window, aggregation, sign/direction, unit and applicability. Do not claim an input scalar cap proves the objective. Result enforcement needs fresh native result evidence and its gate stage, which may legitimately be after execution; it cannot be represented by an always-passing pre-effect input check. HH-02 adds no such result adapter and does not relax generic run-profile rules.

## 4. Record, scope and authority contract

Add a typed `requirements` document to the existing parent JSON, alongside the legacy fields. Proposed names in this section are new contracts, not claims that these classes/functions exist today:

```text
requirements = {
  version: 1,
  requirements_revision: integer >= 0,
  records_digest: sha256(canonical current records),
  records: [RequirementRevision],
  request_receipts: [bounded idempotency receipt]
}

RequirementRevision = {
  id: server UUID, revision: integer >= 1,
  state: active | superseded | retired,
  enforcement: enforced | advisory,
  scope: {owner_id, project_id, thread_id},
  kind, predicate: kind-specific closed structure,
  target: kind-specific typed target or null,
  source: {origin: explicit_user, episode_id, turn_id, source_event_id,
           quote, proposed_by: user | assistant},
  confirmation: {decision_id, by: user, confirmed_at, preview_digest},
  created_at, changed_at, supersedes: prior revision or null
}
```

Server derives actor, project, thread, timestamps, source event ownership and confirmation linkage. The user/model may propose wording, a target and numbers; they may not assert `state=active`, confirmation metadata, an approval token, or an enforcement verdict. `source.quote` is at most 512 characters of the exact relevant user intent; avoid copying unrelated messages. Source IDs are opaque and bounded. An optional document or tool-result citation is additional provenance only: an attachment, PDF, imported prompt, Library description, tool output, model response, or summary cannot be `origin=explicit_user` by itself. The user must explicitly adopt the displayed normalized requirement.

`pending` is a proposal/confirmation state, not a confirmed active record. The existing pending card owns the immutable normalized proposal and its bindings until approved, denied, expired, aborted or revoked. No durable active requirement is written during preview. After a restart, a historical pending-card observation remains historical; it cannot restore an approval token. A durable read may describe an unavailable/revoked proposal origin, but may not merge it into `records`. Rejecting a proposed replacement leaves the old active revision unchanged.

Each ID has one current active revision or one retirement tombstone. Replacement atomically supersedes the old revision and creates the new active revision; removal creates a retirement revision and retains the prior confirmed provenance. No record is edited in place. `requirements_revision` advances once per committed patch, not once per record. `records_digest` covers current normalized record content, scope, enforcement and record revisions; display-only evaluation timestamps are excluded. Historical revisions and confirmation links remain immutable.

Bounds: at most 32 current records including advisory notes, 12 operations per patch, 256 retained record revisions and 1 MiB for the whole requirements document, in addition to the horizon descriptor cap. On overflow, refuse without changes (`requirement_capacity_exceeded`); do not evict active requirements or provenance. An explicit future archival design may amend these limits. Request receipts share this bound; completed request IDs remain sufficient to prevent a replay from creating a second mutation. When their bound is exhausted, refuse new mutations rather than quietly making an old request executable again.

The saved native project and parent thread are both scope, with current project ACL/acting identity/authoritative replica checked on every read and change. Scope is not a user-supplied filesystem path. First-slice records are owner-private parent facts; another editor does not inherit the owner's conversation requirements. A different thread in the same project does not silently inherit them either. This is not a shared project policy feature. Retained identifiers never substitute for a fresh ACL check.

Target identity in v1 is explicitly the native model row `{project_id, component_class: Generator, name: exact native name}`. No immutable physical-equipment UUID is claimed. Ordinary edits to that row keep the requirement identity and cause fresh validation. A missing row, rename, ambiguous resolution, changed commodity basis or incompatible schema gives `unresolved`; do not fuzzy-match, choose a similarly named generator, or silently retarget. A user who wants the renamed row amends the target on the same requirement ID and confirms the old → new target. The card states that the requirement applies to the named model row, not a separately tracked physical equipment incarnation. Deletion/recreation and whole-network replacement require source/identity review where native provenance cannot establish continuity; a same-name appearance alone must not be presented as proof of physical continuity. HH-04 may add stronger native identity references through an explicit schema amendment.

Legacy `constraints: list[str]` and `units` remain readable historical notes. No migration parses them into enforced requirements or manufactures a confirmation. Show “Earlier conversation note · not confirmed for enforcement” where needed. `checkpoint_thread` must reject attempts to set the new typed document, its revisions/digest, or its confirmation fields through generic checkpoint payloads. Generic updates to legacy text cannot shadow typed records. Do not expose typed requirements as another free-form `dict[str, Any]` replacement.

## 5. Mutation, read API and tools

Add exactly these native controls for this slice:

* `get_requirements(thread_id, offset=0, limit=8, include_history=false)` — read tier. Returns authenticated scope, generation, `requirements_revision`, `records_digest`, counts, bounded current rows and optional paged historical revisions. Maximum `limit=20`; paginate by returned count, no omitted enforced record disguised as a complete list. Response is `no-store`. Current validation status is clearly separate from the confirmed predicate; a read does not write a new confirmation or advance a task.
* `update_requirements(thread_id, generation, expected_requirements_revision, expected_records_digest, request_id, operations)` — write tier, classified as a settings edit. Operations are `add`, `replace` or `remove`; replacement/removal require ID and expected record revision. Add/replace accepts only the closed proposal structure. `request_id` is 1–64 characters, server scopes it to owner/project/thread. No raw persistence path, force flag, `approved=true`, `skip_validation`, `apply_to_running`, or predicate-language escape hatch exists.

Operation objects are exactly `{op: add, proposal}`, `{op: replace, id, expected_record_revision, proposal}`, or `{op: remove, id, expected_record_revision}`. Their array order is part of the request digest; validate the final candidate set before commit and prohibit two operations naming the same existing ID. IDs are canonical UUIDs. Generate add IDs deterministically on the server from the already-authorized thread UUID, request ID and operation index (UUIDv5 with the thread UUID as namespace), so pure re-preview returns the same ID without writing a draft checkpoint. A changed request under that ID still conflicts on its canonical payload digest. Preview-generated IDs grant nothing and unconfirmed ones need not be retained in the authority store. A previously confirmed identical request returns its existing IDs/receipt.

Use one update tool for create/update/delete rather than three permission surfaces. Preview is the existing `edit_card.preview` path and is pure; do not add a second persisted preview tool. Readback returns a bounded receipt containing exact committed revisions/digest and the old/new current records. Requirement removal is retirement, not a hard delete. The receipt says “Saved requirement,” “Changed requirement,” or “Removed requirement,” not “Model approved,” “Study valid,” or “Run authorised.”

Add matching native routes beneath existing durable-conversation routing: `GET /{thread_id}/requirements` with the bounded read query, and `POST /{thread_id}/requirements` with body exactly `{generation, expected_requirements_revision, expected_records_digest, request_id, operations}`. These are proposed new route suffixes; the authenticated path supplies `thread_id`. The POST is an internal native tool route, called in-process by the ordinary dispatcher after its confirmed edit card, not a new browser confirmation API. Require the server-held exact approved edit digest (`edit_card.approved_digest()` is the existing digest context seam), augmented with the verified `by=user` decision/request linkage; a network HTTP request cannot manufacture this context using a body field/header/token. A direct unconfirmed POST returns typed `requirement_confirmation_required` and writes nothing. The service verifies this context too, so bypassing the route does not bypass confirmation. UI mutation uses existing chat dispatch/confirmation; frontend adds only the GET helper and typed tool/stream shapes. Classify POST's internal-only disposition in route parity. Do not create a second “confirm requirement” trust mechanism.

The update card includes: saved project/thread identity, old/new requirement wording, enforced versus optional, exact target and native field, comparator/endpoints/unit/basis, existing current value where readable, horizon summary when relevant, records being superseded/retired, and “Applies to future supported assistant actions; does not authorise a run.” A predicate may be confirmed while its current target value violates it; show that violation prominently and do not fix inputs as part of saving the requirement. A missing target/basis cannot be newly captured as enforced. Existing records that later become unreadable remain active and unresolved.

The settings-edit adapter must be complete and pure, bind the entire normalized patch and both CAS values in its digest, and read back the actual committed document. An incomplete arguments-only fallback cannot activate an enforced record. Requirement changes always require `by=user` even in Expert and when auto-approval/envelope settings would permit another tier. An envelope may not approve this metadata change. A policy-approved/no-card decision is insufficient. Audit failure or inability to persist the exact one-use commit marker refuses the operation. A Choice response such as “Yes,” a brief approval, an old chat message, or a forged source event is insufficient.

Append the two catalogue entries in `harness/catalogue.py`, use native wrappers in `services/chat_tools.py`, wire `DISPATCHERS` and `TOOL_ROUTES`, classify both tools in capability/access/route parity and strict-profile dispositions, and classify the mutation in edit-card tests. Keep the existing checked-profile guard: these newly introduced requirement controls remain unmapped/refused in strict checked execution until an explicit assurance adapter is approved in another slice. Ordinary requirement context does not weaken that guard. Do not hand-edit a generated tool catalogue or checked-profile allowlist.

The catalogue, route parity and control inventories are computed by `smoke/assistant_inventory.py --check`, `smoke/assistant_route_parity.py --check` and `smoke/assistant_control_matrix.py --check`; baseline README explicitly says adding a tool requires no committed regeneration. Add new hand-maintained error-kind and route-disposition entries in issue-specific fragments under `pypsa-gui/tool-error-kinds.d/` and `backend/smoke/assistant_route_parity_declarations.d/`; do not edit generated JSON by hand.

## 6. Exact CAS, concurrency and crash behavior

The authority tuple is `(owner, project, thread, generation, requirements_revision, records_digest)`. Generation alone is insufficient because several changes may occur within one episode. `checkpoint_rev` is still general parent bookkeeping, not a replacement for the requirements CAS. Enforce strict integers (booleans rejected), current digest, and exact per-record revisions before any mutation. Return `stale_generation` for parent-generation mismatch and `requirement_revision_conflict` for same-generation requirement drift, with current revision/digest but no foreign data. Never retry by silently replacing expected values.

Use the existing durable atomic-file approach and `harness.durable.transaction` for cross-process serialization of the parent directory; `_LOCK` alone is insufficient. Requirement mutation, generic parent checkpoint, budget writes, discussed-ref writes, resume and rebind must serialize on the same parent transaction domain and read the latest document inside it. Preserve the existing parent `_save` atomic tmp/fsync/replace behavior. Avoid whole-parent writes from stale read copies that overwrite another field's new requirements. This narrow consistency upgrade is necessary even when another writer changes only a discussed reference.

Lock order for work touching live inputs is HH-01's native mutation guard, then its solver-state guard when the input-version contract includes solver configuration, then bounded `durable_conversation._LOCK`, then the parent directory transaction through the shared proposed `_parent_transaction` helper, then any other participating leaf locks. `_LOCK` is not a later leaf lock; it must not first be acquired inside the directory transaction. HH-09A’s lifecycle guard is outermost once installed on protected directory writers. Never wait for native/solver locks while holding a parent transaction or the global `durable_conversation._LOCK`. Refactor a current outer `_LOCK` path rather than introducing an inverted acquisition hidden inside it. Owner-store-only budget/ref/checkpoint writers use the same `_LOCK`→directory helper (and outer lifecycle guard when applicable) and never reach back for native locks. No path holds those locks while waiting for a session confirmation. Preview and waiting for a user's card occur outside mutation locks. Use bounded locks and a typed busy refusal. Capture bindings for display, release them for any UI wait, then reacquire/re-read all authoritative native state and CAS under the stated order before commit. Requirement activation/replacement holds the final native/solver guards through its atomic parent replace: snapshotting native state earlier and committing later under only the store lock is insufficient. Saving a requirement has no solver/provider work inside a transaction. Its common save invokes HH-03’s whole-parent capacity/headroom validator; a requirement update cannot consume reserved future accounting settlement bytes.

Commit order: validate scope and native proposal; verify the exact audited `by=user` decision; verify generation/revision/digest/request ID; write the normalized document plus idempotency receipt atomically; then deliver the result. An identical replay of an already committed request returns the same receipt without another revision; a changed payload under that ID refuses `requirement_request_conflict`. Check current ACL first even for replay. A crash after file replace and before response is recoverable by that receipt. A crash before replace leaves the old document. A missing/corrupt store or uncertain commit is `requirement_store_unavailable`, never an empty requirement set. No repair, replay or fallback parses chat history into authority.

The native approval may be consumed once; its exact normalized patch/request digest must be recorded with the commit receipt. Approval log availability remains a prerequisite, but a successful approval record alone is not proof of storage commit. Failure to revoke an old in-memory card after a commit cannot permit it: every pickup checks the durable revision tuple independently. Rebind winning a race makes old-generation save/refetch/confirm fail; a save winning first survives the subsequent rebind.

## 7. Attachment to ordinary typed chat and per-turn context

Add a typed optional `requirement_scope` field to ordinary `StreamRequest` and the corresponding frontend send payload:

```text
{thread_id, generation, requirements_revision, records_digest}
```

All four fields are required together; additional fields, partial structures, booleans for integers and malformed digests refuse before provider work. This is an observation binding, not an authorization credential. Server derives owner/project, resolves the active authenticated native context, validates the current parent and authoritative replica, and checks any existing episode/parent association. A thread in another project, another owner's thread, stale revision or contradictory child binding refuses. Do not auto-attach the most recent thread, infer one from `refs.discussed`, borrow the active Live thread merely because it exists, or use localStorage text as authority.

A typed chat with no attached parent keeps its ordinary existing behavior and must not claim persistent requirements are in force. The first explicit “remember/enforce this requirement” action can create a native parent using existing `create_thread` behavior, then explicitly bind that chat/episode through validated server logic. Creation itself does not confirm a requirement. Show its scope on the saved requirement receipt and in the existing chat context area. Existing typed chats do not become attached retroactively. A conflict between an existing child's parent and a requested parent requires a new explicit binding; do not rewrite the child's historical provenance.

Once a chat is explicitly bound, later sends attach the freshly fetched revision tuple. New browser state can recover the known parent only from authenticated native session/thread association. Fetch failure hides stale “requirements active” claims and blocks requirement-bearing supported effects; it does not submit an empty set. Opening a read-only inspector performs no send. Changing attachments, checked selection, draft text or UI mode does not implicitly confirm requirements or detach their scope. Detached/new chats must display that they do not carry that prior conversation scope when the user invokes this feature; there is no global mode toggle.

At accepted turn start and before each supported effect, read the current owned document. Produce a bounded logged per-turn user-context block through `compose.py`; keep `_build_system_prompt` byte-stable for the same static policy. Use normalized facts and their IDs/revisions/digest, native units/basis, enforcement, and current evaluation state. Never put raw quotes into executable prompt prose. Fence/neutralize labels, quotes and notes with the existing untrusted-content utilities. Say explicitly that advisory notes do not block or authorize and that only native admission evaluates enforced records. The model cannot change current records by summarizing them.

All 32 current records fit the context envelope or the turn refuses `requirement_context_too_large`; do not silently omit one due to relevance ranking, tool selection caps, summary trimming or “first N” display pagination. Target labels and notes are bounded, and the horizon is summarized by descriptor identity. Store the exact per-turn revision/digest in the event log; avoid persisting duplicate full horizon arrays in each turn. Dynamic records belong in logged per-turn content even when tools are disabled, marked observational and incapable of execution.

## 8. Revision survival, native validation and HH-01 boundary

Requirement identity is independent of the project's input revision/fingerprint. Store the confirmed predicate's capture basis separately from an evaluation receipt. A receipt contains exact scope, generation, requirements revision/digest, schema/reader version, current native input fingerprint, evaluated predicate IDs/revisions, native observed values/units, `pass|fail|unresolved|not_evaluated`, reason and timestamp. The server computes it; the model cannot submit it. Do not use a previously passing receipt to skip the next native check.

An unrelated legitimate edit invalidates the old receipt but leaves requirement IDs and confirmation intact. Re-read and re-evaluate against the new inputs: a new configured power inside the bound passes without asking the user to re-confirm the unchanged requirement. Horizon equality is against its confirmed descriptor, not against the last successful project fingerprint. A changed horizon fails until the user restores it or explicitly amends/retires the requirement. Missing row, changed commodity/schema basis, corrupt horizon or unreadable source remains active with an unresolved/unevaluated result. It cannot fall out of an “applicable” set and silently stop blocking effects.

Requirements apply to future supported assistant admissions only. HH-01 v1 covers exact scalar `Generator.p_nom`/`Generator.marginal_cost` input updates, as declared by that issue. HH-02 does not extend that effect allowlist. For those admitted updates, HH-01's permit binds `requirements_revision` and `records_digest` alongside owner/project/thread/generation, exact arguments/target identities, candidate inputs, native input fingerprint and its own approval/policy bindings. The native handler's before-effect callback, holding the native mutation/solver guards and shared owner-store transaction in the order above, re-reads the current requirements and evaluates the exact proposed candidate's p_nom and horizon. Keep the requirements CAS protected through the actual native write; releasing the store transaction after validation but before mutation is not sufficient. Its first effect and the corresponding HH-01 reservation/outcome writes follow HH-01's concrete atomic contract. The check and first mutation are one serialized native admission; a model saying “checked” or a pre-dispatch prompt check has no force.

The permit requires every enforced record to be freshly `pass`; advisory records are recorded as advisory, not counted as passes. Evaluate the actual candidate, including native defaults/derived effects, rather than just checking the requested number. Evaluate any immutable HH-01 guard baselines separately; retiring a requirement cannot remove those guards. A pre-existing native violation cannot be carried through an unrelated supported effect with a cached green result. A repair effect that moves into compliance may proceed only if its exact candidate satisfies every enforced record and all ordinary native rules. Changing requirement metadata does not repair the model.

If any active enforced requirement could be affected by an effect with no complete native candidate/atomic adapter, pause/refuse that assistant effect with `requirement_effect_unsupported` and a clear native next step. Unknown impact counts as potentially affected. In v1 this includes unattended horizon edits, restores/imports/network replacement, deletion/rename, arbitrary bulk edits, runs/solves, and effects through external/MCP implementations outside HH-01. Do not dispatch them “because the model promised preservation.” A separately user-reviewed ordinary action may remain available under its existing native flow, but it must not be represented as guarded by HH-02 or inherit a requirement-bound permit. Returning to a guarded chain requires explicit re-review with fresh native state. HH-03 must disclose that coverage boundary before send where applicable.

The guard is assistant-scoped; manual UI editing is not silently intercepted as a universal policy engine. After manual changes, the next requirement read/admission recomputes state. Native input-fingerprint drift already invalidates cached evaluations; lack of an immediate push event cannot allow a stale permit because pickup always re-reads under lock. Unknown provenance after replacement remains unresolved until reviewed. A requirement's original confirmation survives these changes; only its stale evidence is invalid.

## 9. Open cards, tasks, runs and state transitions

On committed requirement change, mark pending requirement-bound native decisions/admission snapshots for the old revision as revoked and release waiting confirmation workers using the existing audit vocabulary. Revoke unstarted armed HH-01 work that named that revision. The durable pickup check is mandatory even if the process cannot find every open browser/session. The requirement update's own completing card is exempt from self-revocation; any other pending card in its affected scope is not.

Do not apply new constraints retroactively to already admitted/running work, change its recorded requirement revision, abort it, retry it, or label its previous output compliant with the new revision. Running records retain the exact old requirement snapshot and receive only an observation that current requirements changed. Later reads may compare current requirements with that historical result only through an explicit supported native evaluation; they cannot rewrite the old receipt. Historical pass/fail always names its historical revision/input basis.

At task/brief creation, explicitly bind the current requirement tuple as an additional immutable brief/run observation. Existing requirements do not inherit into an already armed plan when the records change. Before an unstarted effectful task step, re-check the bound tuple and current native requirements through the same HH-01 admission. A changed tuple yields `task_requirements_stale`, preserves completed/uncertain steps and reservations, and requires a freshly shown plan/step review. Do not silently update the task binding during `get_task`, job completion, continuation, `resume_task`, an automatic gate refresh or history recovery. Re-review never resets no-replay receipts, attempt caps, budget charges or uncertain effects.

Existing `assistant_tasks._gate_brief` and input gates continue to detect ordinary out-of-plan input drift. Requirement stale and input stale are separate reasons and neither clears the other. A paused-at-card task still needs its existing explicit Continue; acknowledging requirements is not that Continue. Plan approval remains no authorization for individual writes/runs. HH-02 does not add a result rule to a shipped immutable run profile or auto-adopt new requirements into an existing gate history.

| Event | Record state | Validation/admission consequence |
| --- | --- | --- |
| Model/user drafts a supported proposal | Pending card only | No enforcement change or effect grant |
| User confirms exact card; CAS and persistence pass | New active record/revision | Fresh evaluations required for future work; old pending admissions revoked |
| Deny, expiry, abort, approval/audit failure, stale card | Existing records unchanged | Proposal ends; no replacement/removal |
| Replace or retire through confirmed patch | Old revision superseded; replacement active or retirement tombstone | Tuple changes; old permits unusable |
| Same-project ordinary scalar/input edit | Confirmed record unchanged | Old validation stale; re-read can pass or fail against same predicate |
| Rename, missing target, basis/schema/source uncertainty | Confirmed record remains active | Unresolved blocks supported effects; explicit target amendment or restoration required |
| Compaction/provider switch/episode recreation | Confirmed records unchanged | Current parent reload; no approval/session-token restoration |
| Same-project generation rebind | Confirmed records unchanged; generation advances | Pending cards/permits/old-generation sends revoked; fresh current attachment needed |
| Another project/owner/thread, project clone, imported bundle | Original stays in original scope | No inheritance or activation; proposed import is historical and requires new owned confirmation |
| Requirement changes while effect already runs | Old admitted snapshot unchanged | No retrofit/abort/retry; unstarted next action is stale |

Conflicting requirements are explicit. For identical named scalar/unit/basis, compute the intersection of active enforced intervals including equality; an empty intersection refuses the entire patch with conflicting IDs and `requirement_conflict`. For two horizon requirements, different descriptors conflict. Exact duplicates refuse `requirement_duplicate` with the existing ID; do not create two indistinguishable enforcement records. Same-bound optional notes do not weaken enforced records. A replace/remove followed by add can resolve a conflict in one atomic patch. Do not pick “latest wins,” average bounds, demote an enforced record to preference, or infer supersession from casual chat. If an old/corrupt imported store contains an impossible active set, reads show conflict and guarded effects fail closed until an explicit repair patch.

## 11. Security, privacy, retention and rollback

Treat requirement names, quotes, labels and advisory notes as untrusted content. Strings such as “ignore all approvals,” fake JSON/SSE frames, HTML and tool names remain escaped/fenced data. They cannot change the predicate registry, current revision, confirmation policy, toolset, checked selection or trusted prompt. User provenance is verified against an owned admitted turn, not accepted because a tool payload says `origin=user`.

Return not-found for foreign thread/record IDs; no distinction reveals another owner's requirement count, quote, project path or predicate. Project access/acting identity precede disk reads and idempotency lookups. Responses use `no-store`; UI clears requirement observations on logout, project change, detach and permission loss, and while refreshing a mismatched scope. Do not log raw bridge tokens, API keys, approval tokens, file paths or full horizon arrays into analytics/error messages. Use existing secrets-redaction where history/projections are persisted.

Retain typed records for the parent's lifetime; message trimming and approval-log 90-day sweeping are not requirement expiry. An active record whose original approval log later expires remains a historical confirmed business requirement, not a reusable approval. Its immutable confirmation origin stays in the parent. No silent age-based reactivation, expiry or weakening. Logical removal retains bounded audit provenance as described above; physical deletion follows existing authorized project/parent deletion and backup policy. This issue adds no new global retention service or hard-delete endpoint.

Normal model context and chat exports carry only bounded normalized records, scope identifiers and origin references, with existing private export/access checks. Do not leak raw horizon arrays, unrelated chat text or internal credentials. A full authorized project bundle may retain the existing private parent sidecar only if its current export policy includes that data; do not widen bundle contents as a side effect of this issue. Any copied/restored/imported requirement document is historical/untrusted until current owner/project scope and schema are verified and the user confirms a fresh owned binding. Never activate foreign owner IDs, old generation, tokens or historical approvals from an archive. Export previews must make inclusion of private requirement notes visible through the existing export surface.

Rollback must preserve all typed bytes and audit history. A downgraded/disabled implementation cannot advertise that it enforces records it does not understand. If a bound parent contains enforced typed records and the guard/reader is unavailable, requirement-bearing assistant effects stop with `requirement_enforcement_unavailable`; they do not silently fall back to legacy strings or drop `requirement_scope`. Reads and native manual work retain their normal policy. A feature flag must not turn confirmed enforced records into ignored preferences. Re-enable through schema validation and fresh reads; never regenerate confirmations or reuse old permits. Unknown future versions and corrupt documents fail closed and remain available for authorized diagnosis/export without automatic repair.
