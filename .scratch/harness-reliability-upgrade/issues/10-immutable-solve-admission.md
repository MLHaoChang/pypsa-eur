## Outcome and exact first slice

The user can approve a finite capacity study, leave it running for hours, continue work in another project, and return to an exact native result or an honest stopped/uncertain state. Each physical solve consumes one immutable admitted input artifact on its own isolated candidate. A model cannot infer completion from enqueue success, silently solve subsequently edited inputs, adopt a different queued job, or duplicate an uncertain solve after restart. HH-06 may inspect exact native plausibility evidence, propose a permitted scalar correction and request another separately identified candidate attempt through this seam.

One adapter is enabled: **`isolated_capacity_lopf_v1`**, submitted through the existing `solve_queue_enqueue` shared dispatch and native `SolveQueue` for a saved `capacity_expansion` network. This is a mathematical linear optimal power flow/capacity or dispatch solve. It establishes no AC convergence, grid-code compliance, GFM/fast control, transient stability, hardware behavior, reliability certification or investment recommendation.

The adapter has a closed scope:

- One source project UUID, one explicitly bound parent conversation/task, one frozen reviewed profile, one linear source-to-candidate lineage and one physical native queue solve per attempt. At most **three reserved solve attempts per approved lineage: initial plus up to two correction/rerun attempts**, further lowered by existing task/envelope/HH-06 caps. No parallel candidate branches or automatic parameter search.
- Flat, single-period electrical network; no MultiIndex investment periods, rolling/myopic/multi-period strategy, SCLOPF, AC stage, unit commitment/MIP, user code, external engine, island constraints, library-backed commercial input or dynamic/process study. Native schema/validation remains authoritative. Standard electrical buses, carriers, generators, loads, lines, transformers, storage units, stores and global constraints may be present; nonempty Link/process/multicommodity models are outside this first adapter. Bus power units must be the native MW basis; unresolved commodity/unit basis refuses.
- Full `SolverConfig` is captured, never a partial config or a legacy default. Required values: `solver_name='highs'`, `mode='lopf'`, `solve_strategy='full'`, `solver_options={}`, `extra_functionality_code=''`, `multi_investment_periods=False`, `sclopf=False`, `run_ac_pf_after_lopf=False`, `island_constraints=False`, `commercial=None`, `finance=None`. Nondefault scalar `discount_rate`, `default_lifetime`, `co2_price`, `voll` may be preserved after existing schema validation; they are **frozen**, not tunable by the loop. Preserve the full native goal fields `target_lole_h`, `mc_draws`, `site_archetype` as declared context, with no claim that this LOPF evaluates them. All remaining fields must equal the pinned adapter's explicitly versioned `SolverConfig()` defaults. Generate/check that exact field/default inventory from the dataclass in tests; a new/unknown config field or nondefault unsupported option refuses until the adapter version is reviewed. Never silently discard fields in `_solver_config_from_dict` or let `SolverConfig.__post_init__` lift nested options to change the admitted config.
- Source has no active island/cuts, external dispatch, commercial/library, process/template or other sidecar dependency required to execute/evaluate this adapter. Ordinary `flow_scope.json`/`flow_acks.json` presence is **permitted**, frozen as versioned provenance when HH-09's reviewed IntentContractV1 selects capacity only and the native generic path is proved not to consume them as physics. Normal UI module metadata must not make every otherwise eligible saved network unsupported. The capture/semantics matrix below is authoritative; referenced unknown semantic dependencies refuse. This first slice is a generic electrical capacity network, not every energy-hub/site template.
- A correction is exactly one existing Generator row and a nonempty subset of `{p_nom, marginal_cost}`, matching HH-01's supported scalar shapes, native schema, existing-carrier condition and explicit grant bounds. `p_nom` is configured power in MW, not `p_nom_opt`; `marginal_cost` is native EUR/MWh on the frozen declared cost basis. No name/identity, demand, horizon, weights, topology, outage/goal, solver option, tolerance or currency conversion may change. A correction to fixed `p_nom` must not be described as bounding the optimal capacity of an extendable generator. Corrections accumulate from the preceding attempt's **immutable input**, never from solver-mutated output or the live baseline.
- Requested numeric corrections reject booleans, nulls, non-finite values, unit guessing and native rounding. Native input formats may contain documented infinity sentinels such as an unset unbounded native capacity maximum; preserve their exact native representation in the network artifact, never reinterpret them as JSON `null`, zero or a finite cap. Snapshot/weight arrays must be finite and have their native valid sign/basis. Do not reject native defaults by pretending every native network cell is a user-entered finite scalar.

This is enough for a complete bounded solve→native evidence→permitted correction→new solve loop. Unsupported sources/actions stop with their reason and ordinary native next step. They never fall through to legacy unattended queue behavior while claiming HH-10 protection.

## Schemas, identities and bounds

New envelope-specific helpers are proposed in **`services/immutable_solve.py`**; shared input identity remains HH-01's proposed `harness/admission_identity.py`. Native queue consumes only the validated immutable intent reference/projection and frozen scope, not provider/model logic or a mutable chat summary. Canonical identifiers are `profile_ref=capacity_isolated@1`, `lineage_kind=isolated_capacity_candidates_v1`, `adapter_id=isolated_capacity_lopf_v1`; validate that exact closed mapping.

`SolveAdmission` is frozen, internal and invocation-scoped:

- `version=1`, adapter_id/version; canonical source UUID/registry key and source HH-01 `InputVersion`; owner/organization; parent/thread/generation; task/profile digest/stage/step/attempt/call identity; exact source tool args digest; envelope grant id and revision/digest.
- `lineage_id` (server UUID, one per explicit grant), integer `iteration=0..2`, preceding attempt id/input digest (null for initial), server attempt UUID, server native job UUID, candidate UUID/registry key and ownership marker. These are allocated once and reused for readback, never replaced on timeout/retry.
- HH-02 `requirements_revision`/`records_digest` plus exact evaluated predicate/candidate digest; immutable native goal snapshot and digest including goal fields excluded from the solve fingerprint; immutable config JSON/digest; full source lineage/cost/unit basis descriptors; exact bounded correction rows/digest.
- Input artifact manifest/content digest, exact hydrated candidate-input fingerprint, grant expiry, cancellation generation and finite caps/reserved solve ordinal. Request InputVersion and source identity remain distinct from candidate execution InputVersion; a child UUID is never passed off as the source UUID.

`InputManifest` v1 is closed JSON with schema/adapter and native serialization reader versions; all identities above; source InputVersion; source full config/goal/lineage digests; candidate exact input digest; predecessor input digest and corrections; a **complete ordered allowlist** of files with relative filename, exact byte length and SHA-256; presence/absence flags; full snapshot index/weighting shape/digests; full user-ts row/column/schema digest (including off-horizon values and metadata); creation timestamp and HMAC. The manifest contains no self-referential manifest digest/receipt; compute `input_manifest_digest` over canonical sealed manifest bytes after finalization, then bind it in the external descriptor/DB row. Canonical JSON forbids NaN/infinity; native network special values stay inside netCDF. Reject unknown keys, duplicate file entries, unsafe paths, symlinks/hardlinked writable source files, unsupported schema or directory entries. Manifest is written last using atomic native IO.

Required executable files are exactly `network.nc`, `solver_config.json`, `user_ts.json` (explicit canonical empty object if empty), and a new bounded `goal_lineage.json`. Include generated candidate `metadata.json` as a hashed hydration/identity file, with only the adapter-approved metadata fields and ownership/provenance. Optional manifest-listed `provenance_flow_scope.json` and `provenance_flow_acks.json` contain versioned validated source provenance according to the matrix; their names deliberately do not make them native hydration/routing inputs. They have explicit absence entries when absent, at most 64 KiB each, and cannot be fabricated/defaulted if unreadable. Do not copy arbitrary source metadata, `results_state.pkl`, old `run_evidence`, studies, reports, uploads, scripts, chat history, library references, equipment/control sidecars or hidden directories. Source lineage is data in `goal_lineage.json`, not a rehydrated source study/approval. Store all input files under a private attempt directory; native result files are in a separate mutable work/output directory. No solver writes to the input artifact.

Artifact limits: ≤1 GiB combined executable bytes, ≤8 MiB `user_ts.json`, ≤1 MiB config/goal/metadata each, ≤64 KiB manifest, ≤10,000 snapshots and ≤100,000 rows across static component tables; all limits are checked before publication without allocating an unbounded JSON/string. Existing native tighter limits remain. No truncation. A larger model is unsupported and retains an explicit ordinary native solve path; limits are not expanded automatically because a task runs for hours.


Its owner/thread/task/generation binding is native, not model-provided. `run_id` is existing `run_evidence.queue_run_id(job_id)`. `evidence_manifest_digest` is over the canonical entire sealed native terminal manifest; `output_manifest_digest` binds the saved native output files used by plausibility/retained-results adapters. **ResultScope is constructed only after that terminal manifest is durably sealed and verified.** It is an external consumer/receipt object, never an embedded field that the same terminal manifest or its sections must hash. Missing fields are unavailable, not a request to read the “latest” source/candidate result. A copied/serialized scope grants no ACL, solve admission or numerical publication authority.

Construction uses this acyclic, versioned sequence; implementations must not insert a final ResultScope placeholder, null digest, future digest or iterative fixed-point hash into earlier stages:

```text
InputManifest seal -> input_manifest_digest + immutable SolveAdmission/DB fence
  -> native execution/restoration -> OutputManifest seal -> output_manifest_digest
  -> ResultObservationIdentity v1 + native observations/retained sections
  -> section byte hashes -> terminal run-evidence manifest seal
  -> evidence_manifest_digest -> final ResultScope -> external terminal receipt/DB publication
```

The proposed native **`ResultObservationIdentity v1`** contains the complete ResultScope field list above **except `evidence_manifest_digest`**, plus `version=1`. It binds `profile_ref`, adapter/version, lineage/iteration, exact source/candidate/attempt/job/run, input/exact-input/config/output/goal digests and requirement tuple before native checker execution. Its native owner/thread/task/generation binding is unchanged. `output_manifest_digest` exists at this point; no native checker needs the later evidence seal to observe these verified output bytes. This preseal identity is not a verified-completion receipt and cannot authorize a gate pass, model numerical publication or another solve. Validate equality with SolveAdmission, strict DB fence and sealed InputManifest/OutputManifest before constructing it.

InputManifest and OutputManifest include neither the final ResultScope nor the terminal evidence-manifest/terminal-receipt digest. OutputManifest may bind the deterministic `run_id` and existing attempt/job/claim/input identities without referring to a future evidence seal. Each hashed retained/checker section contains its preseal observation identity and own schema/source/basis data; it excludes the final ResultScope, final manifest digest, section's own digest and later receipt digest. The terminal manifest contains the preseal identity/projection and section hashes, excluding its own digest, final ResultScope and terminal receipt digest; its MAC omits only its own `mac` field as existing native sealing requires. Hash the complete canonical **sealed** terminal manifest (including MAC) after writing/reading/verifying it. Then construct final ResultScope by adding exactly that digest to the already fixed observation identity (dropping its preseal type/version wrapper), and seal/persist an external terminal receipt binding the final scope. No rewrite of a section, OutputManifest or terminal manifest follows this addition. Readers verify the full chain and equality of all shared fields before a numerical gate; a scope/manifest mismatch is unavailable.

Strict publication must propagate key/seal failure: existing `run_evidence._sealed` may log and return an unsealed legacy manifest, which is never sufficient for this adapter. Section/capture/seal/hash/verification/receipt/DB failure leaves computed-unpublished or explicit unavailable/uncertain state, with no verified terminal notification. Recovery may finish this one chain from exact durable bytes/identities without physical re-execution; a conflicting already-published manifest cannot be overwritten to manufacture a new scope. This preserves the existing sections-first/manifest-last native storage pattern and removes any dependency on a digest of the container before the container exists.

Native unique org/name plus immutable prepared identity make a crash-before-projection recoverable by exact owned-row readback; another factory cannot choose a new name/id for this iteration. ## Lock and store order, including capture feasibility

There are three separate bounded native transactions, never a lock transferred across threads:

| Transaction | Exact order and held interval |
|---|---|
| Source capture | Resolve/hydrate/allocate DB child first; source mutation → source solver-state → short netCDF I/O for native save-file reads if needed. Source state copy only. Release before detached serialization. |
| Final submission | Source mutation → source solver-state → parent owner-store transaction → existing task lease sidecar → task RLock → short strict DB transaction. The task lease/CAS must not be taken first and then wait for native/owner locks. Queue bookkeeping occurs only after releasing this hierarchy. |
| Pickup claim | Resolve actor/candidate identities and stable files first; private candidate mutation → candidate solver-state → parent owner-store transaction → short strict DB CAS. Release store/solver-state before solve; native solver later owns only candidate mutation lock. No source lock. |
| Native result serialization | Quiescent private candidate mutation → short global netCDF I/O. No owner-store/task/queue lock, and no registry activation. Publish evidence after releasing native/IO locks. |

All blocking lock/DB pickups have finite limits; use HH-01/native timeout policy and typed busy/refusal rather than wait forever. Never acquire registry/hydrate lock while holding mutation/solver-state/owner store. Never keep queue `_lock` over I/O. Owner-store-only requirement/HH-03 budget transactions never resolve/load a network or acquire source/candidate locks. Store/task paths used together must follow the listed order; review cancellation/revoke helpers for the reverse order. A task update that needs native work must snapshot under its task lock, release it, then enter this admission path and CAS-revalidate. Read-only preparation/proposal cannot hold a project lock while a model/network/approval wait occurs.

The chosen source capture is feasible against the inspected native code: `_network_copy` copies under source ownership without detaching the live solver model; `_save_context` exports under context mutation→IO and can be used on an already-bound private child without registry rekey; `_hydrate_context_from_disk` works off to the side and preserves off-horizon stores. The broad scenario/saved-snapshot walks are deliberately not used as executable identity. `_save_context`'s multi-file writes and tolerant hydrate are wrapped in manifest/roundtrip verification, not assumed atomic. Required complete source config is read under solver-state lock; `update_solver_config`'s protected merge does not acquire mutation inside that lock. Long compute uses only the private candidate's native solver lock, so the user may continue another source/project without an HH-10 global lock.

The original parent run `project_id`, brief and source InputVersion remain the **source**, even when an action executes on a child. Add separate execution identity/ResultScope fields. Never replace task `project_id` or use child hashes to refresh the baseline brief/HH-01 source chain. HH-10 input artifacts form their own receipt-bound candidate lineage; source chain advancement requires a separate actual source mutation, which this adapter never performs.

## Durable row, state transitions and no-replay fence

Extend existing `SolveJobRow`, `SolveJob`, store row serialization and native Alembic/local schema support with nullable versioned strict columns (ordinary rows stay null): `immutable_admission_version`, `harness_task_id`, `harness_lineage_id`, `harness_iteration`, `harness_attempt_id`, `immutable_manifest_digest`, `immutable_contract_json`, `physical_claim_token`, `physical_started_at`, `terminal_receipt_digest`. Contract JSON is bounded sealed native data, including candidate/source and requirement/grant bindings, never a model-authored capability. Use unique constraints on **attempt id** and **(task id, lineage id, iteration)**; retain native UUID job primary key. A proposed migration after current `0010_assurance_record_seq.py` must use the actual next revision/head discovered at implementation; do not renumber existing migrations. Test SQLite and the supported deployment database schema semantics.

The strict helpers live in `services/solve_job_store.py` and return typed committed/not-committed/readback states rather than legacy “best effort normal return.” They must not swallow SQL errors and publish anyway. Exact load failure is unavailable, not no-row/permission to insert another attempt. Frozen fields are immutable; terminal states never regress. Capacity reservation is authoritative in the strict row/attempt set under the task's existing cross-process lease/CAS and strict DB constraints, rather than an unenforced in-memory counter. File/task projection and DB are not one transaction: DB fence is the authoritative submission record, and a missing projection is repaired by exact readback or marked uncertain, never by another enqueue.

| State | Durable fact and allowed next state |
|---|---|
| `preparing` (task attempt, no executable queue row) | Exact iteration/attempt/child allocated; no optimizer. Can become `prepared`, `rejected_before_submission` or orphaned/uncertain preparation. Duplicate factory may only inspect existing identity. |
| `prepared` | Finalized verified input manifest and native candidate gate; still no physical authority. Can become committed queued or rejection. |
| `queued` (strict DB fence committed) | One job id, reserved solve ordinal, complete artifact/config/authority. Can become claimed running, aborted-before-start, stale/unavailable failure. Same exact row may be restored after restart. |
| `running` (strict CAS committed) | One native worker token may call optimizer once. Can become computed/failed/aborted/uncertain/interrupted; never queued again. |
| `computed_unpublished` (strict contract/task observation; queue not verified-completed) | Solver returned and restoration/input checks passed, but native output/required evidence not durably committed. Resume may capture retained native files if exact and quiescent, never re-solve. |
| `completed_verified` (native receipt; queue public completed only afterward) | Exact terminal output/evidence/input/job/attempt tuple is committed and verifies. HH-06 may inspect this ResultScope; numerical policy/engineering plausibility still apply separately. |
| `failed` / `aborted` / `interrupted` / `uncertain` | Preserve exact job and any partial output/error/cancellation. Stops this attempt; no automatic replacement. A permitted new iteration requires HH-06/native reason, remaining cap and fresh admission; unknown prior physical effect blocks continuation. |

Queue public `status` vocabulary may retain completed/failed/aborted/interrupted; richer strict attempt outcome is a separate typed field in the bounded contract/task receipt. Do not report a `computed_unpublished` job as verified completed merely because ordinary queue status is terminal. Implement terminal status publication after required evidence, following existing evidence-before-terminal ordering but making the strict evidence failure observable/uncertain rather than logged-and-ignored.

Cancelled queued work consumes its conservative reserved ordinal unless a separately proven no-start accounting rule is approved; HH-10 does not refund it on timeout/read failure. At most three reserved attempts and two corrections, with current task retry/round/wall caps also applying. HH-03 accounts actual model/reviewer calls separately; native solve seconds and native solve count are not token usage. Expiry/cancel before running CAS prevents new physical work; after native start, use stop event and wait for native cleanup without claiming immediate quiescence. No lease takeover, resume button, new browser session or continuation resets reservations.

## Failure capture, retention, cleanup and rollback

- Error records bind source/candidate/attempt/job/input digest and native phase, with redacted typed message; never include credentials/model code/arbitrary file content. Keep exact unknown/submitted/running state even when notifications fail. Handler JSON cannot mint native receipt, evidence MAC or completion.
- Preparation failure before DB fence can remove only its exact owned staging directory and unsubmitted candidate if DB parent+ownership match, no queue row/worker exists and no user child was branched from it. Record why/what was cleaned. Uncertain existence/readback is not permission to delete. A crash leaves an inspectable orphan preparation; bounded recovery may clean **after 24 hours** only with proven no-fence/no-worker/no-user-child ownership. Never sweep another feature's decision-study forks.
- Once submitted, pin immutable input/output/evidence and candidate ownership until terminal quiescence and HH-06 lineage completion/cancel plus **30 days**. No automatic expiry while queued/running/uncertain or while a persisted pending gate/retained user inspection references the attempt. Cap a lineage at three artifacts and refuse new preparation on storage cap; do not prune old unresolved receipts to make space. After retention eligibility, existing native explicit delete semantics/owned cleanup may remove executable blobs; keep bounded metadata/job/tombstone identity and report `artifact_expired`, never rebuild from baseline. User-branched descendants block candidate deletion; retain the lineage marker or detach explicitly with no restored authority.
- State/evidence/key/DB unavailability fails closed for new strict admissions/pickup, but never cancels ordinary jobs, releases unknown reservations or degrades a strict job into a legacy solve. Rollout flag proposed `PYPSA_GUI_IMMUTABLE_CAPACITY_SOLVES=1`, default off pending qualification. Disabled means HH-06 unattended solve/correction/rerun pauses clearly; ordinary explicit native queue remains available under its own semantics and without HH-10 claim.
- Rollback disables **new** strict admissions. Existing committed queued jobs are either observed/picked up with the same complete adapter version and checks, or explicitly parked `adapter_unavailable` if binary cannot read it; never legacy-fallback. Running jobs finish/abort natively and preserve receipts. Do not clear rows, expire grants retroactively into a duplicate, or cancel background work merely because the UI disconnects.
- Scope is one backend/native queue deployment with the existing durable task lease plus strict DB fences. DB CAS prevents two physical starts for the same attempt even if two processes see it; no claim is made that legacy unmarked native writers are distributed-safe. Adapter never permits concurrent mutable contexts on one candidate; held child, unregistered worker and exact-output publication avoid source/global-state overlap.
