## 1. Outcome and verified boundary

Land two independently releasable slices. **09A is the request/acceptance foundation:** it works for one coordinator using ordinary native stages, including HH-08 artifacts, with delegation absent or disabled. **09B is the bounded worker scheduler:** it consumes 09A and adds evidence without acquiring acceptance authority. Shipping four type definitions alone does not satisfy 09A. Native stages continue to run under their existing gates; new controllers advertised as tracking every requested part must use the 09A store. Legacy tasks stay readable and cannot be upgraded to accepted by inference from their old `completed` status.

One coordinator owns the user's study, decision packet, and authoritative model-change path. It can commission two concurrent workers for scoped research synthesis and parameter proposals. Workers return evidence and suggestions; they cannot edit the shared model, approve anything, contact reviewers, change requirements, widen tools, or spawn children. A future explicitly configured limit of three workers retains the same contract and needs its own release evidence. There is no arbitrary recursive agent tree.

The first production slice is deliberately concrete: two inference workers receive independently serialized, immutable packets of already acquired project/evidence data and have **no tools**. One extracts competing evidence and gaps; the other synthesizes candidate parameters and questions. Packet adapters initially allow ordinary coordinator dispatch of `get_component` for HH-04-supported Generator rows and `get_run_evidence` for explicit completed recorded runs, plus shipped template metadata and supported HH-07 ledger reads. Other source adapters refuse. Live web research, candidate-project execution, and automatic patch application are separate adapters, disabled initially. Do not advertise fresh research when only retained sources were read.

## 2. Shared intent and executable acceptance contract

`harness/decision_packets.py` owns shared strict `IntentContractV1`, `AcceptanceItemV1`, `AcceptanceCoverageV1` and `DecisionPacketV1`. HH-06/07/08 import these definitions; extensions retain shared IDs and schema versions. Intent captures what the user requested, separately from HH-02's native engineering predicates. A chat summary, worker conclusion or successful solve cannot replace it.

`IntentContractV1` contains `schema_version=1`, `intent_id`, monotonic `intent_revision`, canonical `intent_sha256`, predecessor hash, owner/project/parent identity, originating user-turn reference, objectives, requested deliverables, selected scope/cards, source policy, budget-policy references, approval-policy references, requested-part register and `acceptance_items[]`. Store the user request reference and bounded verbatim excerpts so omission can be audited. Every captured requested part maps to at least one stable `acceptance_id`; software checks that structural mapping before work starts. It cannot prove a model extracted every natural-language request: free-text decomposition requires explicit user checklist confirmation before automatic work (§2.3). Ambiguity becomes `needs_user`, never a guessed omission. Only an explicit user instruction supersedes/removes a requested part; retain its replacement ID and originating decision.

`AcceptanceItemV1` contains ID, item revision/digest, requested-part references, deliverable ID, concrete predicate/expected outcome, dependencies, required evidence selectors, frozen checks `{check_id, kind: native|artifact|user_review, adapter_id, version, parameters_digest}`, applicable units/window/basis, and required user-decision category. Checker IDs resolve a closed server registry, never model-provided executable expressions. Unsupported checkers remain unsupported; they cannot become prose checks. Budget and approval references constrain execution, without granting rights.

`AcceptanceCoverageV1` binds `(intent_id, intent_revision, intent_sha256, acceptance_id)` to current state `pending|running|software_passed|needs_user|unsupported|incomplete|failed|accepted|superseded`, evidence/claim/artifact/check receipt references, checker version, source digests, decision reference and reason. These are server transitions: `software_passed` requires the prescribed deterministic checker receipt; `accepted` requires all declared checkers and required user decisions. `superseded` requires an explicit user decision. Evidence loss/revision change invalidates affected closure. Unknown, failed or unsupported items remain visible and block an unqualified “request complete.”

`DecisionPacketV1` carries packet ID/revision/digest, immutable intent reference, coverage rows for **every** item, per-claim/action assessments below, conflicts, remaining decisions and worker lineage. HH-06 study-cycle receipts, HH-07 research entries and HH-08 artifact/acceptance tasks carry the same intent triple and acceptance IDs. Report-specific child schemas may extend fields; they cannot renumber, drop or silently close parent items. Completion is a deterministic coverage-ledger reduction, with explicit partial completion when unresolved items remain.

### 2.1 HH-09A canonical storage and ownership

Persist **one protected `acceptance_v1` aggregate inside the existing parent JSON**, not in delegation records, chat summaries, a new database or an artifact-specific all-done ledger. `services/durable_conversation.py` owns serialization, authentication and the parent commit. New `services/acceptance_store.py` owns the closed acceptance commands; `harness/decision_packets.py` owns strict shared schemas, canonical hashing and pure reducers. Controllers import schemas/reducers and call the store; they never write `AcceptanceCoverageV1` directly. An accounting-only HH-03 parent cannot activate request intent: explicit user request attachment is separately recorded before adding an intent. A standalone HH-08 task obtains that explicit parent attachment before entering this workflow; its operation schema can retain an optional parent for legacy tasks only.

```text
durable_conversations/<thread_id>.json
  ... existing parent, requirements and HH-03 budget fields ...
  acceptance_v1:
    schema_version: 1
    store_revision, store_sha256, next_seq
    intents[intent_id]:
      head_revision, revisions[]: immutable IntentContractV1
      events[]: immutable sequenced command/evidence/check/decision records
      coverage: derived AcceptanceCoverageV1 for every head acceptance item
      packets[]: immutable DecisionPacketV1 snapshots
    request_index[]: command_kind + request_id + payload_digest + result_ref
    task_bindings[]: task_id + intent_ref + acceptance_ids + binding_digest
    projection_outbox[]: task/Activity projection refs + applied acknowledgement
```

The aggregate is the only authority for request closure; native study/report/research records remain authority for their own facts and effects. Native receipts are referenced, not copied into a competing engine store. All IDs except closed adapter/check IDs are server-generated canonical UUIDs. Initial policy caps: 8 intents/parent, 64 items/intent, 32 immutable revisions/intent, 2,048 events/intent and 2 MiB serialized aggregate excluding owned artifact/source bytes. Reject duplicate JSON keys, unknown fields, nonfinite numbers, invalid references and excess depth before hashing; refuse capacity exhaustion without discarding history or treating missing rows as passed. Source bytes and native artifacts stay in their existing owned stores; bounded request excerpts in the aggregate remain after ordinary chat-log retention. Any longer-lived archive is a separate reviewed migration; no automatic compaction removes active obligations.

Existing `assistant_tasks/<task_id>.json` gains a typed protected `acceptance_binding` containing the immutable intent triple, parent ID, acceptance IDs and binding digest. This attachment owns the operational task, never request closure. `bind_task` first commits canonical binding plus projection outbox in the parent, then updates the task using its own CAS; execution is blocked until both exact bindings agree. Recovery attaches that same task once, or leaves an explicit pending/conflict state. No create-on-read, automatic replacement task or claim of atomic two-file commit. Task creation uses its existing idempotent request ID; legacy tasks need an explicit verified attachment and complete requested-part mapping. Generic parent `task_ids` changes cannot remove the canonical binding. Preserve all non-owned parent/task fields on every write.

### 2.2 Source-checked transactions and immutable revisions

All parent read/modify/write entry points, including checkpoint, discussed-run updates, resume/rebind, HH-02 requirements, HH-03 accounting and acceptance, must use **the same** `harness.durable.transaction(project_dir / 'durable_conversations')`. The process RLock and runner lease alone do not provide this guarantee. Migrate each touched writer and test field preservation. Never nest two differently named locks for the same parent authority. 09A extends the existing `_save` atomic temp/write/file-fsync/replace path with bounded no-follow reads and parent-directory fsync where supported; uncertain IO yields `acceptance_checkpoint_unreadable`, never a fresh empty aggregate. A missing `acceptance_v1` is a legacy state, not unreadable/corrupt state.

For supported operations the lock order is project lifecycle guard (§2.7), native project mutation RLock, native solver-state RLock when needed, conversation-directory transaction, then participating process/task/receipt leaf locks. Parent-only commands omit native locks. Acquire current actor/project ACL before this interval and recheck binding/replica and restrictions at commit. No parent/task/leaf lock may be held while acquiring native locks, waiting for a user, calling a provider, rendering or taking an unrelated store transaction. `resume_episode`/`rebind_scope` currently call `_revoke_checked_episode` under the parent RLock; it enters `network_guard`. Refactor that native/session work before the parent transaction, then CAS the captured generation; a race refuses conservatively rather than entering native locks under a parent lock. Likewise split task/envelope callers that currently acquire a task lock before native fingerprint reads. Do not make a parent call from their locked callbacks. No distributed native safety is inferred: 09A/B initially retain the existing one-authoritative-application-worker deployment restriction.

Each modifying command supplies `request_id`, exact `(expected_store_revision, expected_store_sha256)`, `expected_parent_generation`, and current intent triple when addressing an intent. Under the one parent transaction, reload disk, check all expectations, validate the command, append one monotonic server `seq`, run the reducer, compute canonical digest and persist once. Hash canonical UTF-8 JSON with sorted keys, fixed separators, finite JSON values and no timestamps generated inside the hash function. `intent_sha256` excludes only its own digest and covers identity, revision, predecessor hash, requested-part map, policy refs and frozen items/check parameters. `store_sha256` excludes only itself; packet/check/decision digests similarly exclude their own digest field. No Python `repr`, unordered sets or fresh timestamps during reduction.

Idempotency key is `(owner, project, parent, command_kind, request_id)` with payload digest including expected bindings. Check a retained matching retry before stale-CAS refusal, after current ACL/replica checks: return the recorded historical result without reapplying it or restoring authority. Changed payload gives `acceptance_request_conflict`. Two different requests racing one expected revision yield one commit and one `acceptance_stale`. Metadata/budget writers preserve the acceptance aggregate; a budget-only update does not change `store_revision`. Acceptance never resets budget counters, parent generation or engineering requirement revisions.

### 2.3 Intake, requested-part mapping and amendments

`create_intent` ingests an owned explicit user request, not a model's summary. Retain server-authenticated origin (actor, episode/turn or direct UI action ID, content digest and bounded verbatim excerpts), and a requested-part register with stable `requested_part_id`s. A model may propose decomposition and checks; it cannot attest its own completeness. Admission requires a nonempty mapping for **every registered requested part**, all deliverables represented, valid acyclic dependencies, nonempty supported deterministic checks or an explicit user-review requirement, and fixed check IDs/versions/parameter digests. Missing/ambiguous coverage refuses execution with `acceptance_mapping_incomplete` or records `needs_user`. Structural mapping checks cannot prove arbitrary natural-language completeness. For every free-text intake, show the bounded original user text alongside the proposed complete checklist and require explicit user confirmation before automatic operation; every unclassified or ambiguous fragment remains `needs_user`. A native feedback form with server-known comment IDs may bind those IDs directly without model extraction, but must preserve each submitted comment and its one-to-many obligations. Do not advertise automated semantic completeness.

Only the authenticated user-origin intake/amend decision path may add, replace, withdraw or weaken requested obligations/checks. A worker/controller can submit a proposal but cannot commit that command. `amend_intent` appends revision N+1 with predecessor hash and decision ref; no in-place edits. Require every prior requested part and item to be retained unchanged, explicitly replaced with successor IDs, or explicitly superseded with the user's exact withdrawal/replacement decision. A removed row, changed predicate, changed required checker or narrower source/window/basis without that decision refuses `acceptance_scope_change_requires_user`. Unchanged items retain stable IDs and item digests; changed predicates get a new item revision/digest, preserving lineage. Requested-part IDs are never recycled. Later feedback and new artifact comments append to this register before work.

All coverage references bind the new intent triple. Old receipts/decisions stay historical and do not silently transfer to a new revision, even if source values change and return. An unchanged-item deterministic result may be reused only by explicit native revalidation that issues a new receipt binding the new triple and original evidence; user sign-off never carries forward automatically. Superseded obligations remain visible with their originating decision and successor links. Ambiguous new comments cannot weaken prior checks. HH-02 engineering requirements and native asset-sizing DesignIntent keep their own revisions and semantics; this mapping adds no permission to change either.

### 2.4 Evidence append, checker receipts and deterministic reduction

`append_evidence` accepts only a closed registered controller adapter and typed native receipt/source reference bound to task, attempt, intent triple and item IDs. Resolve the actual owned native record and digest server-side; caller-supplied `passed`, confidence, actor, time or authority is never authoritative. Worker claims enter as untrusted evidence proposals until a native adapter validates their exact sources. Identical adapter/receipt/digest appends deduplicate; conflicting content for one native receipt ID refuses and records a conflict. Append-only invalidate/supersede events replace updates/deletions of evidence. No evidence event alone closes an item.

`run_check` resolves frozen `adapter_id/version/check_id` from a closed server registry, reads the exact evidence/artifact versions, and executes code independent of generator output. It emits `CheckReceiptV1` with server receipt ID, intent triple, item revision/digest, frozen check/parameter digest, source/artifact/task/attempt refs, checker version, observed verdict `passed|failed|unavailable`, bounded measured facts, dependency digests and check time. Registry entries identify owning subsystem; 09A ships structural/mapping/source-binding checks, while HH-06/07/08 register their own native checks in their respective slices. No arbitrary executable expressions, callable uploads, client receipt-submission endpoint or qualitative reviewer `passed` certification.

For mutable native inputs capture the check observation and identity together under the source's defining native locks, and commit the receipt under the nested parent transaction before releasing those locks; no late rehash of a newer state. For immutable native artifacts validate their exact bytes/manifest under the owning read contract, release artifact leaf locks, then commit by parent CAS; re-read exact availability at closure/action. If a source/check adapter cannot provide this source-binding contract it stays unavailable. Slow checking/rendering occurs on immutable private snapshots outside parent locks; the short commit rechecks identity. Check crashes/timeouts produce unavailable/pending, never a pass.

`reduce_coverage` is a pure fold of the immutable intent and sequenced committed events. It emits exactly one row for every current and superseded item; duplicate/missing/foreign item refs refuse. Precedence is explicit: user-authorized supersession → `superseded`; missing/stale required evidence or uncertain unfinished effects → `incomplete`; unsupported mandatory checker → `unsupported`; current failed required check → `failed`; active admitted work → `running`; incomplete mandatory checks → `pending`; all mandatory checks passed with outstanding judgment → `needs_user`; all checks passed without outstanding judgment → `software_passed`; then a server closure event with the full check set and applicable exact user decision yields `accepted`. Newly created untouched items are pending; invalidation events identify affected items and retain historical passes. User rejection/change requests yield needs_user/new revision as appropriate, never accepted. A user decision cannot override a failed, unavailable, security or required factual check. Empty/vacuous check coverage cannot pass.

`build_packet` and `close_items` operate through the same store without requiring a delegation ID; worker lineage is empty for ordinary stages. Packet snapshots include all coverage rows, evidence/check/decision refs and a coverage digest. `close_items` revalidates source availability/current bindings, all frozen checks, decisions and absence of uncertain effects, then appends closure once by CAS. The request view reports complete only if every current required item is accepted and every supersession has a valid explicit user decision with required successor coverage. All-superseded is a visible withdrawn outcome, never completed work. A delivery receipt, native job success, operational task completion or missing row cannot establish request completion. An inspector's side-effect-free freshness projection may downgrade a formerly accepted item to incomplete when source retention/drift is detected; it cannot certify current acceptance from stale cached coverage. Persist invalidations on the next explicit reconciliation, and always revalidate before an actionable close/apply.

### 2.5 Review receipts, user decisions and authorization boundaries

`prepare_review` commits `ReviewReceiptV1` binding the exact packet/coverage digest, intent triple, selected item revisions, artifacts/digests, source/check receipts, displayed choices/consequences, parent generation, actor, `purpose=intake_confirmation|item_acceptance|intent_amendment`, optional frozen amendment payload/digest, and expiry (ten minutes initially). Intake confirmation and amendment approval record user scope decisions; they cannot close pending acceptance checks. It is a preview snapshot, not approval; a random opaque review ID references server-owned bytes. Persisting it precedes enabling the decision control. `record_user_decision` accepts only that server review ref plus `accept|reject|request_changes|supersede` and bounded user text from a dedicated authenticated user UI route, outside model-callable tools. Resolve current actor from authentication; no `by=user`, boolean `user_origin` or pasted token can confer authority. Verify exact displayed target, all expected CAS bindings, expiry and item/artifact/check freshness. A stale preview refuses `acceptance_review_stale` and presents a new diff. Initial authority is the owning user; a collaborator cannot sign for that user without a separately reviewed actor-policy extension. Imported comments, generated prose and worker output cannot impersonate this route.

Persist `UserDecisionV1` with immutable server ID/digest, actor/project, exact review/packet/item/artifact refs, verdict and the originating authenticated action. Its parent commit is canonical; Activity/chat/approval-log mirrors use the outbox and cannot create a decision. Chat-origin explicit amendment proposals still require a server-recorded user request or this displayed checklist decision; if event history cannot durably establish origin, refuse rather than trusting model text. Generic checkpoints cannot replace request origin or decision records. Human acceptance establishes the stated judgment only, never engineering certification.

Acceptance, grant and operation receipts are separate references. Decisions to accept a report do not authorize model writes, exports or publication; generation/claim/packet refs do not grant anything. Store only references to existing envelope/card approval receipts and HH-08's narrowly scoped copy-revision grant; their native owner remains authority. `route_action` re-reads the current native grant, restriction and requirement revision, fields/bounds/expiry/quota and exclusions at admission and again at native commit. Revocation and authorization-required pickup serialize under the same native grant/task lock after the parent guard; the grant owner increments a monotonic revision/fence. If revoke wins before effect intent, no effect; if the already admitted operation wins, retain its precise receipt and honor the stop fence at the next safe boundary. No lock is held while awaiting the user's decision. A recorded old acceptance is historical after grant revocation; it can never rearm an action, reset consumption or restore a revoked grant. Policy changes cannot waive mandatory user review by rewriting coverage.

### 2.7 Recovery, deletion and rollback

Parent replacement is the commit point. A crash before it commits nothing; after it, an idempotent retry returns the same immutable refs and reduction. Parent fsync uncertainty refuses new work until exact disk reconciliation, without a new request ID as an escape. Outbox replay may repair task/Activity projections by their exact bindings only and never rerun native checks, inference or artifact effects. Resume/rebind retains intent revisions and consumed resources but invalidates generation-bound actionable review/grant refs; it requires current source/policy revalidation before new work. History reset/compaction and generic task cancellation satisfy no acceptance item. Cancellation appends an execution fence and leaves unresolved items visible; it is not withdrawal.

Deletion needs an explicit participant, because the baseline delete route only guards solves. Add `harness.durable.project_lifecycle_guard(project_registry_key)` using the existing bounded file-lock primitive on a hashed stable lock path under `<app data>/project-lifecycle-locks/`, **outside** removable project storage. This is a mutex, not a new persistence authority. Acceptance/parent/task writers for bound work, delegation writers and native project delete/rename acquire it before native/parent locks; cascade operations acquire project keys in sorted order, never a child lock after a parent transaction. Resolve current registry row/ACL and existing project directory again inside that guard before opening the parent transaction (which currently can `mkdir`). Never recreate a missing/deleted project from a stale captured path. Do not use `hydrate_or_adopt` as this guard: its resident fast path deliberately takes no lock.

Delete refuses `acceptance_lifecycle_busy` while a bound task, unclosed native operation, live/straggling worker, pending projection or unsettled HH-03 reservation can still write/settle. User cancellation alone is not proof those are absent. Once quiescent, normal authorized deletion holds the stable guard through storage/registry removal; retain no secret orphan acceptance DB. A waiting writer re-resolves and returns not found after deletion. A partial delete leaves the remaining record unavailable and cannot trigger replacement records. Rename preserves project UUID and re-resolves its new directory under the same guard. Normal native project restore/undo cannot silently import accepted state or grants: a restored acceptance record is historical/unvalidated until explicit current-owner/source revalidation; model charges and revoked grants never roll back.

The guard is per project, bounded and held only over owned metadata IO or the native deletion/rename critical interval. Resolve/hydrate contexts before entering it; hold it across neither inference, solve, rendering, user wait nor network contact. Every protected writer enters it at its outer entry, never from a task/receipt callback already holding a leaf lock. `durable_conversation._save`, protected `assistant_tasks._save` and delegation save helpers require an existing authorized registry row/directory and the matching held guard; they cannot call ensure/create from stale paths. Explicit new parent/task creation rechecks the existing project under the guard; it does not create project storage. The implementation audit must cover parent create/checkpoint/resume/rebind/discussed/accounting/requirements writers; task create/runner/continuation/cancel/envelope writers for acceptance-bound tasks; project delete/cascade/rename; restore/import; and any retention/GC entry that can remove referenced parent/task storage. Add no automatic acceptance GC. Untouched legacy tasks preserve their native behavior, but any legacy writer reaching a protected acceptance binding must use this guarded path or refuse it.
