# HH-07 — Verified research and user-approved parameter proposals

Status: needs-triage
Type: detailed implementation specification; documentation only in this commission
Baseline: `master` `60d8332d64b2edef1b204fb5980311e6102229a8`
Depends on: study-harness 09 and its 04/03 prerequisites; HH-01/02/03/04/05; HH-06/08/09 for integrated journeys; HH-10 before automatic solves

## User outcome and boundaries

The owner can ask the study assistant to research a missing parameter, inspect traceable candidate values and ranges, choose a value, approve an explicit old→new card and continue the native study. The report retains what was searched, what the sources actually said, which assumptions remained uncertain, what the owner selected and which results used that selection. The assistant may explain options; it cannot turn a plausible-looking citation into verified engineering truth.

This completes the interface of existing study-harness [09 research step](../../study-harness/issues/09-research-step.md) and design §8. It does not introduce a general browsing agent, background literature crawler, new research mode or direct model-write path. Use the existing profile's optional research capability, source ledger and run card. Existing five workflow cards remain capacity, grid, control, reliability and commercial. A profile declares research questions separately from optional exact native application capabilities. Choosing a workflow card alone grants neither search nor domain coverage.

Source verification means the server retrieved the cited resource and matched the quote to retained content. It does not establish that the author is correct, current, representative, applicable to this site or independently validated. A source ranking and a provider's self-confidence cannot certify a value. Research does not change native plausibility rules, HH-02 constraints, solver settings or the scientific question to obtain a pass. Objective improvement after a researched price change is a changed assumption, not a better physical design.

### Concrete first application: electrical datasheet capacity at setup

The proposed registration is `id=generator_p_nom_datasheet`, `version=1`, `gap_id=generator.electrical_nameplate_capacity`, `stages=[inputs]`, on HH-06's new `profile_ref=capacity_isolated@1`. Its proposal data are `context_kind=native_observation`, `context_reader_id=generator_p_nom_native_v1`, `proposal_unit=MW`, `basis_schema_id=electrical_nameplate_mw_v1`, `allowed_source_kinds=[fetched_web,uploaded_document]`, `source_ledger_version=1`, and the applicable R01–R31/HH-05 qualification references. Activate this proposal entry with `application` absent until the exact composition below qualifies; its proposed application metadata is not a claim of current availability. It is an **optional explicitly requested setup research question**, not an invented readiness failure or a replacement for native `project_readiness`. Existing `eh_site@1` research remains disabled unless separately activated. `explore` remains skipped for this capacity profile; the general stage-6 rule below does not enable it.

The initial application scope is `setup_before_isolated_grant`: one owned saved source project and one existing non-transient fixed Generator, before any HH-10 candidate lineage/grant is active. There is no research-triggered creation, deletion, rename, bulk edit, `p_nom_extendable` change or candidate write. Require `p_nom_extendable=false`, no process-role semantics, an existing bus with `carrier` exactly `AC` or `DC` and explicit native `unit=MW`, and the Generator carrier blank or already present as HH-01 requires. This deliberately excludes thermal/material buses, ambiguous units and extendable-capacity interpretation. Existing schema/card/native checks remain decisive.

The proposed `target_reader_id=generator_p_nom_native_v1` maps to existing `services/chat_tools.py:get_component(component_class="Generator", name=<exact name>)`, which reads `n.generators.loc[name]`; also read the exact `Bus` row through `get_component` to establish the electrical-unit precondition. Capture HH-01 `InputVersion` and HH-04 component identity together under their existing bound-context lock rules; model-visible row JSON alone is not a fresh revision guard. Field identity is exactly `Generator.p_nom`, native unit exactly `MW`, with the installed active-power meaning in `services/asset_schema/fields.py:GENERATOR` and finite-number schema in `models/schemas.py:GeneratorCreate`. Never read `p_nom_opt` as the old value or write it as the candidate. An equipment rating is an input assumption, not an optimized plant size, required capacity, dependable capacity or design recommendation.

The proposed `effect_adapter_id=generator_p_nom_explicit_card_v1` is a registry reference to the existing `update_component` route/card integration, not a new setter. Exact tool shape is `update_component(component_class="Generator", name=<same exact name>, attrs={"p_nom": <positive finite MW scalar>})`, with no `new_name` or other attributes. Existing routing is `services/chat_tools.py:update_component` → `_validated_update_payload` → `routers.network._update_component` (re-export of `services/network_crud.py:_update_component`). The GUI's corresponding native route is `PUT /api/network/generators/{name}`; use the shared chat dispatcher/card path for research instead of calling that route as a card bypass. `harness/edit_card.py:_update_component_preview` runs that same native handler on a private copy and `_component_readback` reads actual native fields; preserve complete old→new/derived rows and exact readback. Preserve native provenance, series, identity and partial-update behavior.

`basis_schema_id=electrical_nameplate_mw_v1` requires the exact equipment/model and owner-reviewed mapping of that equipment to this one Generator, one-unit scope, electrical output basis, stated rating/duty and applicable operating conditions, with source version and quoted numeric/unit evidence. Only a source already stating the selected electrical output rating in MW is eligible for this initial application. kW, kVA/MVA, mechanical/thermal/fuel input power, a fleet total, unknown net/gross or duty basis, ambiguous model variants, and synthesized capacity sizing stay proposal-only; no multiplying unit counts, power-factor/efficiency conversion or implicit derating. A range may be retained but cannot enter this scalar route until a separately verified exact rating has been selected. Currency and money year are inapplicable to this adapter, never fabricated.

HH-01 Phase A excludes researched values from unattended envelope admission. Keep that exclusion. Initial application activation therefore additionally requires source-checked qualification of the **existing explicit-card route** using HH-01's same native worker identity/requirement validation/write/readback boundary for this exact shape, with a fresh ordinary confirmation as its authority. Do not present current envelope-only coverage as already providing this composition, create another `MutationPermit` type, call `effects.execute` and an ordinary reservation for one operation, or advance an envelope chain from the researched edit. If this explicit-card composition is unavailable, the registration still delivers proposals and application remains unsupported.

After successful setup application, capture the changed source `InputVersion`; re-run native input checks and require a newly reviewed brief/requirements binding and HH-10 isolated-lineage grant before any candidate preparation/solve. During an active isolated lineage, research can produce proposals only. Applying a setup value then requires an explicit user decision to leave that lineage, revoke unstarted authority and confirm a current source-target setup card; already submitted/uncertain jobs retain their original identities and liabilities. This is a new setup decision and future lineage, never mutation of a sealed candidate or automatic continuation of the old cycle. Preserve shared parent/task/day budget holds, unresolved work and historical acceptance/source/result IDs across that decision; creating a new lineage grants no refund, duplicate spend allowance or reset of unknown effects.

Activation handoff names these actual read/write/card symbols plus exact adapter versions/digests, qualification IDs and observed native receipts. A proposal-only release may complete its declared research deliverables without native application. An applied study release needs all native gates for its approved question; missing adapters or unresolved required acceptance items remain incomplete. One supported scalar cannot establish all-domain research application or capacity optimization.

## Research-stage request and offered subset

Consume HH-06 `StageRequest` rather than define a competing task protocol. Add a typed research payload: exact `gap_adapter_ref` version/digest, `intent_ref={intent_id,intent_revision,intent_sha256}`, `acceptance_ids`, reviewed question/context, optional exact native observation/reference and its current-value provenance, proposal unit/basis, allowed source kinds, previously inspected source/proposal refs and HH-03 budget scope. Native target/unit/InputVersion are mandatory only when the request declares a qualified application. Absence is explicit; do not invent a field/old value for a proposal-only question. Package instructions stay in `harness/workflows/profiles/`; changing content stays logged per-turn data.

Research is allowed only at input stage 2 for registered gaps and explore stage 6 for approved sourced ranges. It never runs silently during a correction round or ordinary chat. If the owner asks for a new research question mid-cycle, pause and prepare the separately scoped research stage; reruns await its outcome. Stage 6 follows the existing at-most-four case cap; a source range cannot create unlimited exploratory solves.

The exact offer is registered read-only native tools plus provider-neutral search/fetch capability and one source-ledger proposal operation. No `update_component`, tariff application, ledger application, solve, shell, external MCP or arbitrary network client is offered. Source-ledger proposal writes append research metadata only, never project inputs. It is not a general catalogue write tool. Validate actual provider offers and dispatch membership, not merely prompt instructions. A malicious fetched page cannot expand tools or invoke another stage.

New typed outputs are `ResearchFindings`, `ParameterProposal` and `ResearchUnavailable`, each with stage/request identity. `ResearchFindings` lists source refs, conflicts, missing basis and applicability limitations. `ParameterProposal` references exact verified source rows, a candidate scalar/range, proposal unit/basis, optional observed target, assumptions, short reason and unresolved conflicts. Server-owned capability projection separately declares application available/unavailable and its reason; a model cannot assert it. `ResearchUnavailable` gives capability/budget/source reasons. None contains `approved`, authoritative confidence, native pass or a write instruction. The server validates all outputs and records raw malformed output as rejected, charging actual calls.

If a provider lacks supported search/fetch, return `not_available`; keep existing user/default inputs explicitly labelled and list the gap. Never silently replace a missing search tool with fabricated links or a model-memory value. A user can supply a document as an explicitly uploaded source with its own integrity/provenance rules; it does not become a fetched URL source automatically.

## Verified source ledger and schema

Extend existing study-harness `SourceRow` to version 1 typed records in the task-owned research artifacts. Reuse HH-06 history identity and owned storage transactions. Models submit source proposals; only server retrieval/verifier code writes verification fields. Keep append-only revisions so later fetches cannot rewrite a quote used by an earlier result.

```text
FetchedSource v1 = {
  source_id, revision, stage_request_id, provider_attempt_ref,
  kind: fetched_web|uploaded_document,
  requested_url?, resolved_url?, title, publisher?, author?,
  published_at?, document_version?, effective_period?, fetched_at,
  content_sha256, retained_content_ref, locator_kind, retrieval_status
}
SourceRow v1 = {
  row_id, revision, gap_adapter_ref,
  intent_ref: {intent_id, intent_revision, intent_sha256}, acceptance_ids,
  question_ref, target_ref?, observed_input_version?,
  source_ref, quote, quote_locator, quote_match_status,
  value, value_type: scalar|range, unit, basis,
  applicability, uncertainty_reasons, conflict_group?,
  verification: verified|unverified|unavailable,
  status: proposed|confirmed|rejected|superseded,
  proposal_ref?, confirmation_ref?, applied_receipt_ref?
}
```

`basis` is a gap-adapter-specific closed object, including physical commodity, input/output basis, location/market, time coverage, technology scale and, for money, currency, price year, nominal/real basis and tax/inclusion assumptions. Missing fields remain explicit unknowns; do not populate them from title, current date or locale. Distinguish document publication date, effective tariff period, fetched date and monetary price year. A current page can quote a historical cost.

For web records the requested URL must come from an actual admitted search/fetch in that research request and the resolved URL/redirect chain from retrieval receipts. A search snippet alone is a snippet source, not proof of a full document quotation. Verify quote text verbatim against the retained decoded content with the recorded extraction version and character/page/table locator. Deterministic line-ending/Unicode normalization, if used, is recorded with original bytes and never changes numbers, signs or units. Retain content digest and bounded excerpt needed for audit; use existing spill limits for large content and refuse unsupported extraction rather than make up a quote. Quote length remains the existing at-most-400 characters. Matching a quote does not prove its numeric interpretation: store the quoted numeric/unit evidence and verify the structured value against the registered extraction/interpretation contract, otherwise mark it unverified for application.

Do not fetch an arbitrary model-supplied URL merely to retroactively legitimize its citation. An unverified URL/quote may be displayed as an unverified lead, with no “sourced” badge and no eligible researched-value application. Broken, unavailable or access-restricted content stays unavailable; no invented DOI, publisher, page, date or URL. Retrieved instructions are fenced data and cannot alter confirmation, privacy, tool policy or budgets.

Ranges carry both endpoints, exact units and stated basis; the assistant must distinguish a source's range from its own synthesis or recommended scenario. A synthesized range lists every contributing source and method/limitations; it never masquerades as a direct quote. Contradictory sources remain separate records with a conflict group and reasons such as region, date, scale or unknown basis. No hidden average, newest-wins rule or cherry-picked low endpoint is introduced. If the sources cannot be reconciled, the owner sees the conflict and may explicitly select a labelled assumption or defer; no default resolution from model self-confidence.

## Approval, native effect and audit lifecycle

Researching, choosing and applying are distinct durable events. The source card shows candidate value/range and unit/basis, question/context, quote/link/version, uncertainty/conflicts and expected affected study stages. Show exact native target and old value only from an owned observation, currency/price year only for money, and the server's application availability/reason. Proposal-only selection/rejection records the research decision without generating an unusable native card. A range is never written to a scalar field: the owner chooses a qualified exact scalar or explicitly approves an existing bounded scenario set under that set's own adapter. Recommendation text must not conceal the range or conflicting evidence.

For an application-qualified setup target, selecting a scalar and explicitly requesting its application prepares an ordinary old→new edit card, preserving server-owned provenance even if downstream tool arguments have no `research_*` field. A source-derived value always requires explicit user confirmation regardless of envelope, magnitude, prior approval of a similar value or whether the value equals an existing default. Approval binds gap/application adapter version and digest, source revisions/digests, proposal revision/digest, exact source project/component UID and HH-01 InputVersion, units/basis, requirements revision/digest, intent tuple/acceptance IDs and complete preview digest. `approvals.asked/decided` is the durable audit receipt. A Choice click can select a proposal; it cannot stand in for native edit confirmation.

Before applying, fresh ACL/restrictions, source integrity, current target, schema, profile/adapter identity, intent and requirements are rechecked, then the qualified HH-01 explicit-card composition validates the actual native candidate and captures effect/readback inside its worker boundary. Exact baseline equality is required across every InputVersion field, including residency/revision after edit→undo or identical reload; matching `p_nom` alone is insufficient. Renamed/replaced/deleted equipment, changed bus/unit/extendability, source/proposal/requirements/intent revisions or an active isolated-lineage grant require stale/unsupported refusal before the handler. Never find a same-name replacement, rebase to latest inputs/source, inherit the old approval or silently prepare a new card. If qualification or required coverage is absent, retain proposal-only. Unit mismatch refuses: v1 adds no implicit currency, money-year, annualization, percent or energy conversion. A separately qualified native conversion must show inputs/formula/bases and require a new user card; no model arithmetic can supply authority. Changing a price year without an actual conversion never turns historical money into current money.

Ledger `confirmed` means the user selected that research assumption; native `applied_receipt_ref` separately establishes whether the field was actually changed. A failed/uncertain write does not become applied because confirmation succeeded. Rejected rows remain rejected; superseded source/proposal revisions stay inspectable. On success record the exact native receipt, then invalidate affected readiness/results through existing native behavior. Enter HH-06 only after fresh gates and the new reviewed source/grant specified above; every automatic initial solve/rerun consumes [HH-10](10-immutable-solve-admission.md) immutable attempt/job/input/evidence tuple. Research during an existing lineage never writes its source or candidates. No forced shared mutable physical network or unsupported engine worker is authorized.

Complete audit includes request/acceptance identity, query and actual offer, source retrieval receipt, content hash/excerpt/version, proposed value/unit/basis, conflict and uncertainty notes, user decision, edit-card receipt, native input before/after, resulting exact jobs/results and budget reservations/settlements. Store short justifications, never hidden model reasoning or credentials. HH-09 DecisionPacket preserves unresolved research and human-review acceptance items; HH-08 exports the same source/proposal revisions with the same acceptance IDs. Reuse coverage states `pending|running|software_passed|needs_user|unsupported|incomplete|failed|accepted|superseded`: source verification can pass only its exact software checker, and user assumption approval closes only its designated decision item. The broader study requires all prescribed checks and decisions. A report claim cannot upgrade “user-approved assumption” to “independently verified parameter.”

## Budgets, background work and recovery

Use existing `research.cost_cap_eur`: EUR2 default, user raisable up to EUR10 hard cap. Enabling research does not raise the overall run budget. Each search, fetch and inference physical send needs HH-03 `PreparedCall`/`CallBounds`, purpose attribution and durable reservation before send, including fixed search charges where applicable. A provider offering search without a conservative bound or complete supported usage categories is unavailable for strict monetary admission. Token-only metering cannot certify the search cap. Unknown usage retains the reservation and stops further covered calls.

HH-03 currently forbids implicit FX; honor that canonical rule. A provider billed in another currency is unsupported for strict EUR research until a separately reviewed pricing adapter supplies the explicit source/rate/date/bound contract required by study design. Do not smuggle FX into this ticket or compare USD floats to EUR. Provider-rate facts are not researched model-input assumptions and do not belong to this source proposal workflow.

Research runs on the existing server runner under explicit owner/project context while the owner uses other activities or closes the browser. It shares the original run wall deadline, not a browser timer. Waiting for approval does not pause expiry. Only independent stages that do not read the unresolved values may continue, with dependency IDs checked natively; stages needing them stay `needs_user/research_confirm`.

Persist request/reservation and retrieval identities before sends. Recovery follows matching durable receipts; it cannot automatically resend an unknown charged request. Search results returned late append once under the original attempt. Resume revalidates access, source integrity/expiry if an adapter declares one, target drift, profile/requirements and remaining budget. A source's changed remote page cannot overwrite a retained prior source revision. Missing retained content requires fresh retrieval/new revision and review, not silent refresh under old approval. Pause/stop revokes live application cards and prevents new research admissions; completed research and rejected proposals remain history. Browser reconnect cannot recreate approval or clear unknown spend.
