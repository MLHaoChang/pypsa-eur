## Problem and acceptance claim

An envelope-controlled edit must compare its expected input identity and perform its native mutation while holding the **same existing project mutation lock**, on the thread that invokes the synchronous handler. Its verified after-identity must be captured before releasing that lock. The existing solver-state lock is also retained in its established inner position for this bounded transaction, because the fingerprint includes solver configuration and its native writers use that lock. A concurrent edit outside that interval must never become the envelope's own next chain link.

The pinned README explicitly describes the current limit: a user edit during a step can enter the envelope freshness chain because the runner releases its locks before the handler takes its own. This is a documented design boundary; this specification does not claim a newly reproduced exploit. The research audit and assessment identify this as the first P0 integration slice:

- `.scratch/harness-research-2026/source-notes/current-harness-audit.md`, item 8 in the research checkout `/workspace/harness-research-2026`.
- `.scratch/harness-research-2026/assessment.md`, prioritized roadmap item 1 in that checkout.
- `pypsa-gui/backend/harness/README.md`, “The approval envelope”, especially the paragraph beginning “Known limit”.

Phase A's claim is deliberately bounded: the exact synchronous operations in the next section have atomic admission and settlement against cooperating native writers in one backend process. It is not a claim that every envelope edit, every async solve, arbitrary disk writes, or distributed writers are protected. The UI/Activity description and release note must use that bounded claim.

## Phase A: exact operation coverage and safe exclusions

The first slice covers precisely **one existing tool**, `update_component`, with these request shapes:

| Field | Admitted shape |
|---|---|
| `component_class` | Exactly `Generator` |
| `name` | One existing, non-transient Generator instance already matched at grant |
| `attrs` | A nonempty dictionary whose keys are a subset of `{p_nom, marginal_cost}`; therefore the three shapes `{p_nom}`, `{marginal_cost}`, `{p_nom, marginal_cost}` |
| Values | Finite native numeric values accepted unchanged by existing schema/card/native validation; booleans, nulls and non-finite values refuse |
| `new_name` | Absent or `None`; an explicit rename, including `attrs.name`, is outside the slice |
| Native precondition | Generator's existing `carrier` is blank or already exists in `n.carriers`; otherwise generic CRUD would implicitly create a Carrier, which is outside this slice |
| Other arguments | Only existing catalogue arguments; no admission object, expected revision, envelope id or fingerprint is accepted from the model |

The exact two fields are a minimal useful subset already used by `tests/test_harness_envelope.py`'s granted envelope and existing generic CRUD path. This is not an alternative schema. Existing tunable restrictions, complete typed card, grant-time instance membership, at-grant relative bounds, value validation, project arguments, research exclusions and current native safety checks remain mandatory. A card that declares any creation/removal, unsupported typed field or incomplete/unresolved target refuses even if the arguments superficially match. Existing derived rows must still pass native readback. Native side effects are those of the existing update implementation; this ticket provides atomic admission, not rollback of a remove/add handler that fails partway.

Every other tool or shape is **unsupported for unattended Phase A execution**, including other `update_component` classes/attributes, bulk edits, time series, settings/sidecars, create/delete/rename, `apply_project_changes`, and all three currently listable async run tools: `run_simulation`, `run_ac_pf_stage`, `solve_queue_enqueue`. `run_sensitivity_sweep` and `run_eh_study` remain never-listable. External tools, destructive actions, grid-code publication and researched values retain their existing refusals/cards.

Do not reject a whole existing profile merely because it lists a future shape. Validate its existing structure as today, but expose the Phase A limitation in its plan-review detail. At dispatch, an unsupported unattended shape records a typed `envelope_atomic_unsupported` refusal, pauses the run before dispatching that handler, and offers the existing explicit step/card route. No automatic fallthrough from an envelope refusal may execute an unsupported write without a user click. A user may elect stepwise operation with ordinary policy and receipt behavior. Such a step does **not** advance the atomic envelope chain; the old unattended grant stays suspended, and unattended continuation requires a fresh explicit grant on a current brief. The changed input must not be silently claimed by the envelope after an explicit card either.

Read-only tools keep existing dispatch policy and never advance the input chain. Existing uncarded task/control steps may not be used to absorb input drift: retain the pre-step drift check, and remove generic post-step chain advancement for them. `continue_at_card` is a recorded decision, never a mutation receipt.

## Native admission data and durable format

Add one shared frozen input-identity value/helper in proposed new `harness/admission_identity.py`, and the small envelope-specific frozen data classes/helpers in existing `services/run_envelope.py`. The proposed names below are new symbols, not claims that these functions already exist. Do not add a framework, public tool, new endpoint, user-supplied bearer token or separate permission store.

The shared **`InputVersion` v1** contract is exactly `{version: 1, project_id, residency_id, network_revision, exact_fingerprint}`. `project_id` is the native project UUID, `network_revision` is existing `dirty_state.revision(ctx)`, and `exact_fingerprint` is existing `workflow_tools._network_input_fingerprint(ctx, exact=True)`. Add a server-generated UUID `residency_id` to `ProjectContext`, fresh on construction and on network/context reload or replacement; never read it from persisted project files, carry it from a replaced residency, or accept it from model/tool arguments. A non-mutating binding to the same resident context keeps it. `set_network`, `reset_network`, `build_context`, restore/load and adopt paths must either construct a fresh residency or rotate it under their existing native mutation ownership, even if they preserve the existing lock. Thus reload/replace-back-to-identical-bytes cannot recreate an old admitted identity. `capture_input_version(ctx)` is a proposed helper requiring the caller to hold the actual mutation lock and acquiring the existing solver-state RLock for coherent config/fingerprint reads (reentrant when the caller already holds it); it fails closed on absent project/residency, unreadable inputs or invalid counter. It never resolves/hydrates/activates a project. Equality compares every field, including version; serialization is data, never authority. HH-02 and HH-04 import this same helper instead of adding a second hash or world model. Retain the legacy fingerprint alongside this value only for existing brief/cache compatibility.

`MutationAdmission` carries:

- Internal format/version and a unique invocation nonce.
- Server-resolved owner id, project UUID and registry key; task id; step id; exact `begin_step` attempt id; runner session id `run:<task_id>`; tool-use/call id; envelope grant id.
- The exact canonical JSON arguments and SHA-256, and approved complete card JSON/digest. Serialize once with non-finite values rejected; decode a fresh copy for invocation. The argument dictionary retained by the model/caller must not remain mutable authority.
- Expected legacy input fingerprint (existing envelope/brief compatibility), expected shared `InputVersion`, and the expected chain head/call id (or grant anchor).
- In-memory references to the **resolved** `ProjectContext`, its `network` and its actual `mutation_lock`. These references are never serialized to the model or restored from disk; the shared residency id detects loss/replacement across invocations and restarts.
- When HH-02 is active: software-bound parent/thread id and generation, `requirements_revision` and `records_digest`, plus the exact candidate-input/predicate evaluation binding. Those values must match its shared owner-store CAS contract through native write/readback; an old requirement receipt cannot be reused. When HH-04 is active, consume its private ref/preview binding through the same native identity check, without accepting a serialized ref as approval.
- Captured current restriction revision/confirmation revision and a deadline/abort observation necessary for worker pickup. Reuse existing restriction/confirmation checking; a copied snapshot is not a grant.

The descriptor is authority only when matched to current native task/envelope/ACL state. A serialized descriptor, copied envelope id or hash grants nothing. Attach it to this dispatch's local invocation state and copied worker context, not mutable session-wide “last admission” fields. Two calls on one session must not share or overwrite it. Clear/reset any temporary ContextVar in `finally`; avoid placing it in model-visible JSON.

`MutationReceipt` is a native, frozen, out-of-band result. It binds the same owner/project/task/step/attempt/call/grant/nonce, argument hash and card digest; captured before/after shared `InputVersion` values and legacy fingerprints; verified native card readback outcome; and `not_started|started|verified|uncertain`. A handler dictionary containing matching keys is insufficient. The loop receives the receipt from its own helper/closure together with the ordinary result and passes it explicitly to task completion. Never parse receipt authority from arbitrary handler JSON. Keep `_edit_receipt` for existing model/UI compatibility, but attach it after the handler result so a handler cannot overwrite the native value.

Version the envelope sidecar to **v2**, preserving v1 files as readable historical state. New proposed envelopes can be v2, but only a new user grant creates the v2 admission anchors:

- Existing grant-time legacy fingerprint plus the captured shared `InputVersion` as `input_version`. No additional envelope-only runtime-generation field is needed.
- Each v2 chain entry binds its existing `after_change` call id and legacy fingerprint plus the captured after `InputVersion`, task step/attempt identity and a native receipt identity/digest. Do not include raw model inputs in the chain.
- A bounded per-attempt admission state in the existing task step, keyed by the existing attempt id and call id: `prepared`, `started`, `verified`, `rejected_before_effect` or `uncertain`, with identity digests and final native receipt reference/data sufficient to distinguish a started attempt after restart. Reuse the task's existing attempt/worker and uncertainty machinery. There must be no second unbounded event database. Preserve existing task/result size limits and native `_stored` bounds; invalid/missing required state fails closed.

Old v1 grants never get synthetic exact anchors or automatic v2 authority. Reading/displaying/reconciling old state remains possible. Resuming unattended operation requires a new explicit current brief/grant. A new backend runtime after restart likewise requires explicit regrant before any new unattended mutation, because in-memory context generation and edit counter are not durable proof of continuity. Recovery of an already submitted native job/uncertain attempt is observational; it does not resubmit it. Process restart must not cancel, rerun or silently block already running ordinary jobs as a migration side effect.

Do not change legacy run/cache/chart fingerprint bytes. Exact identity is an additional admission anchor. If exact fingerprinting fails, or context's lock/network object differs from the captured one, no fallback to legacy hash, active foreground, disk snapshot or another same-named project is allowed.

## Sequence and linearization points

### 1. Preflight and approval, with no project lock held during a wait

Keep the shared dispatch's offered-tool allowlist, strict assurance tool guard, restrictions, validation, task admission, preview and confirmation ordering. `run_envelope.admit` still performs its conservative preliminary scope/budget/chain checks and records approval under the existing policy. A `used` audit row is an **authorization record**, not proof of execution or successful chain settlement.

At the preflight under the runner's existing locks, capture expected input identity from the actual last v2 chain/grant, not from whatever inputs happen to exist later. Check the current legacy/exact fingerprint and revision against that anchor. The descriptor is finalized with the existing step/attempt ticket after `begin_step`; no locks remain held while enqueuing/waiting for `_TOOL_EXECUTOR`. The descriptor has no expiry exemption from the envelope, dispatch or task budgets.

Unsupported unattended shapes are rejected here before `tool_running`, handler scheduling, dirty marking, undo snapshot, new solve job or native input change. A refusal must not fabricate a successful edit receipt or completion row. Existing preliminary `used` records, if already recorded, are retained as history and paired with refusal; do not delete audit history or refund a consumed allowance as though nothing was attempted.

### 2. Pickup and atomic native admission on the actual worker

Introduce proposed `execute_mutation(admission, ..., invoke)` in `run_envelope.py` and use it only for the exact supported ordinary envelope slice. The helper:

1. Rechecks current confirmation/restriction policy on pickup before touching inputs. Refuses expired/cancelled/deadline-lost work. Resolves no new project and takes no registry/hydrate lock.
2. Acquires **the captured `ctx.mutation_lock`**, using the runner's existing bounded `LOCK_TIMEOUT_SECONDS`. Checks that the bound request context is the captured context and that `PyPSAService.get_lock()` is the captured lock; checks project UUID, registry key, network object and shared residency id. A process foreground switch to another project must not redirect work. A replacement within the bound context refuses.
3. Takes `ctx.solver_state_lock` in the established mutation → solver-state order and retains it through bounded native write/readback/after-capture, because `routers/simulation.py:update_solver_config` and other configuration writers currently take that lock without the mutation lock. Releasing it after a precheck would leave a second input-identity gap. Refuses a live solver/study that native edit rules prohibit; fingerprinting or state unreadability refuses. Reuses `Runner.recheck` semantics for fresh active owner/ACL, project binding, task state, edit lock and harness hold. A task read alone is not sufficient authority.
4. Under a short `assistant_tasks._LOCK` interval, reloads the exact task/step/attempt and v2 envelope, verifies grant id/state/residency, owner/project/task, live claim/attempt, unexpired wall time, remaining task/envelope budgets, chain head, current restrictions and exact args/card. Compares the current captured `InputVersion` and legacy fingerprint to the expected before identity while the project lock remains held. `edit_card.require_current` must also be inside this interval of project ownership (it need not hold the task-file lock). The envelope bounds/at-grant/instance decision must be recomputed against the immutable actual call and current complete native card.
5. Records `started` durably for this exact attempt while holding the task-file lock and **before any dirty/undo/native effect**. Failure to save it, record required approval or validate any authority refuses before invoking the handler. This save is the **admission linearization point**. Release the task-file lock immediately. No task-file lock is held through native handler execution.
6. Mark dirty, bump network revision **once**, and take the ordinary undo snapshot for this covered invocation, now inside the worker-owned mutation interval and after the checks. Skip the old loop's pre-worker copies for this invocation. Preserve their behavior for other paths and existing best-effort undo policy; this ticket does not silently make snapshot availability a new grant. In particular a stale refusal has no dirty/revision/undo footprint. The pinned `network_undo.push_undo_snapshot` calls `_backup_network_ts_to_user_ts(n)`, which can synchronize live input data. For the covered path, extract capture from push: perform backup/export on an unregistered private copy of network + user time series, then push the captured bytes/user-ts/template payload into the **actual** context's existing undo stack. Do not mutate the live input store merely to capture undo, or include such a synchronization as an unreviewed envelope edit. Reuse existing serialization/stack semantics, and retain failure logging. This is one small internal native capture helper, not a new snapshot framework.
7. Call the existing `update_component` dispatcher with frozen-decoded args through the existing `experiment_execution.invoke` seam and `edit_card.approved` context. Its native `_update_component` reacquires the exact same existing RLock on the same thread; this is supported reentrancy, not a new lock hierarchy. Retain the existing native checks and schema. The handler must execute synchronously; it may not return an async job masquerading as a synchronous mutation.

The source-feasible order for this exact path is **mutation → solver-state**, with same-thread native reacquisitions reentrant. During undo export it may briefly add the existing global netCDF I/O lock innermost; release I/O before pushing the existing undo stack. Project and solver-state lock pickup must both have bounded waits using the existing runner timeout, and the original attempt deadline is rechecked afterward. This is a bounded synchronous input transaction, never a card/job/provider/network wait. Preview on an isolated copy may not hydrate/activate/register a project or acquire a live foreign-context lock. Extract native row readback/identity capture from `edit_card.receipt` into a small internal helper for this path and defer optional section/flow/undo display decoration until after releasing the locks; decorations cannot change receipt authority. Do not call `Runner.recheck` while holding unrelated owner-file transactions. Preserve existing `PyPSAService` order; do not introduce task-lock → project-lock acquisition in grant, admission, cancellation or recovery.

The source lock trace supporting that choice is concrete:

| Pinned path | Acquisitions while processing this slice |
|---|---|
| `chat_tools._validated_update_payload` → `network_crud._update_component` | Schema/prefill reads; study-state read; same-context mutation RLock. Generic merge, parts derivation, component identity and provenance helpers operate on the network without acquiring registry/hydrate locks. |

### 3. Readback and settlement before releasing the project lock

Still inside the same worker mutation lock:

1. Obtain `edit_card.receipt` natively, including derived rows. Capture legacy and exact after-input fingerprints and after revision with the coherent-read helper. A success-shaped handler result does not substitute for readback. A handler error, failed/partial result, unreadable after identity or any mismatched native row is `uncertain` after `started`.
2. Reload task/envelope under the short task-file lock. If grant/attempt changed, cancellation/revocation occurred after admission, residency changed, or the chain head no longer equals the admitted before identity, persist observation/uncertainty and suspend unattended continuation. Never overwrite the newer head or append to a replacement grant.
3. For a verified still-current attempt, append at most one chain link keyed by call id + attempt id + invocation nonce. Use the **captured in-lock after identity**, never a later ambient `_fingerprint(ctx)`. Update the task brief's legacy fingerprint only when it was the admitted before anchor. Persist the native receipt and its outcome. No-op writes can have a verified attempt receipt and new edit counter, but no invented input-fingerprint transition; update the chain's revision anchor explicitly or append an explicitly marked no-input-change receipt so the next covered invocation has an unambiguous revision anchor. Choose the latter: append a receipt-bound link even when before and after hashes are equal, with `input_changed: false`.
4. Publish no `verified` result until required receipt/chain/task persistence succeeds. If persistence fails after effects, stop as uncertain; never synthesize rollback or rerun. Since task and envelope are separate existing files, require safe write ordering: write task attempt receipt/verified-native-observation first, then envelope link, then expose successful task completion. A crash between writes is an **uncertain incomplete commit**, not permission to replay. Recovery may show the exact observed effect but must require explicit reconciliation/regrant; automatic repair may not create missing authority. If the first write succeeded and the chain write failed, the run cannot advance from the attempt receipt alone.
5. Release the project lock and return the ordinary result plus out-of-band `MutationReceipt` to shared dispatch. `assistant_tasks.finish_step` may complete only the matching attempt and uses the captured after legacy fingerprint for its brief projection. Its existing generic late rehash is bypassed for this covered path. A human edit now landing between worker return and `finish_step` remains drift against the captured chain; it cannot be absorbed by completion or runner `finally`.

Delete the blanket `run_envelope.settle` authority from `Runner.dispatch.finally` for v2. `tool_running` means a handler was scheduled, never that a native mutation happened. A verified matching native receipt is the only v2 chain-advance source. Keep v1 `settle` only for historical compatibility if still needed by readers/tests; it must never service a resumed v1 unattended execution.

## Identity, cancellation, deadlines, restart and concurrency

| Boundary | Required behavior |
|---|---|
| Edit after runner precheck, before worker lock | Compare under worker lock fails `envelope_drift` (or exact typed unreadable/binding refusal); no handler input effect, dirty bump, undo snapshot or chain link. Pause. |
| Edit after worker release, before runner/task completion | Covered write may complete with its captured receipt. Later external edit remains outside the captured after identity; next unattended action pauses. No final rehash extends the chain. |
| Writer obeys same project lock | It cannot interleave inside compare → write → native readback → capture. Other project mutation locks remain usable. |
| Context/registry rebind | Owner UUID, project UUID, registry slot, captured context/lock/network must still match. Same name or same hash in another context is insufficient. Resolve before lock; never reacquire registry lock inside it. |
| ABA edit then undo | A bumped context revision invalidates the descriptor even if exact fingerprint returns to its before value. Writers outside native discipline are not claimed covered; exact fingerprint still detects actual changed inputs when counters miss them. |
| Queued tool future cancelled before pickup | Existing `Future.cancel()` success guarantees no invocation. Record not-started/rejected state without effects or chain link. No retry is added by HH-01. |
| Worker waiting for project lock | Bounded wait, then typed busy/refusal. Before linearization a cancelled task, revoked envelope, expired wall time or execution deadline prevents execution even if the lock becomes available later. Recheck after acquiring it. |
| Cancellation/revoke before `started` save | No new effect. A preliminary envelope approval does not override cancellation. |
| Cancellation/revoke after `started` save | Cannot promise rollback of a synchronous native write. Let native cleanup finish under its lock; preserve its observed receipt as uncertain/suspended when authority changed. Do not advance unattended chain or retry automatically. Clearly report “may have changed; review”. |
| Dispatch execution timeout after worker pickup | Existing timeout cannot kill a Python thread. Mark this invocation closed to new admission, retain worker/attempt identity and uncertainty, and block replacement attempts until native reconciliation. A late worker that has not crossed `started` must refuse at final admission. A worker already admitted may finish its own native write/observation, but cannot convert a timeout/cancel into automatic continuation or replace a newer receipt. |
| Crash/restart before/after effect | Existing task `running/uncertain` and the added attempt state prevent replay; absence of a full durable commit is uncertainty. Residency id mismatch after reload/restart requires regrant. Existing lease takeover is not new effect authority. |
| Duplicate finalization | Same call/attempt/nonce may be observed twice but creates at most one link and no second native handler invocation. Different attempt/nonce cannot reuse a prior approval/receipt. |
| Two runner instances/processes | Existing leases/sidecar file guards still arbitrate tasks. Project RLocks protect only one process. Phase A does not support two independent backend processes mutating the same project memory/disk. Do not market distributed revision atomicity; additional cross-process project fencing requires a separate gate. |

The existing task `_outcome` treats many errors from effectful calls as uncertain. Add a narrow **native-proven rejected-before-effect** outcome for matching covered attempts if needed to distinguish safe refusal from uncertain partial execution. Never infer “no effect” merely from an HTTP exception, `tool_error`, or an envelope refusal after handler start. No-progress/retry limits and manual reconciliation remain existing policies; HH-01 does not grant free automatic retry on safe rejection.

## Interaction with effects, requirements and budgets

- Ordinary envelope Phase A and checked `harness.effects` must not both reserve/execute one call. The current strict assurance guard remains first and determines whether that path is supported. Existing checked update operations continue through `reserve`/`execute`, native contract/readback, owner-store transaction and uncertainty semantics. An envelope marker cannot bypass strict capability policy. Any future combined authority requires a separate reviewed composition rule and lock analysis.
- HH-02, the typed-requirements slice, is an additional native veto, never grant authority. Until active, report requirement enforcement as outside this standalone slice; do not invent a permissive placeholder hook. When active, native admission uses **mutation → solver-state → existing parent owner-store transaction** order, validates the exact requirement record revision/digest and candidate predicates before the `started` linearization point, and retains that same store transaction through native write and post-write readback/`InputVersion` capture. A prevalidation-only CAS check cannot authorize a future write after releasing the store guard. Requirement updates and sibling durable-conversation writers must share that owner-store transaction/CAS discipline to prevent lost updates. Candidate predicates are bounded native computations on the already-resolved immutable call/state, with no provider/network/approval wait. Budget-only writers acquire owner-store only and never wait for native/solver locks. No store-first caller may invoke this native admission path. Release the owner store after native readback/version capture, before optional UI decoration; a later requirement update cannot retroactively alter this admitted revision, and current-compliance claims must recheck it.
- Keep existing task caps, envelope expiry, solve count, round count, confirmation records and runner EUR metering. The authoritative remaining/expired checks happen again at pickup under the short admission transaction. No solve is initiated by Phase A. Rejected/uncertain attempts keep audit/attempt attribution and do not mint fresh allowance or reset caps. HH-03 adds durable provider/reviewer reservations independently; a project lock is never held around a provider/reviewer call, network fetch, budget quote or human approval wait.
- No automatic researched input value is introduced by these two fields. Existing research keys and `research:` provenance still force the ordinary explicit card and suspend the unattended chain as an unsupported explicit step.

## Phase B: async snapshot admission, separately gated

The baseline async behavior is materially different from a synchronous mutation:

- `chat_tools.run_simulation` calls `routers/simulation.py:run`; `run_ac_pf_stage` calls `run_ac_pf`. They claim/start native threads under solver-state synchronization. The actual worker consumes network/config later through native solver services. Wrapping the **submission handler** in a mutation lock does not prove what the solver later reads.
- `chat_tools.solve_queue_enqueue` calls `routers/solve_queue.py:enqueue_solve`. `_config_snapshot_for` captures solver configuration, and `SolveQueue.enqueue_unique` durably records the job before publishing it. `services/solve_queue.py` later selects a resident context (including unsaved inputs) or hydrates a new context. This is not an immutable whole-input snapshot. An existing `already_queued` job can belong to a different admitted input identity.

Phase A therefore cards/pauses these operations and does not claim them revision-atomic. An explicit ordinary job may run under its existing native lifecycle. It cannot silently bridge or advance the suspended atomic envelope chain. Already queued/running jobs continue and are observed through existing job/Activity/continuation machinery; rollout never resubmits or cancels them as a format migration.

Phase B may re-enable **one native run adapter at a time** only after a new plan review and deterministic tests establish this contract:

1. Under the actual source project's mutation lock (solver-state lock only for coherent config capture), recheck envelope/ACL/task/attempt/policy/caps and expected exact source identity. Produce an immutable native input snapshot that covers the network inputs, snapshots/weights, user time series and solver config actually consumed by that adapter. Record source project and captured shared `InputVersion`, before legacy/exact fingerprints, configuration digest, snapshot manifest/content digest, exact native job id and attempt/call/grant id. A config-only snapshot or path to mutable `network.nc` does not satisfy this.
2. Snapshot persistence uses existing safe native serialization and the existing global netCDF I/O lock **inside** project mutation ownership where needed, following mutation → netCDF order. Resolve/hydrate before holding source locks. Never transfer an acquired RLock to a worker, retain a project/IO lock across queue wait, solve, provider or human wait, or make the queue worker silently choose the current resident network in place of the admitted snapshot.
3. Persist the exact submission/attempt/snapshot binding before exposing the job for pickup, extending `enqueue_unique`'s existing persist-before-publish behavior. Submission may be idempotent only when existing job + adapter + source snapshot/config/attempt identity match exactly. Project-only `already_queued` is not proof of this attempt's admission; a mismatch pauses/refuses without a duplicate job or changing the existing one.
4. At pickup the native worker loads the exact immutable snapshot into its own correctly bound solve context, verifies manifest/content digests and project/job/attempt identity, and rechecks the adapter's cancellation/access/restriction/policy rules at the native point where they currently apply. If required snapshot data are absent/corrupt, no fallback to live resident/disk/current inputs. Queued cancellation before pickup prevents a new solve; post-start cancellation retains native uncertainty/cleanup rules.
5. Native job/run evidence records the exact input snapshot identity. Submission receipt means only accepted/submitted. Only matching native terminal evidence and verified adapter-specific publication/reconciliation authorize a completed solve claim. Results from a private snapshot do not overwrite a changed live project or advance its input chain; any publication back to the live context requires its own current-input compare under the native write lock.
6. Persisted/restarted jobs use the same immutable identity and existing native recovery/no-replay rules. Lost snapshot or unknown submission is unavailable/uncertain, not a reason to recreate it from current inputs. Solve caps count admitted attempts according to the existing conservative policy; crash/timeout never releases unknown work for another automatic solve.

Phase B dependencies/owners: solver lifecycle owner (`routers/simulation.py:run`, `run_ac_pf`, `services/solver_service.py`), queue owner (`routers/solve_queue.py:enqueue_solve`, `_config_snapshot_for`; `services/solve_queue.py:SolveQueue.enqueue_unique` and native worker; `services/solve_job_store.py` schema/serialization), job/evidence owner (`harness/job_adapters.py`, `harness/continuation.py`, `services/run_evidence.py`) and Harness owner. Exact snapshot storage/retention, private-context result publication and any persisted job schema migration are **unresolved Phase B design choices requiring this separate gate**, not authorization to extend Phase A's file list.

## Adversarial review loops and stop conditions

The implementation owner must record each loop as a concrete review note linked to test IDs and the exact implementation revision. Do not call this specification's source review an implementation test result.

1. **Seed before fix.** Commit/review the minimal deterministic A01 barrier regression first in the later implementation branch. Demonstrate baseline failure due to the specific interleaving, with A02 as its positive control. If it fails for unrelated fixtures, card widening or unbound context, repair the test before implementation.
2. **Lock/authority review.** Native mutation reviewer traces actual thread + lock object from `Runner.dispatch` through shared loop to CRUD, and independently tries A03, A05, A07, A09, A18 and A19. Harness reviewer checks grant/attempt/argument identity, all excluded shapes and no dispatch bypass. Any unsupported lock or handler behavior shrinks scope/changes plan before coding further.
3. **Settlement/recovery attack.** Reviewer independently introduces A04, A11–A13, A15 and A17, including after-effect persistence failure and a forged success result. A safe precheck with a vulnerable settle is a failed review. Re-run focused relevant tests after fixes; do not widen to Phase B as a “quick follow-up” in the same GO.
4. **Compatibility/rollout review.** Run A14/A16 and existing envelope/runner/dispatch/edit/effects/restriction tests offline. Check v1 readable/non-executing behavior, disabled rollout, explicit stepwise recovery, job observations and no duplicated attempts. QA follows repository `pypsa-gui/TESTING.md` gates, with existing alias/layout/error-kind checks as appropriate.
5. **Handoff GO.** Harness + native reviewer agree the exact coverage table, passing forced schedules, bounded lock order and uncertainty evidence. Findings are fixed and the relevant tests repeated; no unresolved P0/P1 effect-admission/recovery issue may be relabeled a documentation limit for this covered slice. Phase B remains disabled and separately gated.

No infinite review loop is intended: after a material architectural finding or two failed fix/review iterations for the same invariant, stop expansion and produce a bounded amendment identifying the failed invariant and smallest revised slice for gatekeeper review. Do not paper over an unresolved race with longer sleeps/timeouts or broaden authority to make a test pass.

## Rollout, rollback and completion evidence

Add one backend-only capability flag in the existing envelope module, proposed `PYPSA_GUI_ENVELOPE_ATOMIC_MUTATIONS=1`, default **off** until the above gate passes. The disabled default **does not silently fall back to legacy unattended mutation admission**: existing envelopes/tasks/jobs stay inspectable, ordinary explicit card/stepwise paths work, but new unattended effectful dispatches pause with a clear atomic-admission-unavailable reason. V1 grants require explicit current regrant. A user must not be told an old full workflow is now atomically protected.

Rollback turns off new unattended admissions and suspends continuation, retaining all tasks, receipts, audits and running/queued native jobs for existing observation/reconciliation.
