## Assessment

This is already an unusually substantial domain harness. It has provider-neutral schemas and dispatch, native business tools, permissions and cards, saved restrictions, finite budgets, event-sourced session history, deterministic compaction, durable parent threads, immutable authenticated evidence, calculation profiles, checked publication, independently read-back edits, explicit uncertainty/reconciliation, source-bound browser ACKs, native task/job receipts, a server runner, approval envelopes, bounded experiments, and offline adversarial evaluation. Research recommendations to “add tools/memory/checkpoints/approvals/a verifier/a runner/MCP” would mostly duplicate shipped work.

The useful next work is integration and domain coverage: enforce persistent constraints from native state across ordinary typed chat; complete bounded headless correction loops and source-ledger research already specified; extend checked results through precise adapters; close displayed-data coverage; and make resource reservations/recovery coherent across provider/reviewer/runner calls. Distributed execution and OS isolation are separate, optional projects, not prerequisites to these bounded extensions.

## Extension candidates, ordered, with minimal seams and acceptance

These are research-to-roadmap candidates, not authorization to implement. P0 means next safety/reliability slice before expanding unattended authority; P1 is next useful bounded extension; P2 is optional scale/polish. “Existing” means attach research to an already named ticket rather than create a duplicate.

### 1. P0 — Checked plausibility adapter (existing Assurance issue 10; depends K #851)

**Why/UX:** “Do these results make sense?” can produce source-supported checked findings rather than an unsupported-capability refusal. Native warning display alone cannot carry the checked badge.

**Seam:** `assurance.Turn.tool_guard` checks exact `get_results` args; a bounded evidence/profile adapter around K's native `services/results/plausibility.py`; existing MAC/capture/replay/publication stores. Preserve general get_results refusal. Assurance owns publication, K/domain services own rules, GK B reviews admission; study-harness 05 consumes `plaus.*` facts, not a parallel rule implementation.

**Acceptance:** Valid first-five-rule positive control; injected extra verdict/numeric claim withheld; wrong source/run/window and stale fingerprint refuse; MAC tampering/replay mutations fail; lookup re-derives same findings; ordinary get_results variants still never execute on checked turns. Existing catalogue-wide refusal test must express this argument-specific exception without weakening others.

### 2. P0 — Finish bounded headless L1/L2 loops (existing study-harness 04/05)

**Why/UX:** A detached study can fix a bounded input defect or triage an infeasible solve, then stop with useful evidence when no progress is possible. Runner alone currently advances admitted fixed steps.

**Seam:** `runner.py` invokes shared `loop.run_turn` with package stage instruction and per-stage tool subset; `run_profiles.py` and `run_gates.py` select tunables/native facts; verified edit receipts append to existing run ledger. L1 ≤3 rounds; L2 ≤2 rounds, ≤2 edits/round, no re-solve without changed inputs. Harness owns policy; engine owners retain native coupling/margin loops.

**Acceptance:** Exact offered tool subset; seeded missing series corrected once; repeated fail-set+fingerprint stops `no_progress`; no receipt means no successful ledger row; outside tunable/envelope is carded/refused; solve/token/EUR use measured by server; restart midway recovers native receipt and never duplicates a solve. Duplicate generic retry-loop proposals should fold here; task two-retry cap is already done.

### 3. P0 — Make provider/reviewer resource admission durable (partial existing live-voice 09 / assurance 08)

**Why/UX:** Budget remaining stays honest across episode restart, detached review and concurrent requests; users receive an explicit exhausted/unknown-usage stop.

**Seam:** Reuse durable parent reservation/settlement helpers (`durable_conversation.py:397,504`), runner charge and usage normalization in provider wiring; add pre-send reservation at the shared provider/reviewer boundary, with request/attempt identity and defined conservative unknown-late-usage handling. Avoid another budget database. This is an integration gap, not absence of caps or a confirmed unlimited-spend exploit.

**Acceptance:** Two concurrent sends cannot each spend the same remaining allowance; crash after send/before settlement preserves reservation; resumed episode cannot reset cap; cached usage semantics consistent across OpenAI wires; late completion settles at most once; timeout does not free an uncertain in-flight reservation; all calls stay offline/mock in initial tests. Harness/provider owners; coordinate live-voice budget interface.

Keep policy approvals separate from business preferences.

### 9. P1 — Close authority-to-effect fingerprint race (new hardening candidate; known documented limit)

**Why/UX:** An unattended envelope pauses on a concurrent human edit instead of incorporating it into the approved chain.

**Acceptance:** Barrier test puts edit exactly between runner's precheck and handler mutation: envelope refuses/pauses without claiming that edit; unchanged case passes; no deadlock on handler locks, no blocking unrelated project requests, no duplicate receipt.
