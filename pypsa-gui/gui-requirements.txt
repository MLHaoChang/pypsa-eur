# The build environment for the frozen app (workstream I, D14).
#
# A PIP-WHEEL venv, deliberately NOT the pixi/conda environment: freezing a
# conda env produces a build that works on the developer's box and fails on a
# clean machine.
#
# Every pin is GENERATED from the installed `desktop` environment
# (`importlib.metadata`), never typed — a hand-written draft of this file had
# 8 of its 11 guessed versions wrong. Regenerate rather than edit.
#
# Direct requirements only; pip resolves the transitive set. Measured on
# 2026-07-30 for cp313 / macOS arm64: **79 distributions, all from PyPI
# wheels**, with ONE exception — `proxy_tools 0.1.0` (via pywebview) publishes
# no wheel. It is pure Python with no dependencies, so it builds without a
# compiler, but `--only-binary=:all:` will refuse it. Allow that one sdist.
#
# netCDF4's macOS arm64 wheel is `cp311-abi3-macosx_14_0_arm64`, which is why
# the .spec sets LSMinimumSystemVersion 14.0. It is abi3, so it covers 3.13
# despite the cp311 tag.
# ── the numerics stack: pinned to the TESTED versions ───────────────────────
#
# NOT transitive leftovers. Left to pip, `pypsa==1.1.2` resolved
# `pandas 3.0.5` and `numpy 2.5.1`, while the whole backend suite runs against
# `pandas 2.3.3` / `numpy 2.4.6` in the pixi `desktop` environment — a MAJOR
# pandas version between the app that ships and the app that was tested, in a
# codebase whose CLAUDE.md documents pandas-version-specific workarounds for
# MultiIndex reindexing and dtype coercion.
#
# This is the same discipline `pixi.toml`'s single solve group enforces for the
# conda side, applied to the pip side, and it is the reason this file pins more
# than the direct imports. Verified installable from wheels for cp313/arm64.
